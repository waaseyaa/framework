# FW-2757 — verified-email authentication eligibility

Status: implementation candidate

## Intent

Make `auth.require_verified_email` an enforced authentication policy rather
than an inert configuration value. When enabled, an active but unverified
framework User must not acquire or retain an authenticated identity through
registration, password login, direct `AuthManager` use, pending 2FA, bearer
resolution, or an existing PHP session. When disabled, supported historical
behaviour remains unchanged.

## Design

- `waaseyaa/user` owns a neutral `AuthenticationEligibilityInterface` and the
  explicit authentication-stage vocabulary consumed by its session boundary.
- `waaseyaa/auth` owns the one implementation. It combines the canonical
  `AuthConfig` with one audited snapshot containing active and verified state.
- `AuthServiceProvider` binds one singleton policy under its concrete,
  auth-owned identity and aliases the neutral interface to it. Auth
  controllers, `AuthManager`, and `HttpKernel` resolve the concrete authority,
  so an earlier provider cannot shadow the security policy with a colliding
  interface binding.
- `SessionMiddleware` re-evaluates both bearer-resolved and PHP-session users
  before authorization. A denied PHP session has its canonical identity keys
  cleared; a denied bearer identity becomes anonymous.
- Verification resend becomes a public, bounded email lookup with uniform
  existence/verification and delivery-failure responses. Independent email/IP
  admission is atomic, and the normalized email is hashed into a fixed-length
  rate-limit key. It never grants a pending or full authenticated identity.
- Authenticated account payloads expose the audited `emailVerified` state to
  the bundled admin client. Its public verification screen accepts an email
  address, so resend remains usable after browser state and cookies are gone.

## Work packages

1. Pin the policy/config contract and complete on/off, active, and verified
   matrix in unit tests.
2. Route every issuance, promotion, and resolution path through the policy.
3. Replace authenticated-only resend with the non-enumerating public flow.
4. Prove the complete lifecycle through production composition and a packaged
   consumer, then run all governed verification gates.

## Compatibility

- The setting continues to default to `false`.
- Invite-created users remain verified and eligible when active.
- Password, rate-limit, session-generation, CSRF, 2FA, and token-consumption
  controls remain independent and are not weakened.
- `AuthManager::login()` remains `void`; an ineligible direct login throws a
  dedicated exception before any session mutation.
- Non-boolean `require_verified_email` configuration is rejected instead of
  being coerced, because ambiguity at an authentication boundary fails closed.
- The public verification snapshot now requires canonical active state; custom
  internal-field readers must supply it rather than defaulting unknown to active.
- New registrations store email addresses in lowercase canonical form. Identity
  lookup retains exact username and exact legacy-email precedence, then uses
  canonical case-insensitive email equality; uniqueness uses the same canonical
  equality so upgraded mixed-case rows cannot be duplicated.
- When verification is required, the bundled admin client retains only the
  pending email needed by the public continuation. It does not manufacture a
  `currentUser` or authenticated redirect from the registration response.

## Exclusions

This change does not redesign email ownership, token cryptography, password
policy, profile/onboarding data, or external-provider trust. External identity
adapters must set canonical verification state through their own reviewed
trust contract before the shared policy can admit the User.

Synchronous mail transports can still produce an observable latency difference
between a no-op resend and a delivered resend. Closing that transport-level
side channel requires a durable queued-mail/outbox contract and is tracked in
#2769; status, body, lookup bounds, limiter
state, and exception behavior are uniform in this change.

## Required evidence

- retained-red tests for every issuance/promotion/resolution path;
- policy-on and policy-off controls, including inactive users;
- anti-enumerating resend and rate-limit tests;
- registration → resend → verify → login → authenticated-request integration;
- bundled-admin payload, public resend form, typecheck, and focused UI tests;
- production route/kernel wiring and packaged-consumer acceptance;
- separate Unit, Integration, Architecture, full preflight, and changed-line
  coverage results bound to the exact candidate commit.
