# FW-2701 — fresh-install semantics for V2 entity evolution

- Parent: `6ebacc3daf2f9decfe4917755bb375fd9a362bf1` (FW-2695 review candidate; this record is stacked on it)
- Contract: `docs/specs/schema-evolution-v2.md` §9, §11, §15 Q3/Q4; `docs/specs/infrastructure.md`; `docs/specs/entity-system.md`
- ADR: pending — the contract decision below requires ratification before an ADR is written
- Issue mirror: `waaseyaa/framework#2701`
- Consumer blocker: `jonesrussell/claudriel#764` (milestone R1, due 2026-10-11)
- Authority: this record; the forge issue is a discussion mirror

## Outcome

One immutable V2 source catalogue must upgrade an existing site and initialize a
fresh one, converging on the same physical schema and the same ledger evidence.
Today the fresh lifecycle diverges. `packages/cli/tests/Integration/FreshInstallV2EntityEvolutionTest.php`
reproduces this through the stock `migrate` runtime: the existing-site case passes,
the fresh-install case fails with `no such table: account` raised from
`packages/foundation/src/Migration/Executor/V2PlanExecutor.php:48`.

## Established facts

Entity schema synchronization behaviour was measured, not inferred, by running
`EntitySchemaSyncRunner::run()` against a registered entity type carrying one
field definition (`user_id`) on each backend:

| Backend | Fresh sync creates `user_id`? | Sync adds `user_id` to an existing table? |
|---|---|---|
| `sql-blob` (framework default) | No | No |
| `sql-column` | Yes | Yes |

`EntitySchemaSync::resolveBackend()` returns `ReservedBackendIds::SQL_BLOB` when a
type declares no backend, and `SqlSchemaHandler` emits per-field columns only on
the `sql-column` branch; the `sql-blob` branch emits entity-key columns plus `_data`.

Two consequences follow, and they are opposite:

1. **`sql-blob` (default).** Synchronization never materializes a per-field column
   in either lifecycle, so a V2 `AddColumn` is the only thing that can create it,
   and it is required in both lifecycles. The issue's stated counterargument to
   running synchronization first — "it creates the current column, after which the
   same unconditional `AddColumn` collides" — does not hold on this backend.
2. **`sql-column`.** Synchronization already owns the column in both lifecycles:
   it emits the column at table creation and additively adds it to an existing
   table. A V2 `AddColumn` naming a registered field column is therefore redundant
   with the field registry, and collides wherever synchronization has already run.

The issue's problem statement treats these as one case. They are not, and any
contract that does not separate them will be silently wrong on one backend.

A ledger-seeding design ("baseline the node on a fresh install and let
synchronization materialize the shape") was drafted and **rejected on this
evidence**: on the default backend synchronization never creates the column, so a
baselined node would leave a site permanently missing it while the ledger and
`migrate --verify` both reported a successful apply.

## Decisions

Ratified in this record:

- **D1.** Compilation stays a pure function of `(CompositeDiff, PlanPolicy)`. No
  live-database state may enter compilation, so `checksum` and `diff_hash` remain
  stable across lifecycles (`docs/specs/schema-evolution-v2.md` §5.2, §15 Q2).
- **D2.** No migration class performs database I/O and no plan emits conditional or
  raw SQL. Any lifecycle awareness lives in the runtime, never in the authored value.
- **D3.** A fresh site and an upgraded site must produce identical ledger evidence
  for the same node. Amended during ratification to cover the `checksum` /
  `diff_hash` pair rather than the whole row; see "Disclosed conflict with D3".
- **D4.** Ownership knowledge flows downward only. `foundation` is layer 0 and
  `entity-storage` is layer 1, so any entity-table knowledge reaching the Migrator
  arrives as plain data supplied by the composition site.

The ordering and authority rule was ratified by the maintainer; it is recorded
under "Ratified contract" below.

## Ratified contract

The canonical entity-schema materializer remains authoritative for entity
base-table existence. Migration authors neither recreate that authority nor
perform database I/O. Targeted materialization happens under the migration
coordinator; unrestricted schema synchronization is **not** run ahead of
existing-site migrations, because that would let it act before a migration's
intended order and validation.

- **C1 — targeted materialization.** Immediately before a V2 node applies, and
  inside that node's coordinator transaction, any *registered entity base table*
  the node's plan targets that is absent is materialized through the canonical
  framework service. Only the targeted tables, never a full sync.
- **C2 — apply.** An existing table missing the requested column applies the
  evolution normally.
- **C3 — already satisfied.** An existing column that *exactly* satisfies the
  declared operation yields an explicit, auditable `already_satisfied` outcome.
  Exactness is decided by comparing the live column against the authored
  `ColumnSpec`; a name match alone is never sufficient.
- **C4 — fail closed.** An incompatible existing column, any ambiguous state, an
  unsafe destructive operation, or an absent table that is *not* a registered
  entity table fails closed. Nothing is skipped because a name exists.
- **C5 — authored plans stay pure.** Immutable, database-I/O-free, no conditional
  or raw SQL. All lifecycle awareness lives in the runtime.

### Behaviour matrix

Table state is evaluated at the node's turn in the topological order.

| Lifecycle | Backend | Table | Materializer (C1) | Column state | Outcome |
|---|---|---|---|---|---|
| Fresh | `sql-blob` | absent | creates keys + `_data` | missing | **applied** |
| Existing | `sql-blob` | present | no action | missing | **applied** |
| Fresh | `sql-column` | absent | creates keys + field columns | present, spec-compatible | **already_satisfied** |
| Existing | `sql-column` | present | no action | missing | **applied** |
| Either | Either | present | no action | present, spec-**incompatible** | **fail closed** |
| Either | Either | absent, not a registered entity table | no action | — | **fail closed** |

**Interrupted initialization.** Materialization, execution, and the ledger write
for one node share that node's coordinator transaction, so an interruption leaves
the node wholly applied or wholly absent. A re-run resumes at the same node.

**Replay.** Unchanged. `hasRun()` short-circuits an applied node and
`guardV2Replay()` still compares stored against computed checksum, throwing in
production-like environments and warning in development-like ones.

### Ledger interaction

- `checksum` is unchanged in every outcome. It hashes authored intent, which does
  not vary by lifecycle.
- `diff_hash` is unchanged: the hash of the **full** compiled plan, recorded even
  when C3 skipped steps. Verification keeps comparing the same value and stays
  sound.
- A nullable `apply_mode` column (`applied` | `already_satisfied`, NULL for rows
  written before this change) is added through the established
  `LedgerSchema/` path, mirroring `V2_0001_add_checksum_columns`. This is an audit
  field, not a second identifier, so §15 Q1's refusal of a parallel identity column
  is not reopened.

### Disclosed conflict with D3

D3 required a fresh site and an upgraded site to produce byte-identical ledger
rows. Under this contract that holds for `sql-blob`, the default backend and the
consumer's case: both lifecycles execute, so `checksum`, `diff_hash`, and
`apply_mode` all match.

It does **not** hold for `sql-column`, and cannot. There the materializer creates
the column during a fresh install, so the node genuinely has no work to do; the
only ways to force an identical row would be to execute a colliding statement or
to record `applied` for work that never happened. Both silently weaken the ledger.

Smallest coherent alternative, and the one adopted: keep `checksum` and
`diff_hash` identical across lifecycles, and let `apply_mode` differ, because the
difference is real and an operator needs to see it. D3 is therefore amended to
cover the hash pair rather than the whole row.

## Exclusions

- Rollback of a V2 node remains refused by `[S1-DB103]`; converting an existing
  ledger row between apply and any other status is out of scope.
- Cross-backend behaviour beyond SQLite is out of scope; `AlterColumn` and foreign
  keys remain compile-time refusals per §15 Q5 and Q6.
- The deployer artifact schema-signature interaction identified during review is
  recorded as a dependency risk, not fixed here.
