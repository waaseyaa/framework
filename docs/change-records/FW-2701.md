# FW-2701 — fresh-install semantics for V2 entity evolution

- Contract: `docs/specs/schema-evolution-v2.md` §9, §11, §15 Q3/Q4; `docs/specs/infrastructure.md`; `docs/specs/entity-system.md`

- Issue mirror: `waaseyaa/framework#2701`

- Authority: this record; the forge issue is a discussion mirror

## Outcome

One immutable V2 source catalogue must upgrade an existing site and initialize a
fresh one, converging on the same physical schema and the same ledger evidence.
Today the fresh lifecycle diverges. `packages/cli/tests/Integration/FreshInstallV2EntityEvolutionTest.php`
reproduces this through the stock `migrate` runtime: the existing-site case passes,
the fresh-install case fails with `no such table: account` raised from
`packages/foundation/src/Migration/Executor/V2PlanExecutor.php:48`.

## Established facts

Entity schema synchronization behaviour was measured, not inferred, by running
`EntitySchemaSyncRunner::run()` against a registered entity type carrying one
field definition (`user_id`) on each backend:

| Backend | Fresh sync creates `user_id`? | Sync adds `user_id` to an existing table? |
|---|---|---|
| `sql-blob` (framework default) | No | No |
| `sql-column` | Yes | Yes |

`EntitySchemaSync::resolveBackend()` returns `ReservedBackendIds::SQL_BLOB` when a
type declares no backend, and `SqlSchemaHandler` emits per-field columns only on
the `sql-column` branch; the `sql-blob` branch emits entity-key columns plus `_data`.

Two consequences follow, and they are opposite:

1. **`sql-blob` (default).** Synchronization never materializes a per-field column
   in either lifecycle, so a V2 `AddColumn` is the only thing that can create it,
   and it is required in both lifecycles. The issue's stated counterargument to
   running synchronization first — "it creates the current column, after which the
   same unconditional `AddColumn` collides" — does not hold on this backend.
2. **`sql-column`.** Synchronization already owns the column in both lifecycles:
   it emits the column at table creation and additively adds it to an existing
   table. A V2 `AddColumn` naming a registered field column is therefore redundant
   with the field registry, and collides wherever synchronization has already run.

The issue's problem statement treats these as one case. They are not, and any
contract that does not separate them will be silently wrong on one backend.

A ledger-seeding design ("baseline the node on a fresh install and let
synchronization materialize the shape") was drafted and **rejected on this
evidence**: on the default backend synchronization never creates the column, so a
baselined node would leave a site permanently missing it while the ledger and
`migrate --verify` both reported a successful apply.

## Decisions

Ratified in this record:

- **D1.** Compilation stays a pure function of `(CompositeDiff, PlanPolicy)`. No
  live-database state may enter compilation, so `checksum` and `diff_hash` remain
  stable across lifecycles (`docs/specs/schema-evolution-v2.md` §5.2, §15 Q2).
- **D2.** No migration class performs database I/O and no plan emits conditional or
  raw SQL. Any lifecycle awareness lives in the runtime, never in the authored value.
- **D3.** A fresh site and an upgraded site must produce byte-identical ledger rows
  for the same node. No column is added to distinguish the two, per §15 Q1's
  refusal of a second identifier and the issue's own convergence criterion.
- **D4.** Ownership knowledge flows downward only. `foundation` is layer 0 and
  `entity-storage` is layer 1, so any entity-table knowledge reaching the Migrator
  arrives as plain data supplied by the composition site.

Pending ratification: the ordering and authority rule (see Open decision).

## Open decision

Which component is authoritative for an entity base table's existence at V2 apply
time, and what happens when a V2 plan names a registered `sql-column` field column.
The candidate contracts are recorded in the issue thread with their tradeoffs.
Implementation is blocked on this answer because the three candidates place the fix
in three different components and have materially different blast radii.

## Work packages

1. **WP01 — reproduction.** Executable fresh-install regression at the stock
   `migrate` boundary, plus the entity-evolution fixtures. Landed red.
2. **WP02 — contract.** Record the ratified rule in
   `docs/specs/schema-evolution-v2.md` and the affected mapped specs. Blocked on
   the open decision.
3. **WP03 — implementation.** Smallest coherent change satisfying WP02, test-first.
4. **WP04 — lifecycle proof.** Absent table, table present without the column,
   table already containing the column, interrupted initialization, replay, and
   read-only command truthfulness across both backends and both discovery paths
   (package-declared and root-application), proving package and root-application
   migrations behave identically.

## Exclusions

- Rollback of a V2 node remains refused by `[S1-DB103]`; converting an existing
  ledger row between apply and any other status is out of scope.
- Cross-backend behaviour beyond SQLite is out of scope; `AlterColumn` and foreign
  keys remain compile-time refusals per §15 Q5 and Q6.
- The deployer artifact schema-signature interaction identified during review is
  recorded as a dependency risk, not fixed here.
