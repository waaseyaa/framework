## Outcome

One immutable V2 source catalogue must upgrade an existing site and initialize a
fresh one, converging on the same physical schema and the same ledger evidence.
At the original baseline, the fresh lifecycle diverged. `packages/cli/tests/Integration/FreshInstallV2EntityEvolutionTest.php`
reproduced this through the stock `migrate` runtime: the existing-site case passed,
the fresh-install case failed with `no such table: account` raised from
`packages/foundation/src/Migration/Executor/V2PlanExecutor.php:48`.

## Established facts

Entity schema synchronization behaviour was measured, not inferred, by running
`EntitySchemaSyncRunner::run()` against a registered entity type carrying one
field definition (`user_id`) on each backend:

| Backend | Fresh sync creates `user_id`? | Sync adds `user_id` to an existing table? |
|---|---|---|
| `sql-blob` (framework default) | No | No |
| `sql-column` | Yes | Yes |

`EntitySchemaSync::resolveBackend()` returns `ReservedBackendIds::SQL_BLOB` when a
type declares no backend, and `SqlSchemaHandler` emits per-field columns only on
the `sql-column` branch; the `sql-blob` branch emits entity-key columns plus `_data`.

Two consequences follow, and they are opposite:

1. **`sql-blob` (default).** Synchronization never materializes a per-field column
   in either lifecycle, so a V2 `AddColumn` is the only thing that can create it,
   and it is required in both lifecycles. The issue's stated counterargument to
   running synchronization first — "it creates the current column, after which the
   same unconditional `AddColumn` collides" — does not hold on this backend.
2. **`sql-column`.** Synchronization already owns the column in both lifecycles:
   it emits the column at table creation and additively adds it to an existing
   table. A V2 `AddColumn` naming a registered field column is therefore redundant
   with the field registry, and collides wherever synchronization has already run.

The issue's problem statement treats these as one case. They are not, and any
contract that does not separate them will be silently wrong on one backend.

A ledger-seeding design ("baseline the node on a fresh install and let
synchronization materialize the shape") was drafted and **rejected on this
evidence**: on the default backend synchronization never creates the column, so a
baselined node would leave a site permanently missing it while the ledger and
`migrate --verify` both reported a successful apply.

## Decisions

Ratified in this record:

- **D1.** Compilation stays a pure function of `(CompositeDiff, PlanPolicy)`. No
  live-database state may enter compilation, so `checksum` and `diff_hash` remain
  stable across lifecycles (`docs/specs/schema-evolution-v2.md` §5.2, §15 Q2).
- **D2.** No migration class performs database I/O and no plan emits conditional or
  raw SQL. Any lifecycle awareness lives in the runtime, never in the authored value.
- **D3.** A fresh site and an upgraded site must produce identical ledger evidence
  for the same node. Amended during ratification to cover the `checksum` /
  `diff_hash` pair rather than the whole row; see "Disclosed conflict with D3".
- **D4.** Ownership knowledge flows downward only. `foundation` is layer 0 and
  `entity-storage` is layer 1, so any entity-table knowledge reaching the Migrator
  arrives as plain data supplied by the composition site.

The ordering and authority rule was ratified by the maintainer; it is recorded
under "Ratified contract" below.

## Ratified contract

The canonical entity-schema materializer remains authoritative for entity
base-table existence. Migration authors neither recreate that authority nor
perform database I/O. Targeted materialization happens under the migration
coordinator; unrestricted schema synchronization is **not** run ahead of
existing-site migrations, because that would let it act before a migration's
intended order and validation.

- **C1 — targeted materialization.** Immediately before a V2 node applies, and
  inside that node's coordinator transaction, any *registered entity base table*
  the node's plan targets that is absent is materialized through the canonical
  framework service. Only the targeted tables, never a full sync.
- **C2 — apply.** An existing table missing the requested column applies the
  evolution normally.
- **C3 — already satisfied.** An existing column that *exactly* satisfies the
  declared operation yields an explicit, auditable `already_satisfied` outcome.
  Exactness is decided by comparing the live column against the authored
  `ColumnSpec`; a name match alone is never sufficient.
- **C4 — fail closed.** An incompatible existing column, any ambiguous state, an
  unsafe destructive operation, or an absent table that is *not* a registered
  entity table fails closed. Nothing is skipped because a name exists.
- **C5 — authored plans stay pure.** Immutable, database-I/O-free, no conditional
  or raw SQL. All lifecycle awareness lives in the runtime.

### Behaviour matrix

Table state is evaluated at the node's turn in the topological order.

| Lifecycle | Backend | Table | Materializer (C1) | Column state | Outcome |
|---|---|---|---|---|---|
| Fresh | `sql-blob` | absent | creates keys + `_data` | missing | **applied** |
| Existing | `sql-blob` | present | no action | missing | **applied** |
| Fresh | `sql-column` | absent | creates keys + field columns | present, spec-compatible | **already_satisfied** |
| Existing | `sql-column` | present | no action | missing | **applied** |
| Either | Either | present | no action | present, spec-**incompatible** | **fail closed** |
| Either | Either | absent, not a registered entity table | no action | — | **fail closed** |

**Interrupted initialization.** Materialization, execution, and the ledger write
for one node share that node's coordinator transaction, so an interruption leaves
the node wholly applied or wholly absent. A re-run resumes at the same node.

**Replay.** Unchanged. `hasRun()` short-circuits an applied node and
`guardV2Replay()` still compares stored against computed checksum, throwing in
production-like environments and warning in development-like ones.

### Ledger interaction

- `checksum` is unchanged in every outcome. It hashes authored intent, which does
  not vary by lifecycle.
- `diff_hash` is unchanged: the hash of the **full** compiled plan, recorded even
  when C3 skipped steps. Verification keeps comparing the same value and stays
  sound.
- A nullable `apply_mode` column (`applied` | `already_satisfied`, NULL for rows
  written before this change) is added through the established
  `LedgerSchema/` path, mirroring `V2_0001_add_checksum_columns`. This is an audit
  field, not a second identifier, so §15 Q1's refusal of a parallel identity column
  is not reopened.

### Disclosed conflict with D3

D3 required a fresh site and an upgraded site to produce byte-identical ledger
rows. Under this contract that holds for `sql-blob`, the default backend and the
consumer's case: both lifecycles execute, so `checksum`, `diff_hash`, and
`apply_mode` all match.

It does **not** hold for `sql-column`, and cannot. There the materializer creates
the column during a fresh install, so the node genuinely has no work to do; the
only ways to force an identical row would be to execute a colliding statement or
to record `applied` for work that never happened. Both silently weaken the ledger.

Smallest coherent alternative, and the one adopted: keep `checksum` and
`diff_hash` identical across lifecycles, and let `apply_mode` differ, because the
difference is real and an operator needs to see it. D3 is therefore amended to
cover the hash pair rather than the whole row.

## Review corrections

An adversarial review of the first candidate confirmed 25 findings. Four root
causes were real defects in that candidate and are fixed here; each was
reproduced before and after.

1. **Comparison used the wrong vocabulary (high).** Exactness was decided by
   string-matching the v2 compiler's rendered type against the canonical
   materializer's Doctrine DDL. `TEXT` never equals `CLOB`, and SQLite reports a
   nullable column's default as the literal string `NULL`, so *every*
   materializer-created column was reported incompatible and a fresh
   `sql-column` install aborted the whole run — making the ratified matrix's
   `already_satisfied` row unreachable in production. Types are now compared by
   **SQLite storage affinity**, a literal `NULL` default normalizes to "no
   default", and the default **value** is compared rather than only its presence.
2. **Rename destinations were materialized (high).** `PlanTargets` returned both
   ends of a `RenameTable`, so C1 pre-created the table the rename was about to
   produce and `ALTER TABLE ... RENAME TO` collided — breaking renames that
   worked before this change. The list is now explicitly *prerequisite* tables:
   a rename requires only its source.
3. **One pre-execution snapshot (high).** Classifying every operation up front
   judged each against a database its predecessors had not yet changed. An
   operation made necessary by an earlier one in the same composite was dropped
   as already satisfied while the full `diff_hash` was still recorded, so
   verification would report a match for a database missing part of the plan.
   Operations are now classified **and executed one at a time, in authored
   order**.
4. **Index identity was too loose (medium).** Any live index covering the same
   columns satisfied the op, including SQLite auto-indexes and partial indexes,
   while a differently-named index silently suppressed the authored one. Identity
   is now the name the compiler will actually emit, via
   `AddIndexTranslator::resolveName()`, with partiality, uniqueness and column
   order all compared.

Further accepted findings, all fixed:

- `migrate --dry-run` advertised SQL for operations the runtime would classify
  satisfied. It now reports only outstanding work. A consequence worth stating:
  an *incompatible* column is now refused during dry-run as well as during apply,
  which surfaces the divergence before anything is attempted.
- The lifecycle tests stubbed the materializer on one side and the compiler on the
  other, so neither half was ever tested against the real other half — which is
  exactly why the vocabulary defect survived. An end-to-end `sql-column` case now
  runs through the real `EntitySchemaTableMaterializer`.
- A partial or descending index falsely satisfied a full ascending one. Index
  comparison now reads `PRAGMA index_xinfo` for sort direction and refuses both.
- The `apply_mode` ledger upgrade path and the `V2_0002` authoring record were
  untested; removing the upgrade left both suites green while an upgrading site
  would have failed on the first `record()`. Both are now pinned, extending the
  existing WP09 precedent test.
- The "compile in full before touching the database" ordering was unasserted. A
  policy-refused plan now proves the materializer is never invoked.

## Independent review corrections (round 2)

An independent review of `91e49def5` requested changes with five findings and a
failing CI coverage gate. All five were reproduced before being fixed.

- **R1 — default comparison (P1).** Expected defaults were unquoted PHP strings
  while live defaults are SQL literal expressions. The mismatch refused an
  authored empty string, an authored `"NULL"`, and any value carrying
  surrounding whitespace or apostrophes — values this compiler itself emits —
  and, worse, *accepted* a column with **no default** when the authored default
  was `''` or `"NULL"`. Both sides are now rendered through the compiler's own
  `SqliteIdentifier::literal()`; only the live side normalizes an unquoted `NULL`
  to "absent", which is what Doctrine emits for a nullable column.
- **R2 — boolean (P1).** The affinity rule refused the framework's own
  `sql-column` output for a boolean field: the materializer emits `BOOLEAN`
  (NUMERIC affinity) where the v2 compiler renders `INTEGER`. Reconciled by an
  explicit per-logical-type allowlist, **not** by equating INTEGER and NUMERIC
  generally — a `DECIMAL` column still fails an authored `int`. All four
  supported logical types are now proven end to end through the real materializer.
- **R3 — rename destination (P1).** Prerequisites were still aggregated across
  the whole plan, so a later operation naming the rename's destination
  re-introduced it and the materializer pre-created the table the rename was
  about to produce. Prerequisites now walk operations in order and exclude what
  earlier operations produce.
- **R4 — index collation (P2).** `PRAGMA index_xinfo` exposes `coll`, which was
  ignored, so a `NOCASE` index satisfied an authored index on a `BINARY` column
  despite different uniqueness semantics. Effective collation is now compared
  against the column's own, read from `sqlite_master` and defaulting to SQLite's
  `BINARY`. A column declaring `NOCASE` correctly expects a `NOCASE` index.
- **R5 — dry-run (P2).** Filtering against the initial snapshot silently omitted
  work that apply performs, and could refuse a column a preceding operation
  replaces. Operations whose target an earlier operation touches are now
  **preserved** rather than filtered, and the node is reported `state_dependent`
  in both text and JSON output.

**Coverage.** The `ci/coverage` changed-line gate failed at 129/325 (40.82%)
against an 80% requirement. Two whole blocks proved to be attribution rather than
absent tests — `DryRunPlanner` and `V2_0002` were exercised but named in no
`#[CoversClass]`. Those attributes were corrected and real tests added for the
untested branches. Measured with the repository's own command on PHP 8.5.9 with
pcov: **307/325 (94.46%)**. Neither the threshold nor the baseline was changed.

**Known residue.** `DbInitHandler::entityTypeSnapshot()`'s success path needs a
real booted project and is not reachable from unit tests; its fail-soft path is
covered.

## Contract corrections (round 3)

Review directed that the underlying contracts be fixed rather than the reported
inputs, with an explicit keep / remove / replace map so no helper accumulates
beside faulty logic. Paths that disappeared:

| Replaced path | Replacement |
|---|---|
| `OpPreconditionResolver::columnCollation()` — regex with a `BINARY` fallback | `SqliteTableDefinition::collationOf(): ?string`, a quote/string/comment/nesting-aware scan returning confirmed collation or **unknown** |
| `DryRunPlanner`'s per-migration `$touched` loop | Uncertainty accumulated across the whole ordered graph |
| `DryRunPlanner::isStateDependent()` + `compileStepsFor()` as two traversals | A single `analyse()` producing steps and the flag together |
| `PlanTargets::tables()` / `tablesForOp()` serving two questions | `prerequisiteTables()` and `affectedTables()` as separate concepts |

- **Collation is authoritative or silent.** Confirmed collation, an authoritative
  `BINARY` where no clause is declared, or unknown. Unknown fails closed; it is
  never collapsed to `BINARY`, because that would silently accept an index with
  different uniqueness and ordering semantics. An index entry that is an
  expression or rowid rather than a plain column is refused for the same reason.
- **Uncertainty is graph-scope.** A pending legacy migration is opaque and makes
  every later node uncertain; a pending v2 migration marks the tables it
  *affects*; an already-applied migration adds nothing, because its effects are
  already in the database the snapshot describes. Uncertainty stays per-table, so
  unrelated migrations do not infect one another.
- **Prerequisite and affected are different questions.** A rename *requires* its
  source but *changes* both source and destination. Materialization uses
  prerequisites; uncertainty uses affected tables. Conflating them was the cause
  of the earlier rename defect.
- **Preview and apply share one model** — operation targets, ordering, and the
  precondition rule — diverging only where preview cannot execute: unknown state
  resolves to outstanding and is never refused. That divergence is documented
  rather than incidental.

Not changed, and no evidence was found that they need to be: the migration
engine, legacy migration support, and the deployer safety checks.

Two defects were found by the new boundary tests rather than by the reported
examples: a `COLLATE` clause with an unreadable argument fell through to the
`BINARY` default, and a quoted column named like a constraint keyword
(`"check"`) was skipped as a table constraint.

## Collation model correction (round 4)

Independent review confirmed the graph-wide dry-run rewrite and all 17 prior
counterexamples, and found one remaining P1: `collateToken()` could return an
authoritative `BINARY` where SQLite actually applies `NOCASE`. Three valid column
definitions were reproduced, and a fourth was found by the new tests:

| Definition | Old result | SQLite |
|---|---|---|
| `name TEXT COLLATE/* c */NOCASE` | `BINARY` | `NOCASE` |
| `name TEXT COLLATE BINARY COLLATE NOCASE` | `BINARY` | `NOCASE` |
| `name acollate BINARY COLLATE NOCASE` | `BINARY` | `NOCASE` |
| `name mycollate COLLATE NOCASE` (found here) | `COLLATE` | `NOCASE` |

All four are one modelling error: the scanner flattened characters, discarding
comments in a way that concatenated the tokens either side of them and matching
`COLLATE` by position rather than as a token, so it could match inside a longer
identifier.

**Replaced, with the old paths deleted:** `significantOffsets()`,
`splitTopLevel()`, `skipQuoted()`, `leadingIdentifier()`, `collateToken()` and
the character-offset `columnDefinitionList()`. In their place a tokenizer
preserves identifier, quoted-identifier, string, comment-separator and
parenthesis-nesting boundaries; `COLLATE` is recognised only as a standalone
token at the definition's own nesting level; the complete definition is examined
and the **last** clause wins; a clause whose argument is not an identifier is
unknown. No parallel fallback exists — no other file in `foundation` interprets
collation at all.

**Tests are differential, with SQLite as the oracle.** Each case builds the
table, creates the authored index through the real compiler, reads the effective
collation from `PRAGMA index_xinfo`, and requires every non-null parser result to
agree. Resolver-level tests then prove the concrete harm is gone: a `BINARY`
unique index is refused for a `NOCASE` column, an inherited index is accepted,
and the refused index is demonstrated to admit both `a` and `A`. All previous
regressions are retained unweakened; no unsupported input was collapsed to
`BINARY` to make a test pass.

### Differential fuzz against SQLite

The tokenizer rewrite was then fuzzed against the database rather than against
its own model: 26,892 generated column definitions across seven adversarial
lenses, each compared to SQLite through the probe described above.

That found **54 further distinct definitions** where the parser returned a
confident collation disagreeing with SQLite, all from one cause the reported
counterexamples did not reach: the identifier character class was ASCII-only,
while SQLite's own rule treats **every byte at or above 0x80** as an identifier
character. A non-ASCII byte therefore ended an identifier early, which could

- fabricate a standalone `COLLATE` token where SQLite sees a multi-word type
  name (`x TEXTéCOLLATE NOCASE` parsed `NOCASE`; SQLite uses `BINARY`), or
- split a column name so a lookup matched the wrong definition
  (`café TEXT COLLATE NOCASE, caf TEXT` answered for the wrong column).

Both directions failed **open**, producing a confident wrong answer that would
accept a mismatched index. The identifier class now matches SQLite's, and all 54
definitions are retained verbatim as a permanent regression rather than sampled.

### Closing the other side of the differential contract

The differential property above is one-sided: a non-null answer must agree with
SQLite, and unknown is always permitted because it fails closed. That is the
safety property, and it is the right one — but it is satisfied completely by a
reader that returns unknown for everything and refuses every migration. Nothing
measured how much valid DDL the reader could actually resolve.

`SqliteCollationOracleCorpusTest` closes that side. Every row names the collation
SQLite really uses and asserts **both** that the expectation is true of the
database and that the parser produces exactly it, so no row can pass by reporting
unknown. The corpus is wide on purpose — the fabricated-clause family
(`a COL"z"LATE NOCASE`, where quoted-word removal invents a clause SQLite never
sees), table-level `UNIQUE` / `PRIMARY KEY` decoys, generated columns, foreign-key
tails, `STRICT, WITHOUT ROWID` suffixes, multi-word type names, quoted identifiers
containing commas, parens and comment openers, blob and paren-bearing string
defaults, non-ASCII identifiers, and leading comments on first and later columns.
Unknown is proved separately, only on input that is not valid stored DDL.

Running it found **one remaining divergence**, and it was an over-refusal rather
than a false accept: a collation name written as a **string literal**
(`COLLATE 'NOCASE'`) was reported unknown. SQLite accepts a string wherever an
identifier is expected and resolves it to `NOCASE` — verified live, in both
`PRAGMA index_xinfo` and duplicate-insert behaviour — so a correct index on a
legitimately case-insensitive column was being refused. The argument test now
admits the same set of spellings SQLite does. This narrows unknown toward valid
DDL only; it does not widen any answer, and no assertion was weakened to reach
it.
### Byte-order-mark lexer exception (round 5)

Review found one narrower P2 after the identifier-class fix: SQLite's lexer skips
a UTF-8 byte-order mark (`EF BB BF`) **where a token would start**, treating it as
whitespace, while the widened identifier class consumed it as an identifier
prefix. For `name TEXT <BOM>COLLATE NOCASE`, SQLite records the declared type as
`TEXT` and collates the column `NOCASE`; the parser answered `BINARY` and would
have accepted a `BINARY` unique index — a wrong accept.

The correction is bounded to token-start handling, not a global strip, and the
distinction is load-bearing in both directions:

| Definition | SQLite | Why |
|---|---|---|
| `name TEXT <BOM>COLLATE NOCASE` | `NOCASE` | BOM at a token start is whitespace, so the clause is real |
| `name TEXT COLLATE<BOM>NOCASE` | `BINARY` | inside a token the bytes are identifier characters, so there is no clause |
| `na<BOM>me TEXT COLLATE NOCASE, na TEXT` | `BINARY` for `na` | the BOM keeps the two column names distinct |

A global strip would get the second and third wrong. The check therefore sits at
the top of the tokenizer loop, which is a token-start position by construction;
the identifier match below still consumes the same bytes when they occur inside a
token. Both negative controls are retained as tests alongside the positive cases.

## Primary-key exactness repair (round 6)

Review found a false **accept** in `OpPreconditionResolver::resolveAddColumn()`:
it compares declared-type affinity, nullability and default, and never reads
`PRAGMA table_info.pk`. A live primary-key column therefore satisfied an
ordinary authored `AddColumn`.

### Bounded design, recorded before the source change

The rule this adds is not a new contract; it is the C3 rule applied to a
property the comparison was not reading. C3 requires the live column to
**exactly satisfy the declared operation**, and the criterion is the authored
`ColumnSpec` and what the compiler renders from it — not what SQLite's
`ADD COLUMN` grammar happens to permit. `AddColumnTranslator` emits exactly:

```
ALTER TABLE "<table>" ADD COLUMN "<col>" <type-sql> [NOT NULL] [DEFAULT <literal>]
```

Type, nullability and default are the whole of the authored vocabulary. A
primary key is not in it, so a live primary-key column is not the column this
operation declares; reporting it satisfied is a C3 violation, and C4 requires an
auditable refusal rather than a skip on the strength of a name. The repair reads
`pk` and refuses; it widens no acceptance.

SQLite corroborates the reading independently — `ALTER TABLE t ADD COLUMN v
INTEGER PRIMARY KEY` is refused outright with "Cannot add a PRIMARY KEY column",
so the shape is also unreachable through the emitted statement. That is
supporting evidence, not the criterion.

Two SQLite details make the omission worse than a missing field:

- An `INTEGER PRIMARY KEY` in a rowid table reports `notnull = 0` while being
  incapable of holding NULL — SQLite substitutes a rowid. The existing
  nullability comparison is not merely silent here, it reads a value that
  misdescribes the column, so no other check can catch the case.
- A composite primary key reports `pk` as a **1-based position** rather than a
  flag. Membership is `pk !== 0`, which is true at every position; the trap is
  testing `pk === 1`, which would silently miss a column in any later position.
  The position is carried into the refusal because an operator needs it.

The guard is placed **before** the type, nullability and default comparisons.
Ordering only decides which refusal an operator sees, and primary-key membership
is both the most structural divergence and the reason the nullability reading
cannot be trusted, so it is the honest message to surface first.

### Test-first plan

1. Unit, coverage-bearing, at the resolver: integer rowid primary key; composite
   primary key at first **and** non-first position; `WITHOUT ROWID`; a
   `PRIMARY KEY` declared as a table-level constraint rather than inline; and an
   ordinary non-primary-key column of the same type as the positive control that
   must stay `already_satisfied`.
2. Integration, through the real `Migrator`, `MigrationRepository`,
   `V2PlanExecutor`, compiler, resolver, ledger and per-node transaction, with an
   **earlier operation in the same plan that succeeds before the refusal**: no
   successful ledger row, the earlier operation's column rolled back, and
   pre-existing data intact. The table pre-exists, so C1 materialization is not
   part of this proof and the file's anonymous test materializer never runs.

### Adjacent false accepts — disclosed, not repaired here

`pk = 0` does **not** establish universal equivalence, and this repair does not
claim it does. Measured on the same head, against the same ordinary authored
`AddColumn`:

| Live column | `table_info` | Verdict before **and** after this repair |
|---|---|---|
| `value INTEGER UNIQUE` (and table-level `UNIQUE (value)`) | `pk = 0` | **already_satisfied** — false accept |
| `value INTEGER CHECK (value > 10)` | `pk = 0` | **already_satisfied** — false accept |
| `value INTEGER REFERENCES parent(id)` | `pk = 0` | **already_satisfied** — false accept |
| `value TEXT COLLATE NOCASE` vs authored `text` | `pk = 0` | **already_satisfied** — false accept |
| `value INTEGER GENERATED ALWAYS AS (…)` | absent from `table_info` | `NeedsApply`, then a real SQL error — **fails closed**, though opaquely |

Every row above is already a mismatch under C3 as written. None of these
constraints is expressible in `ColumnSpec`, so none of them is part of the
column the authored operation declares, and accepting them contradicts
exactness exactly as the primary-key case did. What is undecided is **the scope
and design of the remediation**, not whether they are mismatches:

- **`UNIQUE` is the exact twin of this defect** and needs no design work.
  Membership is readable from `PRAGMA index_list` (`origin` = `u`) with no
  parsing, the same shape of pragma reading as `pk`. It is the obvious next
  bounded repair; it is out of this candidate's stated scope, not out of reach.
- **`REFERENCES` is pragma-readable too**, from `PRAGMA foreign_key_list`, but
  the remediation question is wider: a foreign key is a table-level object that
  may name several columns, so the refusal has to decide what it reports and
  whether it belongs in the column comparison at all.
- **`CHECK` and `COLLATE` are the costly ones.** Neither has a pragma. Proving
  `CHECK` absence requires reading stored DDL, and `COLLATE` would extend
  `SqliteTableDefinition` — already used for index collation — into the column
  comparison. That is a real design decision about parser surface and about what
  unknown-means-refuse would do to the ratified `already_satisfied` matrix.

Until those land, C3's "exactly satisfies" is **broader in the documentation
than the code enforces**. This record states that rather than implying the
comparison is complete; the merge recommendation carries it forward.

## Column equivalence completed (round 7)

Round 6 repaired one false accept and disclosed four more. Independent review
then measured them: a 33-case column corpus reported 21 failures, and a 60-case
CHECK corpus — whose oracle is SQLite itself, each negative control proven by an
insert SQLite rejects — reported 43. Round 7 replaces the partial comparison
with one predicate that decides the whole of C3 for `AddColumn`, under the
existing C3/C4 contract. No authoring contract changes: `ColumnSpec` is
untouched, the compiler stays pure and database-free, checksum and `diff_hash`
still hash authored intent, nodes still apply sequentially inside their own
transaction, and `AddIndex` composition is untouched.

### Why one predicate rather than four more pragma reads

C3 asks whether the live column **is the column the operation declares**.
`AddColumnTranslator` emits exactly

```
ALTER TABLE "<t>" ADD COLUMN "<c>" <type-sql> [NOT NULL] [DEFAULT <literal>]
```

so the authored vocabulary is type, nullability and default, and nothing else.
The question is therefore closed: *does the live column carry any property
outside that vocabulary?* SQLite answers it, because `column-constraint` and
`table-constraint` are **finite productions**. Enumerated from the CREATE TABLE
grammar, a column can carry only:

| Property | Decided by | Refuses when |
|---|---|---|
| `PRIMARY KEY` | `PRAGMA table_xinfo.pk` | non-zero (a 1-based position) |
| generated / hidden | `PRAGMA table_xinfo.hidden` | non-zero |
| `UNIQUE` (inline or table-level) | `PRAGMA index_list.origin` ∈ {`u`,`pk`} + `index_info` | the column is a member |
| `REFERENCES` (inline or `FOREIGN KEY`) | `PRAGMA foreign_key_list.from` | the column is a **source** |
| type / nullability / default | `PRAGMA table_xinfo` | compared, as before |
| `COLLATE` | stored DDL | effective collation ≠ `BINARY` |
| `NOT NULL` conflict policy | stored DDL | policy ≠ `ABORT` |
| `CHECK` dependence | stored DDL | the expression may read this column |

Because the production list is closed, an empty result is a **proof of
equivalence**, not an absence of findings. That is the property four more
independent pragma reads would not have given.

Catalogue is authority wherever a catalogue exists. Only the last three rows
have no pragma, and they reuse the token-preserving `SqliteTableDefinition`
already trusted for index collation. No new dependency, no runtime SQL probe or
mutation, no regex fallback, no table-equality requirement.

Three refusals are **narrower** than a blanket rule on purpose, because the
corpora contain positive controls that must still be *accepted*, not merely fail
safely:

- an index is a separate schema object, authorable as `AddIndex`, so an
  independently created index (`origin = c`) — including a `UNIQUE` one, which
  is what `EntitySchemaSync` emits for `uuid` — never refuses the column;
- a foreign key refuses only where the column is the **source** (`from`); being
  the referenced target is a property of the *other* table;
- explicit `ON CONFLICT ABORT` and explicit `COLLATE BINARY` are compared
  semantically and accepted, because they restate the default the compiler's own
  output has.

`ABORT` is the only equivalent conflict policy, and "it throws on a NULL insert"
is **not** the comparison — three of the five policies do. Measured on SQLite
3.45.1 against a bare `NOT NULL`:

| Policy | Single NULL insert | Rows left by `VALUES (1), (NULL)` | Enclosing transaction |
|---|---|---|---|
| bare / `ABORT` | throws | 0 | intact |
| `FAIL` | throws | **1** — keeps what the failed statement wrote | intact |
| `ROLLBACK` | throws | 0 | **rolled back, earlier work discarded** |
| `IGNORE` | accepted | 1 | intact |
| `REPLACE` | accepted | 2 — substitutes the default | intact |

`ROLLBACK` is the sharpest of these for this runtime: the enclosing transaction
it discards is the migration's own per-node transaction.

### The CHECK dependency proof, and its bounded grammar

A CHECK constrains a column whenever its expression can *read* that column,
regardless of where the constraint is written. Syntactic placement proves
nothing in either direction, and SQLite settles both halves of that:

```sql
CREATE TABLE sample(value INTEGER, other INTEGER CHECK(value > 0)); -- constrains value
CREATE TABLE sample(value INTEGER, CHECK('value' != 'other'));      -- constrains nothing
CREATE TABLE sample(value INTEGER, CHECK(sample.'value' > 0));      -- constrains value
CREATE TABLE sample(value INTEGER,
                    derived INTEGER GENERATED ALWAYS AS (value + 1),
                    CHECK(derived > 0));                            -- constrains value
```

So the scan is whole-table, and the question asked of each CHECK body is only:
**can its value depend on the target column?** That is answered by
over-approximating the set of column names the expression may read. In SQLite an
expression names a column only as `[[schema.]table.]column`, and each part is
one of five identifier spellings, so the reader admits as a candidate name:

- every bare identifier token;
- every delimited identifier token — `"x"`, `[x]`, `` `x` ``;
- every single-quoted token in an **identifier position**, meaning one adjacent
  to a `.`. That is the only context in which SQLite reads a string literal as
  an identifier, which is why `sample.'value'` is a column reference and a
  standalone `'value'` is not.

Everything else — numbers, operators, blob literals, a standalone string — is a
value, never a column. The set is then closed transitively through the table's
generated columns, so `CHECK(derived > 0)` over `derived AS (value + 1)` reaches
`value`, and through arbitrarily many links.

**The approximation is deliberately one-sided.** It may name more columns than
the expression really reads — a function name, the `e10` of a numeric literal —
which costs a false refusal. It cannot name fewer, because every column-reference
syntax SQLite offers is in the admitted set. False refusal is C4-safe; false
acceptance is the defect being repaired. This is why the reader does not need to
parse SQLite's expression grammar, and does not claim to: it classifies tokens
against a closed list of reference spellings, which is a strictly smaller and
provable obligation.

**Unknown is explicit, and refuses.** The stored schema text absent or
unreadable; the column list unbalanced; the statement not an ordinary
`CREATE TABLE` (a `CREATE VIRTUAL TABLE` names module arguments, not columns, and
its ordinary columns report `hidden = 0`); the target column not among the
definitions; a `COLLATE`, `ON CONFLICT` or `CHECK` clause whose argument cannot
be read. Each refuses under the existing `[S1-DB110]`, saying which.

**Unknown does not disable normal schemas.** Measured, not asserted:

- The canonical `EntitySchemaTableMaterializer` emits, on both backends, columns
  with no `COLLATE`, no `CHECK`, no conflict clause, no `UNIQUE` constraint and
  no foreign key — every index it creates has `origin = c`, which is exactly why
  an independently created unique index must not refuse the column.
- The framework ships **many** CHECK-bearing tables — `configuration_activation`,
  `configuration_authority`, `entity_mutation_authority`, `cache_generation`,
  `oidc_signing_key_lifecycle` and `waaseyaa_schema_authority` among them — so
  "CHECK is rare here" is not the argument and was not checked into this record
  as one. The argument is narrower and verifiable: **no shipped framework
  migration authors an `AddColumn` against any of them.** Every shipped
  migration that creates those tables is a v1 raw-SQL migration, and the only
  `MigrationInterfaceV2` implementations in the framework are the two
  `LedgerSchema/` records, which are documentary — `MigrationRepository::ensureCurrentSchema()`
  applies the ledger's own columns idempotently, because the row recording the
  apply needs the column to exist first. Their target, `waaseyaa_migrations`,
  carries no `CHECK`, no `COLLATE`, no `UNIQUE` *constraint* (its unique index is
  `origin = c`) and no foreign key.
- A CHECK-bearing table is still usable: the scan refuses only the columns a
  CHECK can read. `waaseyaa_schema_authority`'s
  `authority_id INTEGER PRIMARY KEY CHECK (authority_id = 1)` reaches its own
  primary-key column and no other, so every other column of that table stays
  acceptable.

Ordinary columns beside unrelated constraints are a positive control in both
corpora, not an assumption.

### Known limitations, stated rather than hidden

- The reader does not evaluate expressions: `CHECK(value IS NOT NULL OR 1)`
  refuses although it constrains nothing.
- Over-approximation refuses a CHECK in which a token that is not a column
  reference happens to spell the target column's name.
- Collation is required to be `BINARY` for every affinity, including ones where
  it is inert. It is unauthorable either way, and refusing uniformly avoids a
  second, weaker rule.
- The predicate is SQLite-only, matching the rest of this record.
