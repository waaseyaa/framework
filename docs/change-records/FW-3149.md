# Framework deployer schema authority reconciliation

Status: implementation candidate for Framework #3149, a bounded child of
#2548.

## Problem

`SqliteArtifactPreparer::prepare()` copies the artifact database into the
candidate. `waaseyaa_schema_authority` and `waaseyaa_migrations` are both
catalogued `RuntimeTablePolicy::Artifact`, so the candidate carries the
artifact's manifest and ledger verbatim. Runtime preservation then clones the
schemas of serving-only runtime-preserved tables into the candidate
(`cloneSchema()`) and merges or copies their rows, changing the candidate's
actual logical schema without ever re-recording the aggregate
`schema_fingerprint` that describes it. The next code-only deployment's
`MigrationRepository::assertSchemaAuthorityPreState()` then refused with
`[S1-DB109]` against a candidate that was not actually wrong — reproduced
twice on Sheguiandah staging (#2548, 2026-09-22 and 2026-09-23 comments): the
recorded fingerprint described the artifact alone; the live computed
fingerprint, which matched an independent preparer replay, differed only by
nine catalogue runtime tables and their twenty-one indexes.

## Design choice: deployer-local fingerprint computation (option b)

The issue posed two options: depend on
`Waaseyaa\Foundation\Migration\LogicalSchemaFingerprint` and
`MigrationRepository`'s ledger fingerprint directly, or duplicate the
algorithm locally with a parity test. This change takes the duplication path.

`packages/deployer/composer.json` requires only `ext-pdo`, `php`, and
`deployer/deployer`. Consumer applications install the deployer recipe into
an isolated deploy-tools vendor boundary, separate from the application's own
vendor tree (see #2303's runtime-state preservation, #3127's additive `user`
transition, and the standalone-install shape of `packages/deployer/composer.json`
itself, which has never carried a `waaseyaa/*` runtime dependency).
`waaseyaa/foundation` pulls in Doctrine DBAL plus `waaseyaa/cache`,
`waaseyaa/queue`, `waaseyaa/entity`, `waaseyaa/error-handler`,
`waaseyaa/routing`, `waaseyaa/access`, `waaseyaa/ai-tools`, and more (see
`packages/foundation/composer.json`'s own path-repository list). Adding a
runtime `require` edge from deployer to foundation would pull that entire
graph into a tool meant to run standalone during a deployment, breaking the
isolated install this package has always guaranteed. The two classes are also
not a drop-in call regardless of dependency policy:
`SqliteArtifactPreparer` opens its databases with raw `PDO`, never a DBAL
`Connection`.

The layer edge itself is legal either way — deployer is layer 6, foundation
is layer 0, and a higher-layer package may depend on a lower one
(`bin/check-package-layers`) — so the choice here is about the isolated
deploy-tools install shape, not about layering.

`Waaseyaa\Deployer\RuntimeState\SchemaAuthorityFingerprint` therefore
replicates both algorithms byte-for-byte using raw `PDO`:
`LogicalSchemaFingerprint::capture()`'s `sqlite_schema` row shape, ordering,
and SQL-text normalization, and `MigrationRepository`'s ledger fingerprint
(including its "absent ledger" domain-separated fallback), both hashed
through a private canonical-JSON encoder that mirrors
`Waaseyaa\Foundation\Schema\Diff\CanonicalJson`'s rules (UTF-8 bytes,
recursive `ksort(SORT_STRING)`, preserved list order, no
`JSON_PRESERVE_ZERO_FRACTION`, `JSON_THROW_ON_ERROR`).

`waaseyaa/foundation` is a `require-dev`-only edge on
`packages/deployer/composer.json` (with the matching path repository CP007
requires), used exclusively by
`SchemaAuthorityFingerprintParityTest`, which pins the deployer-local
computation byte-identical to foundation's own classes across fixtures: an
empty database; tables, indexes, triggers, and an `AUTOINCREMENT` table
(present for its own sake, not for `sqlite_sequence`'s `sql` — that table's
`sql` is not NULL, and it is excluded by the `sqlite_%` name filter regardless;
the only NULL-`sql` rows `sqlite_master` produces in practice, SQLite's
automatic `sqlite_autoindex_*` indexes, are excluded the same way, so there is
no reachable non-`sqlite_%`-named NULL-`sql` object to exercise that branch
against — see the fixture's own comment); mixed line endings in raw DDL text;
non-ASCII/Unicode identifiers; `WITHOUT ROWID`; a partial index; a quoted
mixed-case identifier containing `/`; a view; CR/CRLF embedded inside a
trigger body; FTS5 (several non-`sqlite_%` shadow tables); an absent ledger; a
populated ledger with a null-checksum row; an out-of-order ledger with
string/integer/float/empty-string column values; and the real output of a
`SqliteArtifactPreparer::prepare()` run. `require-dev` never reaches a
consumer's install regardless of `--no-dev`, because `require-dev` is only
ever installed for the *root* package of a Composer install, and a consumer's
isolated deploy-tools boundary always installs `waaseyaa/deployer` as a
dependency, never as the root package.

## Contract

`captureArtifactSchemaAuthority()` runs on the read-only artifact connection
before the candidate file exists at all: it reads the artifact's manifest,
checks the precondition below, and — only on success — captures the
`schema_fingerprint`, `ledger_fingerprint`, `source_catalog_fingerprint`, and
full `sqlite_schema` object set as a snapshot. `reconcileSchemaAuthority()`
then runs inside `prepare()`'s existing candidate transaction, after runtime
preservation and account-reference validation, before commit, and receives
that snapshot rather than a live artifact connection — binding reconciliation
to the exact values already validated, not to a second, later read that could
in principle observe something different.

1. **Precondition.** When the artifact's `waaseyaa_schema_authority` carries
   a fingerprinted manifest (`schema_fingerprint` and `ledger_fingerprint`
   both non-null), its recorded values must equal its own computed schema and
   ledger fingerprints. A stale artifact manifest throws before the candidate
   file is even created. A `waaseyaa_schema_authority` table present but
   missing a required fingerprint column (a pre-#2547 installation) throws
   `[S1-DB105]`, the same refusal
   `MigrationRepository::schemaAuthorityManifest()` gives for the identical
   case — distinct from a genuinely absent table, which is Rule 5.
1a. **Bind.** Before doing anything else, `reconcileSchemaAuthority()`
   requires the candidate's own (copied) `waaseyaa_schema_authority` row to
   still equal exactly the values captured in step 1 — `schema_fingerprint`,
   `ledger_fingerprint`, `source_catalog_fingerprint`, **and `generation`**,
   all four columns, not only the three fingerprints. Runtime preservation
   clones schema objects from the serving database that match `name = ? OR
   tbl_name = ?` for the table being preserved
   (`SqliteArtifactPreparer::cloneSchema()`); a serving trigger genuinely `ON`
   a preserved table is cloned by that match and can fire during the row
   copy that follows, mutating any column of any table it names — including
   `waaseyaa_schema_authority` itself. This bind check is what catches that.
   A second review round found the first candidate's bind checked only the
   three fingerprint columns: a trigger that instead bumped `generation`
   was accepted, silently violating Required outcome 3 ("keep... `generation`
   unchanged"), and no test exercised a trigger mutating
   `source_catalog_fingerprint` either (mutation M16b). Both are now part of
   the bind and both have public-API `prepare()` regression tests; see
   "Hardening from a second review round" below.
2. **Bounded difference.** Every `sqlite_schema` object that differs between
   the artifact (as captured in step 1, before the copy) and the candidate
   (as of just before commit) must belong to a catalogue table whose policy
   is not `Artifact`. This is computed independently of the
   runtime-preservation loop's own table-name filtering: it diffs the two
   databases' raw schema object sets directly rather than trusting that the
   loop above never introduced an object outside a preserved table's own
   schema. It has to be independent, not merely defensive: `cloneSchema()`'s
   `name = ? OR tbl_name = ?` match clones a serving trigger merely *named*
   after the table being preserved, regardless of which table it is actually
   `ON`, so a trigger named `state` but declared `ON` an `Artifact`-policy or
   application-owned table reaches the candidate through the ordinary
   preservation loop, not around it — see "Hardening from an independent
   review" below. The #3127 `user` additive transition needs no special
   case, because `user`'s policy is already `IdentityMerge`, not `Artifact`.
3. **Re-record.** `UPDATE waaseyaa_schema_authority SET schema_fingerprint =
   <computed> WHERE authority_id = 1 AND schema_fingerprint = <artifact
   recorded value>`, requiring exactly one affected row. A zero-row result
   (the manifest changed concurrently) throws. Given the 1a bind check
   immediately above it in the same synchronous, single-writer `prepare()`
   call, this specific zero-row outcome has no realistic trigger left to
   reach it — 1a already requires the identical equality moments earlier —
   but it is kept as its own explicit guard rather than assumed, and a
   focused test still drives it directly.
   `ledger_fingerprint`, `source_catalog_fingerprint`, and `generation` are
   left exactly as the artifact copy already carries them:
   `waaseyaa_migrations` is itself `RuntimeTablePolicy::Artifact` and
   untouched by this handoff, so the candidate's ledger is already
   byte-identical to the artifact's and needs no re-recording.
   `generation` counts governed schema-mutation transitions
   (`SchemaMutationCoordinator::execute()`), not artifact handoffs — an
   artifact handoff is not itself a governed transition — so it stays exactly
   what the artifact recorded.
4. **Verify before activation.** After commit, the candidate's recorded
   schema and ledger fingerprints are asserted equal to their freshly
   computed values, using the identical computation
   `MigrationRepository::assertSchemaAuthorityPreState()` and `migrate
   --verify` use, so refusal here and refusal there can never disagree. A
   mismatch throws, and the existing catch block deletes the candidate file.
   This step is load-bearing, not redundant with 1a or 2: a cloned trigger
   that mutates a *different* `Artifact`-policy table's rows (rather than
   `waaseyaa_schema_authority` itself) — for example inserting into
   `waaseyaa_migrations` — has no `sqlite_schema` footprint for step 2 to see
   and never touches the row step 1a reads, so this post-commit recomputation
   is the only guard that catches it (review probe c, below).
5. **No manifest.** An artifact whose `waaseyaa_schema_authority` is absent,
   or present with a null `schema_fingerprint` or `ledger_fingerprint`
   (fresh install or a #2452 adoption), is left completely untouched —
   matching `assertSchemaAuthorityPreState()`'s own no-manifest pass-through.
6. **Single definition.** Covered by the design choice above: one algorithm,
   two byte-for-byte implementations, pinned together by
   `SchemaAuthorityFingerprintParityTest`.

## Hardening from an independent review

An independent Opus review of the first candidate found that its own
Reflection-only tests for the bounded-difference guard and the re-record
guard's earlier "concurrently" wording rested on a false premise: that
`prepare()`'s runtime-preservation loop "never touches an `Artifact`-policy
table's schema" and that those scenarios therefore "cannot arise from
ordinary inputs through the public API." The reviewer disproved that with
three temporary probes driven entirely through `prepare()`, using
`cloneSchema()`'s `name = ? OR tbl_name = ?` match and the fact that a cloned
trigger executes during the row copy that follows:

- **(a)** A serving trigger *named* `state` (the table being preserved) but
  declared `ON content` (an application table, not a catalogue table at all)
  is cloned by the `name = ?` half of the match, independent of the table it
  is actually on. **On the parent commit this trigger was installed into the
  candidate silently** — there was no reconciliation step to notice it at
  all, only the pre-existing structural-schema check for the *named* table,
  which the trigger's own name satisfies trivially. This is real hardening
  against a real gap, not only a test-strength fix: the candidate this
  produces on the parent commit carries an application-owned trigger the
  serving host chose to plant, wired to whatever table it names, with no
  refusal. Rule 2's bounded-difference check, run against the pre-copy
  snapshot, now refuses it (`SqliteArtifactPreparerSchemaAuthorityTest::probe_a_…`).
- **(b)** A trigger genuinely `ON state` that `UPDATE`s
  `waaseyaa_schema_authority` during the row copy. Caught by the new Rule 1a
  bind check (`SqliteArtifactPreparerSchemaAuthorityTest::probe_b_…`).
- **(c)** A trigger genuinely `ON state` that inserts a rogue row into
  `waaseyaa_migrations` instead. Neither Rule 1a (a different table's row)
  nor Rule 2 (a data mutation, not a schema one) sees this; only Rule 4's
  post-commit recomputation does, which is what
  `SqliteArtifactPreparerSchemaAuthorityTest::probe_c_…` proves directly —
  before this test existed, disabling Rule 4 entirely would have passed the
  rest of the suite.

Probes (a) and (b) are now covered by public-API `prepare()` tests, kept
alongside (not replacing) the original Reflection-based tests for the two
guards they exercise, since those still isolate the `Artifact`-policy branch
and the re-record `UPDATE`'s own zero-row condition specifically, independent
of which cloning path reaches them.

Two further review items landed as code changes rather than only tests:
precondition capture and checking moved from inside the candidate transaction
to the read-only artifact connection, before the candidate file exists at all
(the 1a bind check above is what then re-establishes the link to the copied
candidate); and `schemaAuthorityManifest()` now throws `[S1-DB105]` for a
present-but-column-short manifest table instead of silently treating it the
same as no manifest at all, mirroring foundation's own refusal for the
identical case.

**Residual, recorded for #2548, not fixed here:** probe (c)'s pattern
generalizes beyond `waaseyaa_migrations`. A pre-existing, legitimately cloned
runtime trigger can mutate *any* `Artifact`-policy table's **data** (not
schema) during `copyRows()`, and — for tables other than
`waaseyaa_schema_authority` itself — that mutation persists in the activated
candidate with no refusal at all unless it happens to also corrupt the ledger
fingerprint `MigrationRepository::assertSchemaAuthorityPreState()` or
`migrate --verify` would independently recompute later. This change closes
the schema-authority-fingerprint gap those two probes exercise; it does not
audit or constrain what a legitimately preserved trigger's body is allowed to
write. That is #2548's broader interdependent-schema-design scope, not a
bounded child of it.

## Hardening from a second review round

A second review pass, after the round above landed, found the Rule 1a bind
itself was still incomplete, and named specific gaps to close:

1. **A real gap.** The bind compared `schema_fingerprint`, `ledger_fingerprint`,
   and `source_catalog_fingerprint`, but not `generation`. A probe trigger `ON
   state` doing `SET generation = generation + 5` was accepted — a silent
   violation of Required outcome 3, which requires `generation` to stay
   exactly what the artifact recorded. `generation` is now part of both the
   captured snapshot and the bind (see the updated Rule 1a above), with a
   public-API `prepare()` test
   (`probe_b_a_serving_trigger_on_the_preserved_table_that_mutates_generation_fails_closed`).
2. **Mutation M16b survived** (the bind ignored `source_catalog_fingerprint`):
   no test had a trigger changing it specifically. Added
   (`probe_b_a_serving_trigger_on_the_preserved_table_that_mutates_source_catalog_fingerprint_fails_closed`).
3. **Public-API coverage gap for mutation M4b** (the bounded-difference check
   allows an `Artifact`-policy table through): probe (a) used a trigger `ON
   content`, an application table not in the catalogue at all — the
   `$definition === null` branch, not the `$definition->policy === Artifact`
   branch. Added a variant naming an actual `Artifact`-policy catalogue table,
   `cache_discovery`
   (`probe_a_a_serving_trigger_named_after_a_preserved_table_but_on_an_artifact_policy_table_fails_closed`).
4. **The first round's mutation table mislabelled M2 and M4b.** Corrected
   below with the review's actual definitions and re-run, real outcomes.
5. **A test docblock overclaimed.**
   `a_manifest_changed_concurrently_between_precondition_and_re_record_fails_closed`
   (now renamed
   `a_manifest_that_no_longer_matches_the_captured_artifact_snapshot_fails_closed`)
   claimed to isolate the re-record `UPDATE`'s own `WHERE schema_fingerprint =
   ?` clause from the Rule 1a bind that now runs before it. That is not
   achievable: the bind and the `UPDATE`'s `WHERE` clause compare the exact
   same `schema_fingerprint` value from the exact same captured snapshot, with
   nothing mutating the candidate's row in between
   (`assertBoundedSchemaDifference()` is read-only), so whenever the bind's
   comparison passes, the `UPDATE`'s identical comparison cannot then fail.
   The docblock now says this directly instead of claiming isolation it does
   not have.
6. **Spec wording.** `docs/specs/sqlite-artifact-installation.md` said
   post-commit verification is "the only guard that catches a cloned trigger
   mutating a *different* artifact-policy table's data" — true only for the
   migration ledger specifically (the one other table its recomputation
   actually covers), not for an artifact-policy table in general (a trigger
   that instead wrote to, say, a cache table would have no footprint in
   either recomputed fingerprint and would go uncaught — the residual
   recorded above). Reworded.
