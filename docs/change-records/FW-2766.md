# FW-2766 — `oidc_client.client_id` registry-identity uniqueness

Status: candidate
Anchor mirror: waaseyaa/framework#2766
Parent candidate: `origin/main` (worktree tip `c0a8d5d4dab09d9bb527ec502f5c61b88b027564`)

## Intent

`OidcClient` documents `client_id` as its stable public identifier, but no
layer of the framework declared or materialized a uniqueness constraint for
it. The supported `sql-blob` repository accepted multiple rows sharing a
`client_id`; `OidcClientLookup::findByClientId()` silently selected `$ids[0]`
from any multi-match result on the exact pre-auth path the authorize, token
(`authorization_code` and `refresh_token` grants), and revoke controls all
share. Config seeding (`OidcClientSeeder`) used query-then-create and was
race-prone without a storage constraint. Replace query-order identity with a
storage-enforced unique registry identity that fails closed on collision,
never selects an arbitrary row.

## Decisions

1. **Canonical identity is non-empty `client_id`.** The empty string is the
   pre-column-add default (`ADD COLUMN client_id VARCHAR(255) NOT NULL
   DEFAULT ''` in the base migration) and carries no registry identity —
   `OidcClientLookup::findByClientId('')` returns `null` unconditionally, and
   blank rows are excluded from uniqueness scope (decision 2). Only a
   non-empty `client_id` value is a registry identity subject to uniqueness.
2. **Legacy blank-row exclusion via a partial unique index.** The physical
   constraint is `CREATE UNIQUE INDEX ... ON oidc_client (client_id) WHERE
   client_id <> ''` (SQLite partial index), not a plain unique index, so
   pre-existing or admin-left-blank rows never block materialization or
   spuriously collide with each other.
3. **Migration-only physical enforcement; no `#[StorageUniqueKey]`.**
   `OidcClient` declares no `#[StorageUniqueKey]` attribute. The constraint
   is owned entirely by the `2026_09_06_000009_oidc_client_id_unique_key`
   migration for the supported `sql-blob` layout on SQLite — the framework's
   declarative schema-sync mechanism (`schema:sync`) is not the enforcement
   path and cannot materialize this index. Recovery instructions in both
   `AmbiguousClientIdException` and `DuplicateClientIdException` name
   `bin/waaseyaa migrate` — the actual migration runner — never
   `schema:sync`.
4. **Duplicate upgrade refusal without guessed merge/delete.** If historical
   duplicate non-blank `client_id` values already exist when the migration
   runs, it throws `DuplicateClientIdException` (reporting the exact
   duplicated values), creates no index, and touches no row. Reconciling
   (rename, merge, or remove) the conflicting client definitions is an
   explicit operator decision; the migration never guesses which duplicate
   row is "correct."
5. **Fail-closed multi-match lookup, shared across every pre-auth control.**
   `OidcClientLookup::findByClientId()` throws `AmbiguousClientIdException`
   on any multi-row match rather than selecting `$ids[0]` — this is
   defense-in-depth for a database that has not yet run the migration (or a
   backend that cannot enforce the constraint). Because `AuthorizeController`,
   `TokenController` (both grants), and `RevocationController` all resolve
   `client_id` through the same shared `OidcClientLookup` instance, this
   fail-closed behavior is uniform across authorize, token, refresh, and
   revoke — proven by composition tests, not by unit-testing the lookup in
   isolation. The observable protocol change is a thrown exception (fail
   closed), not an OAuth-formatted error response — no response-shape claim
   is made here.
6. **Physical-constraint-backed concurrent seeding.** `OidcClientSeeder` now
   delegates to `OidcClientLookup::findByClientId()` (removing a second,
   independent query-then-create implementation) and, on a genuine
   concurrent-boot race, catches the real
   `Doctrine\DBAL\Exception\UniqueConstraintViolationException` the physical
   unique key raises and recovers by updating the concurrent winner's row in
   place — never a crash, never a second row for the same `client_id`.
7. **Explicit `sql-column` refusal, not a second reproduction.** `OidcClient`
   declares no `storageBackend` (defaults to `sql-blob`, the only supported
   layout). Its three list-valued fields (`redirect_uris`, `scopes`,
   `grant_types`) have no declared column-encoding contract; a deliberate
   `sql-column` composition of this exact entity shape refuses them with
   `UnstorableFieldException`, pinned by a regression test. This is a stated
   boundary, not a claim of `sql-column` support.

## Scope exclusions (preserved)

- No foundational schema-engine redesign — the declarative
  `#[StorageUniqueKey]` / `schema:sync` mechanism itself is unchanged; this
  candidate deliberately does not use it (decision 3).
- No queue, Bimaaji, distribution, Studio, or shared CI changes.
- `docs/specs/s1-signing-key-lifecycle.md` is not edited — this candidate
  touches no signing-key table, state, rotation, or revocation behavior.
  `docs/specs/api-layer.md` receives a dated spec-reviewed projection
  (observable pre-auth protocol change only); `s1-signing-key-lifecycle.md`
  is acknowledged via a `spec-reviewed:` commit trailer, not a content edit.
