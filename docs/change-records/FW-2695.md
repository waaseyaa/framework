# FW-2695 — root-application schema migration discovery

- Parent: `4040b78b0e440aaf823d4a0fed73b9a600e367f7`
- Contract: `docs/specs/schema-evolution-v2.md` §8 and §15 Q9
- ADR: `docs/adr/009-migration-manifest-discovery.md`
- Issue mirror: `waaseyaa/framework#2695`
- Consumer blocker: `jonesrussell/claudriel#764`
- Authority: source, tests, documentation, branch, commits, push, and draft
  review candidate only

## Outcome

A Composer root application can declare legacy path and class-discovered V2
schema migrations through the same `extra.waaseyaa.migrations` contract as an
installed package. The stock manifest cache, loader, `migrate` command,
`migrate:status`, `db:init`, `install:init`, and kernel-exposed migrator all see
the same root-owned catalogue.

## Decisions

- Review corrections: preserve `app:*` ledger IDs for the canonical root
  `migrations/` directory even when explicitly declared (including aliases).
  Other root paths retain Composer ownership. Prove upgrade safety against an
  applied, non-idempotent legacy migration, not only catalogue keys.
- `db:init --dry-run` must enumerate pending V2 as well as legacy migrations
  without modifying schema or ledger. Every stock Migrator composition must
  receive canonical RuntimePolicy and a logger: development checksum drift
  warns and skips; production-like environments reject it.
- Scoped fixture autoloaders must be unregistered even when database setup
  throws; Windows retained-handle cleanup must not mask assertion failures.
  These corrections do not decide or implement #2701.

- The root Composer package `name` is the default migration package identity. A root
  migration declaration without a non-empty package name fails closed with the
  existing `INVALID_MIGRATION_ENTRY` diagnostic.
- Relative root path entries resolve against the application root. Installed
  package paths continue to resolve against their install paths.
- The undeclared `<projectRoot>/migrations` legacy fallback remains supported
  under package `app`. When the root manifest already declares that directory,
  the declared source keeps the same `app` identity and the fallback is
  suppressed. Existing ledger rows are never renamed or replayed on upgrade.
- Cached manifests are augmented from root Composer metadata on load. This
  makes a framework upgrade safe even when the root Composer bytes—and thus the
  existing cache fingerprint—did not change.
- Every stock apply composition receives `V2PlanExecutor`, and status receives
  both legacy and V2 catalogues. Discovery without executable/observable CLI
  wiring is not considered support.

## Work packages

1. Root manifest identity, validation, cache upgrade, and loader path semantics.
2. V2 executor/status wiring across CLI and kernel compositions.
3. End-to-end discovery, dry-run, apply, status, and verify evidence.
4. Consumer documentation and governed changelog fragment.

## Review and verification boundary

- Gate-completion slice: add coverage-bearing provider Unit acceptance through
  its declared commands, document the CLI catalogue/executor contract, and
  regenerate both verifier-owned rosters after reviewing every addition as
  test-only. No production migration behavior or #2701 design changes are part
  of this slice.
- Rebased onto current remote main before publication; no source conflicts.
- The root runtime, db:init, and provider tests independently register their
  fixture through a scoped loader (or reuse an existing optimized classmap),
  unregistering it afterward rather than mutating every registered loader.
  A second unrelated loader pins the random-order duplicate-discovery regression.
  This matches
  the V2 discovery contract while remaining deterministic under CI's ordinary
  `composer install` mode.
- Optimizing the entire dev autoloader exposes an existing access-policy fixture
  discovery defect: `FreshInstallContentModelHydrationTest` fails twice on both
  this candidate and unmodified parent `4040b78b0`. Both tests pass with ordinary
  autoloading. This is not treated as a #2695 source regression.
- Full merge-readiness evidence must bind the final candidate SHA. Earlier
  pre-rebase Unit evidence is historical, not a substitute for that gate.
- Claudriel remains stopped at the separate public-contract blocker #2701.

## Exclusions

- No new migration registry, loader, manifest key, or application callback.
- No change to V2 plan semantics, compiler policy, ledger identity, or rollback.
- Fresh-install execution semantics for a V2 entity evolution targeting an
  absent or already-current table remain blocked by `waaseyaa/framework#2701`.
- No merge, release, package split, publication, deployment, or consumer-repo
  mutation is authorized by this record.
