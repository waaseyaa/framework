## Route table contract: pure metadata

Agreed design direction for the #3122 shared-contract checkpoint: declarative route contributions, deterministic composition, and an immutable completed snapshot. This is a target contract to audit and qualify, not a claim that current routes() hooks already satisfy it.

The table describes route names, paths, methods, matching constraints, defaults, priority/order, handler identifiers, declared access requirements, and rendering/API metadata. Request matching context and execution services remain separate. Handler references identify execution targets without constructing controllers or capturing live service instances in the published snapshot.

Route contribution collection, composition and inspection must not instantiate execution services, resolve credentials, open sessions, query application data, perform durable writes, or invoke handlers. Composition may use explicit application configuration and finalized declarative definitions; record those inputs and their lifetime rather than assuming all configuration is request-independent. This contract concerns route production/inspection: separately identify any broader kernel boot prerequisites so a metadata-only table is not mistaken for proof that the entire current CLI bootstrap is side-effect-free.

Completeness still requires a lifecycle: collect all applicable Framework and application-provider contributions, validate duplicates and priority, then publish the completed snapshot. Early, recursive, failed or unsupported-profile access must receive explicit refusal or availability status rather than an empty or partially cached table. HTTP, CLI and Bimaaji must consume the same canonical definitions; request-specific matching and handler resolution happen afterward.

Declared route access is not a claim of effective access to every resource. Downstream entity/field policies, middleware and handler checks can impose further restrictions. Introspection must preserve this distinction and describe its coverage limits.

- [ ] Audit existing provider routes() hooks and BuiltinRouteRegistrar against metadata purity. Record service resolution, runtime reads, side effects, captured objects/callables and inputs whose readiness depends on boot. Give each incompatibility an owner and migration/compatibility disposition before changing the extension contract.
- [ ] Specify the canonical contribution/metadata shape, supported handler-reference forms, complete phase, immutable snapshot ownership, cache identity/lifetime, and early/recursive/failure refusal. Reconcile Foundation ownership with routing, Bimaaji and CLI at #3122's shared-contract checkpoint.
- [ ] Prove route composition and inspection with discriminating fixtures whose execution-service factories, credential resolvers, session starts, application-data queries and handlers fail or record a call if invoked. Assert they remain uninvoked while a nonempty application route is described accurately. Keep these controls separate from intentional kernel boot activity.
- [ ] Prove deterministic composition for equivalent declared inputs, duplicate/priority behavior, and that consumers cannot mutate the shared published snapshot or retain request-specific state in it.
- [ ] Prove HTTP matching, route:list and graph inspection agree on the same completed definitions, while access descriptions retain layered-enforcement limitations. Include real installed-package composition as required by #3121.

This adds a required design/audit checkpoint for the bounded route repair. It does not make unrelated Foundation convergence a prerequisite for unblocking the consumer.
