## 6. Reruns and flakes

**Head-SHA rule.** Every attempt of one run id shares one head SHA by
construction -- a new head produces a *new run id* and is therefore not a rerun
at all. A job that flips red to green across attempts of the same run id is a
flake. The property is verified from the collected data (`same_head`), not
assumed.

## 7. Random-order uniqueness

For every failed `ci/random-order-shard-N` job: did random-order execution detect
a failing test that the ordinary timing-balanced shards on the same head did not?

Random-order shards upload **no JUnit** -- they run PHPUnit with `--no-coverage`
and no `--log-junit` -- so their failing-test identity exists only in the job
console log and is `derived` with a parser version and a confidence. The ordinary
side comes from the `php-test-shard-*` JUnit artifacts on the same head.

One bias is recorded rather than corrected: the artifacts API does not say which
attempt produced an artifact, so on a rerun run the ordinary set may union both
attempts. Every attempt of a run shares one head SHA, and a larger ordinary set
can only make a unique-detection verdict harder to reach, so the bias is
conservative and never inflates `unique_first_pass_detection`.

The opposite direction is closed rather than merely biased. A **shrunken** ordinary
set is what would manufacture a false unique detection, so every way of producing
one fails closed to `not_classifiable`: an expired or missing artifact, an archive
with no `junit-*.xml` in it, and a present-but-unparsable JUnit document all stop
the comparison instead of quietly comparing against fewer tests.

## 8. Acceptance floor (`docs/specs/ci-test-selection.md` section 9)

The spec requires, for a future shard-count change: median and p95 critical-path
time plus runner minutes from **at least 10 comparable runs**, **one green
pull-request run**, **one green post-merge `main` run**, and **one green complete
nightly proof**. This section states whether the *evidence* floor is met. It
states nothing about whether a shard-count change is warranted.

| Floor element | Evidence | Status |
|---|---|---|
| >= 10 comparable runs | 80 fingerprint-matched runs across the enforced cohorts | met |
| one green pull-request run | 35 green run(s) in cohort `pull_request`, e.g. run `34169462993` | met |
| one green post-merge `main` run | 20 green run(s) in cohort `main_push`, e.g. run `34149805438` | met |
| one green complete nightly proof | 33 green run(s) in cohort `nightly`, e.g. run `32060622995` | met |

Runner minutes are **not** available (see section 3); the cost proxy stands in
their place and is labelled as a proxy. That element of the floor is therefore
satisfied only in proxy form, and any future acceptance must say so explicitly.

## 9. Missing evidence

- **Billed runner minutes: 0 of 3642 jobs.** Structurally unavailable on a public repository; the cost proxy is labelled as a proxy everywhere it appears.
- **Jobs not mapped to an inventory job: 2 of 3642.** An unmapped job takes no classification that needs inventory lineage.
  - `ci/random-order-shard-${{ matrix.id }}` (1). A matrix job that is skipped before it expands is reported by GitHub under its *unexpanded* name, which is not a visible context the inventory can bound. The tool records the gap rather than guessing a shard number.
  - `ci/test-shard-${{ matrix.id }}` (1). A matrix job that is skipped before it expands is reported by GitHub under its *unexpanded* name, which is not a visible context the inventory can bound. The tool records the gap rather than guessing a shard number.
- **Jobs with no wall time: 0**; **with no queue time: 0**.
- **Run attempts in the cohort that GitHub listed no jobs for: 2.** Each is kept as a run record with `jobs_listed: 0` and null durations, and named in section 2. Their durations are absent from the section 3 distributions, where they are counted in the `Missing` column.
  - `github-listed-no-jobs-for-this-completed-run` (1).
  - `github-lists-no-jobs-for-this-earlier-attempt` (1).
- **Random-order shard failures not classifiable: 0 of 20** (reasons in section 7).
- **First-attempt jobs outside the classification vocabulary: 0.**
- **Live check-run names are unobserved.** Job identity here is the hosted job `name` matched against the inventory's *derived* visible contexts. The live ruleset and its integration bindings are Task 6, not this baseline.

The dataset keeps a per-job step **summary** (step count, the failed steps, and the first of them) rather than the full step list. That summary is not decoration: the
first failed step is exactly what separates a setup or infrastructure failure from
an execution failure, so dropping it would leave a classification `derived` from
evidence the dataset no longer holds.

## 10. What this baseline does NOT say

- It makes **no cadence recommendation**. Whether random-order execution should
  run on every pull request, at what shard width, or at all, is Task 8. Nothing
  here authorizes a workflow, ruleset or policy change.
- A `corroborating` verdict means the random-order failure *also* appeared in an
  ordinary shard **on that head**. It is not evidence that random-order execution
  has no unique detection value in general -- only that it added none on that run.
- The cost proxy is **not** money. No billing figure appears in this document.
- Comparability is structural. Two runs with the same fingerprint may still
  differ in step content, runner image, test count, or dependency versions; the
  fingerprint bounds the *job graph*, nothing else.
- Nothing here re-asserts the offline conformance result (Task 3) or the live
  ruleset (Task 6).
