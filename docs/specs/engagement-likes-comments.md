## Existing implementation

At `7f632a7c298793a786158cadceba1358ad711c59`, engagement registers API-enabled Reaction, Comment and Follow entities. It supplies access policies including authenticated creation, parent-cascaded reads and ownership controls. It has no complete desired-state like service, reply-parent model, durable like uniqueness or supported paginated discussion workflow. Existing unit tests do not establish this target contract. This record reports planned capability and makes no new vulnerability finding.

## Scope and ownership

The slice provides simple like/unlike, text comments and one-level text replies on an eligible published root target. It includes author editing/removal, authorized moderation, permission-aware reads/counts, retry safety and concurrency. Broader reaction selection, public reactor directories, messaging, attachments, notification delivery, ranking and following feeds remain outside this slice.

Engagement owns interaction identity, reply relationships and operation/query semantics. Existing repository, schema, transaction, access, audit and cache authorities retain their responsibilities. Applications supply account eligibility, blocking and scoped moderation decisions through the policy contract below. The limits and retention defaults below apply to this slice. A featured subject or public profile does not become an authenticated actor or acquire publisher/moderator authority.

## Operations and permissions

The service and transport contract below owns these operations. The service boundary is implemented by `EngagementService`, `EngagementPolicyInterface` and the immutable result DTOs in `waaseyaa/engagement`; the API-owned HTTP adapters expose the transport contract below.

| Operation | Authority and outcome |
| --- | --- |
| Set liked state | Bind the authenticated actor, require current target and interaction eligibility, persist the requested boolean state and return authoritative viewer state and permitted count. |
| Read summaries | Return viewer liked state and permitted like/discussion counts for a bounded collection of visible roots. Support feed batching without one query per card. |
| Create comment | Bind actor and immutable root, validate text and current policy, atomically persist comment and actor-scoped operation identity. |
| Create reply | Apply comment rules and require a visible eligible top-level parent on the same immutable root. Reject reply-to-reply and cross-root assignment. |
| Edit comment/reply | Require current author authority and expected revision. Return the new revision and edited time. |
| Author removal | Require current ownership and operation permission. Remove content from ordinary reads while preserving permitted reply structure. |
| Moderator removal | Require explicit scoped authority and attributable audit evidence. Preserve the distinction from author removal. |
| List discussion | Apply current visibility to direct reads, top-level pages, reply pages and derived totals, with stable bounded cursors. |

Anonymous readers may read eligible published discussion when the application's root policy allows it. Authentication alone does not grant access to hidden targets or moderation powers. Server-side actor binding and current policy checks apply inside the canonical mutation authority. Transport authentication, CSRF and form validation compose with that authority. Generic HTTP and trusted service/repository/job/tool paths must enforce the same integrity rules without bypasses.

Like state is separate from private saves and grants no contact permission. A repeated requested state returns success with the same logical state. There is at most one logical like per actor/root, enforced durably under concurrency. Overlapping opposite writes serialize at the database writer boundary; the last committed state wins. Each response describes its transaction snapshot, so a later write may supersede it. After an ambiguous result the caller can reconcile the current state. Retried operations recheck current access before exposing prior results.

## Discussion state transitions

These transitions settle the accepted reply, removal and editing behavior for this slice.

| Current state | Transition | Required ordinary projection |
| --- | --- | --- |
| Visible comment/reply | Author edits with matching revision | Changed text is visible immediately, with edited time. |
| Visible comment/reply | Stale revision edit | Conflict, with no overwrite. |
| Visible top-level comment | Author or authorized moderator removes | Body and author disappear. If permitted replies survive, retain a neutral structural placeholder. |
| Removed top-level comment | Reader lists permitted surviving replies | Show the placeholder and allowed replies, with no removed author/body disclosure. |
| Removed comment/reply | Stale edit or retry | Refuse restoration. |
| Removed top-level comment | New reply | Refuse a new reply to the removed parent. |
| Any discussion | Root becomes hidden, restricted or removed | Hide descendants and reactions from unauthorized direct and derived reads. |
| Hidden root | Root visibility restored | Re-evaluate current access, retaining independent moderation removals. |

Reply depth is one. Every reply retains its root identity and top-level parent identity. Author, root and parent references are immutable after creation. A removed reply is omitted from ordinary discussion. A removed parent without permitted replies is omitted. Placeholder IDs/cursors reveal no unauthorized content existence or identity.

A block-hidden top-level comment uses the same neutral placeholder when permitted replies survive. Show no blocked author, avatar, text, timestamp or author link. A block-hidden reply is omitted. No new reply may target a parent the actor cannot view. Placeholder identity is a structural reference and confers no read or reply authority. Root inaccessibility hides the entire discussion.

## Retry, concurrency and persistence

Comment creation uses durable operation identity scoped to actor and operation, with a payload fingerprint. Same identity and payload returns the same logical result when current access permits it. Conflicting payload refuses. Creation and retry custody share the transaction so a rollback leaves neither a successful-looking receipt nor a partial comment. The fixed retry window and erasure rules below govern receipt custody.

Edits use expected revisions. Concurrent edits cannot silently overwrite each other, and removal wins against stale edits. All operations must recheck current account and target state at the authoritative boundary. Mutations acquire the canonical S1 SQLite writer before reading current account, target, parent and block/moderation state. Those policy records and changes must share that database serialization boundary. A consumer using a separate policy authority must supply a validated current-state fence or receive a configuration refusal for writes; no remote-policy cache substitutes for the fence. Busy/lock failure returns a retryable refusal without a success claim.

Target-integrity implementation remains owned by #2756. For this bounded slice, writes require a resolvable eligible root, and replies require a resolvable eligible parent on that root. Read policy remains fail-closed. The mandatory repository guard and identity table below enforce both `sql-blob` and `sql-column`. Assess existing unresolved targets and duplicate reactions before enforcing new constraints. Inventory and migration decisions must precede destructive cleanup or constraint installation. This slice does not close the wider follow obligations by implication.

## Reads, counts and caching

Use `(created_at, stable numeric ID)` ascending for top-level comments and separately for replies. Page size defaults to 20 with a maximum of 50. A summaries request accepts at most 50 distinct roots. Discussion totals include visible comments and replies, excluding placeholders. A visible top-level count excludes placeholders; page entries may include placeholders with visible replies. Each parent exposes its own permitted reply count. All totals use the same current policy as ordinary reads.

Each page scans at most 200 candidate rows, using a single request-local policy snapshot and a captured high-water ID. If filtering consumes the scan budget, return an empty or partial page with `nextCursor` and `hasMore=true`; only `nextCursor=null` means end. Consumers continue with an explicit load-more action and never infer end from an empty page. Continuation tokens are opaque authenticated-encrypted envelopes using Foundation's `ApplicationMasterKeyring` with new engagement-specific purpose registrations. Bind root UUID, parent UUID where applicable, viewer identity (including anonymous), policy generation, page size, high-water ID, last scanned position and expiry. Cursor lifetime is 15 minutes. Expiry returns `CURSOR_EXPIRED`; policy-generation change returns `CURSOR_STALE`, both requiring a restart. Changing visibility never trusts the cursor as permission. Unknown/malformed/tampered tokens use `INVALID_CURSOR`.

Root access is checked before cursor errors or counts are exposed. Account/block/moderation/root changes increment the canonical policy generation within their transaction. The first implementation performs fresh reads with request-local batching and sends `Cache-Control: private, no-store` on viewer-sensitive responses. It adds no cross-request engagement cache. HTTP error responses use the same privacy rule. Summary queries batch root loading and grouping; exact visibility-aware totals may cost work proportional to the matching discussion and must have real-storage plan/latency evidence before installed qualification. Scan bounds govern pages, not total computation. Read timeouts return a retryable unavailable result and never invented partial counts. This is an explicit first-slice performance tradeoff.

## Text, editing and limits

Comments and replies are UTF-8 plain text, 1 to 2,000 Unicode code points and at most 8,000 bytes after normalization. Convert CRLF and CR to LF, trim leading/trailing Unicode whitespace, preserve interior whitespace and line breaks, and apply no Unicode composition normalization. Reject invalid UTF-8, NUL and C0 control characters other than LF and TAB, and DEL. Blank content refuses. Output is escaped text with no HTML/Markdown execution. Canonical normalized text is the retry fingerprint input, so normalization-equivalent retries replay.

Authors may edit at any time while their account, comment and root remain eligible, using the expected revision. No time-based edit window applies. Unchanged canonical text returns the current revision without a new edit. Removed or moderated comments cannot be edited/restored. Public views expose only current text and edited time. Revision snapshots containing removed text follow the erasure rule below.

Default mutation budgets are keyed by installation, authenticated actor and operation group, shared across all roots and HTTP/non-HTTP callers. Comments plus replies share 5 attempts/minute and 60/hour. Edits share 10/minute and 120/hour. Like/unlike share 60/minute and 600/hour. Each window is fixed from its first admission. Author removals and moderator removals have no engagement quota, so an exhausted posting budget cannot prevent removal. All eligible attempts, including matching retries and no-op likes, consume quota. Initial authentication, root-availability and policy checks occur before quota consumption. A permission change discovered by the authoritative in-writer recheck still consumes the already admitted attempt budget; quota is an attempt limit, not a successful-write counter. Transport-level abuse protection remains with the existing HTTP owner. Limits are named installation settings with these defaults; changing them does not alter identity or permissions.

Use Symfony RateLimiter's fixed-window implementation with a small canonical-database `StorageInterface` adapter and Symfony Lock `FlockStore` on the supported single-host S1 SQLite boundary. All processes use the same installation-scoped local lock directory. Acquire quota locks non-blockingly in deterministic key order before the engagement writer transaction, release them before acquiring that writer, and recheck authoritative permissions inside the writer. Use the externally acquired lock with the limiter's internal lock unset, then call `consume(1)` without reservations or waiting. Failure to acquire immediately returns retryable 503. Do not hold a quota lock while waiting for the engagement writer. Both quota windows must admit before mutation; consumed attempt budget need not roll back if another window refuses. Each limiter `fetch`/`consume`/`save` runs under its externally acquired Flock, with the adapter writes committed in a short dedicated canonical-database transaction before lock release. Store the Symfony fixed-window start, duration, consumed tokens and expiry in a migration-owned table keyed by limiter identity, reconstructing only the known Window state rather than unrestricted object deserialization. Expired rows read as absent and hourly maintenance deletes expired state. All writers use that same lock-plus-transaction path. Service mutation entry points own quota admission and the subsequent writer transaction and refuse invocation inside a caller-owned active database transaction. Both windows may be consumed in separate committed admissions; this is safe because partial quota consumption is documented and no mutation starts until both admit. Limiter storage/lock failure is `TEMPORARILY_UNAVAILABLE`. Qualify parallel PHP processes and time-window edges. Multi-host limiter storage is outside this S1 contract.

## Service and transport contract

Add `Waaseyaa\Engagement\EngagementService` and `EngagementPolicyInterface` through the existing provider. The policy is required for serving engagement, and absence or an indeterminate decision refuses. Use `AuthorizationPrincipalInterface` for actor binding, `EntityAccessHandler` for root visibility and explicit application permission decisions for write, edit and moderation eligibility. A globally privileged account still passes root existence, immutable identity and lifecycle integrity checks. Policy integration provides a transaction-consistent generation and current actor/account/block/moderation decisions, including batched per-viewer visibility. The service resolves references; callers supply no author ID or publication status.

Planned public methods, with immutable root/comment reference and result value objects local to engagement, are:

```php
issueCommentKey($actor, $root, $parent = null): string;
setLiked($actor, $root, bool $liked): LikeState;
createComment($actor, $root, string $text, string $submissionKey, $parent = null): CommentView;
editComment($actor, $comment, string $text, int $expectedRevision): CommentView;
removeComment($actor, $comment): void;
moderateRemove($actor, $comment, string $reason): void;
getComment($viewer, $comment): CommentView;
summaries($viewer, array $roots): array;
comments($viewer, $root, ?string $cursor = null, int $limit = 20): CommentPage;
replies($viewer, $root, $parent, ?string $cursor = null, int $limit = 20): CommentPage;
```

`$actor` and `$viewer` are immutable authorization principals. A root reference identifies registered type and positive numeric ID; the service resolves and persists its UUID to prevent reused IDs changing the target. Comment references use UUIDs. DTOs expose only permitted current data. A create response contains the committed UUID/revision and current projection. A no-op remove of an already removed comment is successful only for its currently authorized author or scoped moderator; other readers receive the generic unavailable result.

`waaseyaa/api` owns `EngagementApiRouter` and `EngagementController` under `/engagement/v1`. Its existing `ApiServiceProvider` router assembly conditionally resolves `Waaseyaa\Engagement\EngagementService` from installed provider metadata, following the opt-in router pattern used for audit/notifications. API declares engagement as a development/test dependency for adapter tests, with string-based optional resolution in production so core-only installs neither require nor boot engagement. Engagement registers its domain service through its existing provider and imports no API/routing class. Absent engagement means these routes are unregistered, while an installed but misconfigured policy returns sanitized 503. Root-scoped routes use `/targets/{type}/{id}` with `GET /summary`, `PUT /like` (`liked` boolean), `POST /comment-keys` (optional parent UUID), `GET /comments` and `POST /comments` (`text`, `submissionKey`, optional parent UUID). `GET /comments/{uuid}/replies` pages replies after resolving the root. `/comments/{uuid}` supports GET, PATCH (`text`, `expectedRevision`) and DELETE. `POST /comments/{uuid}/moderation-removal` accepts a required reason of 1 to 500 code points. `POST /summaries` performs a bounded read over root references. Normal session authorization and CSRF apply to mutations. Trusted jobs invoke the same service with an explicitly authorized principal.

HTTP JSON bodies are plain objects served with the existing JSON:API-shaped envelope. The optional reply-parent field is `parentUuid`; key issuance returns `data.submissionKey`. Bulk summaries accept `roots: [{type, id}]` with at most 50 references. Summary data is `{root: {type, id}, liked, likeCount, commentCount, topLevelCount}`; likes return `{liked, count}`. Comment data contains only `uuid`, `authorId`, `text`, `createdAt`, `editedAt`, `revision`, `placeholder`, `replyCount` and `replayed`. Pages return a data array plus `meta.nextCursor` and `meta.hasMore`. Placeholder identity/body/time/revision values stay null. No entity serialization or raw repository access occurs in the transport.

Bodies reject unknown fields and non-object JSON; boolean and revision fields require exact JSON types. Page queries accept only `cursor` and decimal `limit` (1 through 50). The canonical kernel rejects malformed JSON syntax with its existing 400 envelope before adapter dispatch; well-formed invalid engagement input is 422. Reads support HEAD with an empty response body. Session middleware supplies the immutable decision principal; caller-supplied author/account fields are never accepted. Every mutation explicitly opts into the existing CSRF middleware even for JSON. Existing transport precedence applies: missing/invalid CSRF returns 403 before adapter authentication; an anonymous write that passes CSRF returns `401 AUTH_REQUIRED`. `POST /summaries` is read-only and opts out of CSRF while retaining root-policy checks.

The API provider publishes a copied `api.route.engagement` availability fact and composes all 11 route declarations without resolving the domain service. Compiled terminals retain a scalar action default on the canonical route; the router also supports legacy controller dispatch. Service resolution occurs inside the request refusal boundary. The API-owned response privacy middleware wraps the session, CSRF and transport-abuse pipeline for matched engagement routes, so their early refusals and normal results replace the complete cache policy with `private, no-store`. Framework routing/boot failures before a route is matched retain their existing global refusal surface.

Generic JSON:API writes for Reaction and Comment are disabled. Generic reads also use these projections or refuse; they cannot bypass removed/blocked-content filtering. Direct configured repository writes require the mandatory invariant authority below, including `saveMany`, deletes and revision/published-pointer paths. Generic Follow behavior remains under #2756 and is not changed by this bounded endpoint cutover.

Error codes map to existing JSON:API-shaped error objects with string HTTP status, title and detail. Use `AUTH_REQUIRED` 401 for absent authentication on writes; `TARGET_UNAVAILABLE` 404 for unknown/missing/inaccessible root or comment; `ACTION_FORBIDDEN` 403 only after the target is visible; `VALIDATION_FAILED` 422; `REVISION_CONFLICT`, `SUBMISSION_CONFLICT`, `SUBMISSION_EXPIRED` and `CURSOR_STALE` 409; `INVALID_CURSOR` and `CURSOR_EXPIRED` 400; `RATE_LIMITED` 429 with `Retry-After`; configuration/storage/lock failure `TEMPORARILY_UNAVAILABLE` 503. Submission-key issuance returns 200. New creation returns 201, matching replay 200, like/edit reads 200, removals 204. A post-commit completion failure returns a retryable 503 with the same submission key guidance, never a false rollback claim. Framework transport sanitization handles unexpected errors.

## Write boundary and schema decisions

Use canonical repository writes and transactions. Add a mandatory repository-owned invariant registration for Reaction and Comment, extending the shared UnitOfWork mutation boundary where needed under #2756. The actual consumer is engagement's need to enforce identity, current authority and lifecycle even with `validate=false`; optional entity validation and controller-only checks cannot meet it. Registry invocation is mandatory for all configured repository save/delete/batch and revision/pointer mutation paths, with original and proposed state and canonical transaction connection. Mark these entity types as requiring that guard, so missing wiring refuses instead of creating an unguarded repository.

The new minimal storage SPI is `EntityMutationInvariantInterface::assertMutation(EntityMutationInvariantContext $context): void`, registered by required entity type in the kernel repository factory. The context contains the operation enum (`create`, `update`, `delete`, `revision`, `translation`, `publication`, `maintenance`), original/proposed entity, immutable principal/maintenance authority, and active canonical transaction identity. Registration metadata `requiredMutationInvariant` names the guard; construction of a writable repository for such a type fails when its guard or canonical database is absent. Invoke inside the UnitOfWork after writer acquisition and before any storage effect. Guard exceptions roll back the batch. Guard execution is independent of `validate` and `SaveContext` flags.

Covered public methods are `save`, `saveAggregateMutation`, `saveMany`, `delete`, `deleteMany`, `rollback`, `setCurrentRevision`, `setPublishedRevision`, `promotePublishedRevision`, `clearPublishedRevision`, `saveTranslation`, `saveTranslationRevision`, `saveTranslationRevisions`, `pruneRevisions`, `backfillInitialRevisions` and `backfillMutationAuthorities`. Non-revisionable/untranslated engagement entities reject revision/translation/publication operations before storage. Maintenance operations have their own explicitly scoped internal authority and cannot impersonate a member mutation. Batch operations validate every affected member under one rollback boundary. The same registry covers configured repository reads only where needed to preserve ordinary projection policy; public engagement reads use the service projections.

Engagement's guard requires a service-created, non-exported, operation-scoped authorization context bound to immutable principal, root UUID, entity UUID, operation and the active transaction. It rechecks invariants at persistence time and clears the context in `finally`, including rollback and reentrant failure. Direct repository callers outside that context refuse and must call the service. No client-controlled save flag or admin permission disables the guard. Existing invariant/lifecycle hooks may implement this only where they provide the same mandatory coverage; a new generic interceptor framework is unnecessary. Storage-driver SPI and raw SQL remain internal trusted infrastructure and are outside the public authorized-mutation API. Their tests/migrations must not be described as actor-authorized entry points.

Use a migration-owned engagement identity table with unique `(actor_id, root_type, root_uuid, reaction_type)` to own like membership, independent of blob/column field projections. Reaction is the canonical entity; identity row and entity create/delete share the writer transaction. Unlike removes both. The guard enforces the same projection for all authorized writes. Comments remain non-revisionable and untranslated. They add immutable `root_uuid`, `parent_comment_uuid`, lifecycle state and edited/removed timestamps through canonical schema authorities in both layouts. `expectedRevision` is the integer `aggregateVersion` from the existing repository `EntityMutationToken`, initially 1. The service loads current state/token inside the writer transaction, compares that version with the client expectation and uses the canonical aggregate mutation authority to claim the loaded token for edit/removal; successful content/lifecycle mutation increments the version. No-op edits do not claim a new version. New comments initialize their mutation authority atomically with creation. Existing imported comments receive a version-1 authority through the existing backfill path. This uses `saveAggregateMutation`/canonical delete fencing for non-revisionable entities, with no revision-table creation or new version-counter authority. If the current aggregate path assumes revisionability, extending that existing owner for non-revisionable comments is part of WP2. No comment revision snapshots are created; legacy body-bearing snapshots encountered during migration/removal must still be erased.

Migration scans existing rows before installing the unique projection. Keep the earliest `(created_at, ID)` eligible duplicate like as the survivor and remove other duplicate like rows through migration-owned canonical operations in the same atomic batch. Existing valid comments become top-level revision-1 comments. Legacy unpublished comments preserve their text and status in a non-serving `unpublished` lifecycle; restriction alone does not become removal or start removal retention. Missing/unknown/unresolvable roots and invalid authors enter a restricted quarantine state excluded from all ordinary reads, summaries and mutations. Do not invent an author or root. Retain quarantined payload for at most 30 days, then erase through the bounded purge path; migration logs record counts/reasons/IDs without bodies. New integrity enforcement is active for writes during migration. Migration failure rolls back the current batch and resumes from recorded progress without duplicate survivors. Existing non-like reactions remain outside the new like projection and must retain their integrity/read rules under #2756.

## Retry and retention decisions

`issueCommentKey` returns a purpose-bound opaque token sealed by Foundation's application-master keyring. Include version, installation scope, actor binding, root UUID, parent UUID, random nonce, issue time and fixed expiry 48 hours later. Token issue is permission checked and limited to 60/minute per actor. It creates no durable receipt until submission. New key purposes and versioned rotation/rollback compatibility belong in the existing Foundation key registry and rekey inventories, using its established envelope format. Unknown-purpose/key or expired keys refuse before mutation. Expiry is never extended by replay.

The engagement receipt contains only actor/key digest, canonical payload digest, result comment UUID and creation/expiry times. Store it atomically with the comment. No response body snapshot is stored. Replays load the current permitted projection, which may reflect subsequent edits, or return unavailable after removal. Same key and different normalized body/parent/root is `SUBMISSION_CONFLICT`; an expired valid key is `SUBMISSION_EXPIRED` even after its receipt has been swept. Request admission rejects tampered tokens before using claimed expiry. This prevents purging a receipt from making an old operation create a second comment. Reuse Foundation envelopes and canonical database transactions; publishing's `IdempotencyStore` remains publishing-owned because its Layer 3 dependency, response snapshots and retention semantics do not fit Layer 2 engagement.

Live published text stays until author removal, moderation, root deletion or the consuming application's erasure policy acts. Author/moderator removal erases body and any body-bearing revision snapshots in the same transaction; metadata records operation, actor and removal time for 30 days, then pseudonymizes the removed author and purges unnecessary metadata. A minimal author-free/body-free structural parent may remain while permitted replies need it. No public edit history is exposed. Mere restriction of a root hides content without erasing it. Permanent root deletion hides immediately and queues bounded purge of engagement bodies/revisions within 24 hours, with no restore through a reused ID. Receipts expire at 48 hours and are swept within 24 hours afterward, retaining no payload; expired-key admission remains cryptographically enforceable.

Use existing audit authority for attributable moderator actions with metadata only and a default 90-day retention, subject to its configured governance. Report evidence remains with its existing owning policy; engagement removal creates no separate evidence copy or hold store. Account erasure invokes the same purge mechanisms and removes engagement receipt actor links immediately. Purge runs hourly in batches of at most 200 via existing scheduler/CLI conventions, records aggregate progress, and retries safely. Author removal is idempotent while retained metadata can authorize it; after metadata erasure ordinary callers receive unavailable. Permanent deletion and privacy purge preserve only necessary body-free structural links. Concrete legal/evidence holds must be enforced by the existing retention owner before adopting its policy, with no implicit indefinite engagement retention.

## Installed storage selection

`engagement.storage_backend` selects `sql-blob` (default) or `sql-column` for Reaction and Comment when their provider constructs canonical metadata. Invalid values refuse before registration. Both retain the mandatory invariant and generic API cutover. The setting is an install-time choice for a new database; changing it is not a blob/column conversion procedure. Follow retains its existing layout. The installed-consumer fixture uses this supported setting rather than replacing entity definitions in a booted manager.
