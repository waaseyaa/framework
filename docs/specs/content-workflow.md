## Purpose

A general content-workflow engine: named editorial states, permission- and group-gated transitions between them, enforced in the write path, with transition audit history. The v1 consumer case is department routing — content drafted in one department routes to decision-makers for approval before publication — but nothing in the engine knows about any specific department: departments, states, and approval chains are site configuration.

**What Drupal core does that we match:** workflows as config, moderation state on revisions, forward drafts of published content (engine substrate; deferred on the shipped workflow — see the deferral note below), per-transition permissions.
**What Drupal needs contrib for that we ship (the "beyond"):** group-scoped transition constraints (department routing) as a first-class optional dimension.

## Concepts and config schema

A **workflow** is a config entity (CMI-syncable, validated on import):

```yaml
# config: workflows.workflow.editorial
id: editorial
label: Editorial
states:
  draft:      { label: Draft,     published: false, default_revision: false }
  review:     { label: In review, published: false, default_revision: false }
  published:  { label: Published, published: true,  default_revision: true }
  archived:   { label: Archived,  published: false, default_revision: true }
initial_state: draft
transitions:
  submit_for_review: { label: Submit for review, from: [draft],            to: review,    permission: 'use editorial transition submit_for_review' }
  publish:           { label: Publish,           from: [draft, review],    to: published, permission: 'use editorial transition publish' }
  reject:            { label: Send back,         from: [review],           to: draft,     permission: 'use editorial transition reject' }
  archive:           { label: Archive,           from: [published],        to: archived,  permission: 'use editorial transition archive' }
  restore:           { label: Restore to draft,  from: [archived],         to: draft,     permission: 'use editorial transition restore' }
  restore_to_published: { label: Restore,        from: [archived],         to: published, permission: 'use editorial transition restore_to_published' }
```

**Deferred: no `revise` edge ships on `editorial` (WP-2 rework descope).** An earlier WP-2 draft shipped a `revise` transition (published → draft, the forward-draft entry edge, mirroring Drupal editorial's "Create New Draft") on `DefaultWorkflows::EDITORIAL`. The final whole-branch review found the mechanic unshippable as-is (findings #1/#2/#4/#5/#11): forward drafts (a published→draft edge on the shipped `editorial` workflow) are deferred: the WP-2 review found no read path is pointer-aware, so a forward draft's tip content is served by `find()`-based readers while status/pointer reflect the published revision. Forward drafts return on true default-revision semantics (the base row keeps serving the published revision; drafts live only in revision rows). `revise` was pulled from the shipped workflow (WP-2 rework task 1); the underlying engine mechanic is untouched — see "Forward-draft mechanics" below, which describes live substrate — and stays reachable via any custom workflow that defines its own published → draft edge, and via the archived → restore → publish round trip below (unpublished throughout, so it does not carry the read-side risk). See "Deferred: forward drafts on the shipped workflow" below for the full follow-up scope.

`restore_to_published` (also task 2.6) is what makes archived content republishable: `restore` yields a forward draft whose published pointer still sits on the `archived` revision, so that draft's eventual publish is an `archived → published` pointer move — this edge is what the strict pointer-guard rule (below) checks it against. Mirrors Drupal editorial's "Restore" (`archived_published`) edge, shipped alongside "Restore to draft" (`archived_draft`). Full restore-flow permission set: `publish` + `archive` + `restore` + `restore_to_published`.

A transition MAY additionally carry `group_constraint: content_groups` (WP-3): fireable only by members of the group(s) the content belongs to (departments are `groups` entities; content carries a department relationship). Permission answers *may this kind of person do this*; the group constraint answers *may they do it to this content*. A workflow with no group constraints behaves exactly like Drupal core.

**Bindings** map `entity_type` + `bundle` → workflow id (config: `workflows.assignments`). Binding requires the entity type to be revisionable — rejected at config-import validation otherwise.

The default `editorial` workflow ships as **config data, not code**. The retired machinery's preset-in-code (`EditorialWorkflowPreset` as canonical definition) is an explicit anti-pattern here: replacing a self-contained populated default with an empty generic silently broke consumers once already (CLAUDE.md gotcha).

## State lives on revisions

`workflow_state` is stored **per revision** on workflow-bound types (two-axis storage substrate: `RevisionableStorageDriver`, `docs/specs/revision-system-unified.md`).

- A state flagged `published: true` sets the entity's `status` accordingly when its revision is the default.
- `default_revision: true` states promote their revision to default on entry — this is the **forward draft** mechanic: editing published content creates a new non-default revision in `initial_state`; the live revision stays published; the `publish` transition promotes the draft revision to default.
- Creating content starts it in `initial_state` (see save-path guard).

**Staged limitation (documented, not hidden):** v1 state is per *revision*, not per revision-*translation*. Drupal moderates per translation; per-translation state is a post-v1 stage on the same storage axis. Until then, translations share their revision's state.

## TransitionService — the one door

`Waaseyaa\Workflows\Transition\TransitionService` (final, container-bound):

- `transition(ContentEntityInterface $entity, string $transitionId, AccountInterface $account): TransitionResult`
  1. **Validate:** binding exists for the entity type/bundle; transition exists in the bound workflow; current revision state ∈ `from[]`; `$account` holds the transition's permission; group constraint (if any) satisfied. Failure → typed exception (`TransitionDeniedException` with a machine-readable reason), never a silent no-op.
  2. **Apply:** set `workflow_state` on the target revision; set `status` and promote to default revision per the target state's flags; persist through `EntityRepository` (the canonical pipeline — no direct storage writes).
  3. **Announce:** dispatch `WorkflowTransitionEvent` (pre + post, Symfony `Event` subclasses like the live `EntityEvent` lifecycle events); write a transition audit entry (see Integration).
- `getAvailableTransitions(ContentEntityInterface $entity, AccountInterface $account): array<TransitionDefinition>` — the read-side the admin UI renders buttons from. This resurrects the *concept* behind the retired dry-run/guards controllers as a real engine method.

## Save-path guard

An entity pre-save subscriber makes the raw write path equivalent to the service:

- A save that mutates `workflow_state` is validated as if `TransitionService::transition()` had been called by the acting account (`_account` semantics) — same denial, same exception. A raw `PATCH /api/node/{id}` cannot do what the service would refuse.
- **Create forces `initial_state`** and, for workflow-bound types, a non-published `status` unless the acting account holds a transition permission into a published state. This closes the born-published hole (`Node` defaults `status = 1` in its constructor) for workflow-bound types.

**Wiring invariants (both are lessons from the machinery this replaces):**
1. The subscriber registers against the **Symfony-contracts dispatcher FQCN** via the kernel-services bus — resolving the foundation FQCN silently no-ops (this exact bug left `DomainValidationListener` dead and is still latent in Media/Field). A **wiring regression test** asserts the subscriber actually fires on a real kernel-dispatched save; a unit test on the subscriber class alone does not count.
2. **Deny-path tests are first-class:** every gate (permission, from-state, group, create-initial-state) has an explicit test proving denial, not just tests proving the happy path.

**`SaveContext::isImport` has no effect on this guard (verified, WP-2 task 2.8).** `Waaseyaa\Entity\Event\EntityEvent` — the event `WorkflowStateGuard::onPreSave()` subscribes to — carries only `entity`/`originalEntity`/`langcode`; `SaveContext` is not threaded onto it at all (it only reaches the separate `BeforeSaveEvent`/`AfterSaveEvent` pair the migration platform's `EntityDestination::write()` sets `isImport` on). Consequence: a migration-platform import is validated by this guard exactly like any other create/update — the WP-0/WP-1 "born-published hole" rule applies uniformly, `isImport` notwithstanding. A create naming a non-initial `workflow_state` (e.g. an import preserving an already-published legacy row's status) is denied with `REASON_PERMISSION` when there is no ambient acting account, import or not. The sanctioned ways to import already-published content: (a) thread an authenticated `AccountContextInterface` account holding the transition's permission through the import run, or (b) import as `initial_state` (the common shape — no `workflow_state` set at all sails through regardless of account) and promote afterward via `TransitionService::transition()`, which takes its `AccountInterface` as an explicit argument, not ambient context. Pinned by `packages/workflows/tests/Integration/ImportSaveContextGuardTest.php`.

## Group constraints (WP-3)

A transition MAY carry `group_constraint: content_groups` (see "Concepts and config schema" above). `content_groups` is the only v1 kind — `Waaseyaa\Workflows\WorkflowTransition::GROUP_CONSTRAINT_CONTENT_GROUPS` is the single shared home for the literal, referenced by both `WorkflowValidator` (rejects any other value as a config violation at import) and `GroupConstraintChecker` (fails closed on any other value at runtime, in case invalid config ever evades the validator). Permission answers *may this kind of person do this*; the group constraint answers *may they do it to THIS content*.

**Membership model (`waaseyaa/groups`, L2).** Membership and content-department assignment are plain `relationship` rows (`waaseyaa/relationship`, L2), not a bespoke join table: `Waaseyaa\Groups\GroupRelationshipTypes::MEMBERSHIP` (`group_membership`, directed `user`/{uid} → `group`/{gid}) and `::CONTENT` (`group_content`, directed `{entityType}`/{id} → `group`/{gid}). `Waaseyaa\Groups\Membership\GroupMembershipService` (mirrors `GenealogyFamilyService::memberPersonIds()`) exposes `groupIdsForUser()`, `groupIdsForContent()`, and `isMemberOfAny()` over those rows, querying with `->accessCheck(false)` (system-context membership lookup, same justification pattern as genealogy) and taking scalar uid/entity-id arguments rather than `AccountInterface` — `waaseyaa/groups` does not need to require `waaseyaa/access`. Every lookup additionally filters `status = 1` (relationship liveness, mirroring `RelationshipTraversalService`'s own status filtering) — a soft-revoked (`status = 0`) membership or content-group row never counts. Temporal windows (`start_date`/`end_date`) are deliberately NOT evaluated in v1; that is a follow-up. `workflows` (L3) gains two new downward composer edges to satisfy this: `waaseyaa/groups` and `waaseyaa/relationship` (both L2) — see "Layering" below.

**Enforcement, at all four sites that can change or reveal a workflow state, in the same order (permission before group, never the reverse):**

1. **`TransitionService::transition()`** — the group-constraint gate sits immediately after the permission gate and before `PRE_TRANSITION` dispatch. Order is pinned by test: when an account holds neither the permission nor the membership, the denial reason is `permission`, never `group_constraint` — permission-precedence is checked end-to-end, including for accounts that *are* members of the content's department but lack the transition's permission.
2. **`TransitionService::getAvailableTransitions()`** — filters out any transition whose group constraint the account fails, in addition to the existing permission filter. This is the UI's only sanctioned read side; it must never offer a button the write side would refuse.
3. **`WorkflowStateGuard::guardUpdate()`** — the raw-save path gets the identical gate, checked immediately after its own permission check, and only when an acting `AccountContextInterface` context exists (a null context — CLI/queue/programmatic — stays edge-legality-only, unchanged from WP-2). Without this, a raw `PATCH` mutating `workflow_state` could enact a group-constrained transition `TransitionService` itself would deny.
4. **`WorkflowPointerMoveGuard`**, both branches:
   - *Different-state* pointer move: the edge's own group constraint is checked right after its permission check, same order as the other three sites, only when an account context exists.
   - *Same-state* pointer move (the any-of rule over all transitions targeting the state, see "Pointer-move guard" below): each candidate transition now needs **permission AND satisfied group constraint** to count, not permission alone — a constraint-less candidate still counts on permission alone, so the any-of semantics are unchanged for workflows with no group constraints. When every candidate fails (whether by permission, by group constraint, or by a mix), the denial's reason stays `REASON_PERMISSION` by design — the same-state rule was never granular about *why* the any-of loop found nothing, only *that* it did, and this is not changed for WP-3.

**Fail-closed rule (design invariant 5).** `GroupConstraintChecker::satisfies()` denies, never silently passes, in two cases: content carrying no `group_content` relationship row at all (there is no department to compare membership against — silently allowing here would defeat the constraint entirely, a loud misconfiguration rather than a silent pass), and a `group_constraint` value the checker does not recognise (config that somehow evaded `WorkflowValidator` degrades to deny, never to "unconstrained").

**Null-account-context rule (unchanged from WP-2).** The two guards' pass-through-on-null-context behavior, already established for permission checks, extends unmodified to the group-constraint gate: a null `AccountContextInterface` (CLI, queue, bootstrap) stays edge-legality-only everywhere, group constraints included. `TransitionService` never has this ambiguity — its `AccountInterface $account` parameter is always explicit, never ambient.

**Nullable-checker construction note (fail-closed, amended by the adversarial review fix wave).** All four sites take an optional `?GroupConstraintChecker`, following the same syntactic convention as `TransitionService`'s existing optional `dispatcher`/`auditWriter` — but null no longer means "no group gating". A transition WITH a non-null `groupConstraint` is DENIED (or filtered out of `getAvailableTransitions()`) when the checker is null, exactly as if `satisfies()` had returned false; only *unconstrained* transitions are unaffected by a missing checker. Production wiring (`WorkflowServiceProvider`) always injects a real checker via `resolveOptional()`, so this changes nothing for a correctly-wired install — what it changes is the failure mode of a wiring regression: a checker that silently fails to resolve now denies every group-constrained transition loudly (visible immediately as a spike in `REASON_GROUP_CONSTRAINT` denials) instead of silently un-gating them (the WP-3-as-shipped bug this fix closes). A null checker remains the correct choice for fixtures/tests that never exercise `group_constraint` transitions — they are unaffected either way.

**Membership write surface (WP-4).** The WP-3 "hand-crafted relationship rows" gap is closed by write methods on the same service — `GroupMembershipService::addMember()` / `removeMember()` / `assignContent()` / `unassignContent()` — and operator CLI commands (`groups:create` (ensures the `group_type` bundle exists), `groups:member-add`, `groups:member-remove`, `groups:content-assign`, `groups:content-unassign`; `Waaseyaa\CLI\Provider\GroupsCliServiceProvider`, `cli` L6 → `groups` L2 downward edge). Writes are idempotent and soft-revoke-aware: add/assign reactivate an existing `status = 0` row or no-op on a live one (never a duplicate row); remove/unassign set `status = 0` and never delete; add/assign throw `\InvalidArgumentException` when the target group does not exist (loud failure over dangling edges), while revokes tolerate an already-deleted group. Still out of scope, unchanged: the `group` JSON:API access PARK (#1871), admin SPA membership management UI, temporal-window evaluation, and wiring `RelationshipPreSaveListener` into production boot.

**Ops note.** An account with a blanket permission grant but no membership rows — e.g. `DevAdminAccount`, which answers every `hasPermission()` check `true` — is still denied on a group-constrained transition: memberships are data (relationship rows), not permissions, and nothing about holding a permission implies belonging to a department.

**Caveat: ambient vs. explicit account.** `TransitionService::transition()` gates on its explicit `$account` parameter, but `WorkflowStateGuard`/`WorkflowPointerMoveGuard` re-gate the service's OWN internal saves and pointer move against the ambient `AccountContextInterface` — the two are not the same account unless the caller keeps them in sync. Callers must set the ambient context to the acting account before calling `transition()` (the same pattern the API layer's `_account` request attribute follows, and the department-routing integration spine documents end-to-end). A mismatched ambient account — e.g. a queue worker that authorizes the explicit `$account` correctly but leaves a stale or null ambient context — can be denied mid-`transition()`, inside the guard, after the top-level permission/group gates already passed.

**Caveat: multi-edge shapes and denied-promotion residue.** The "permission before group" gate order is proven per-edge, not globally: a workflow with distinct constrained and unconstrained transitions both targeting `published` can let a first publish pass the save-path gates on one edge and then be pointer-guard-denied on the other (the never-published fallback state, see "Pointer-move guard" below) — reproducing the WP-2-documented "Denied-promotion residue" (see below) via a group-constraint mismatch rather than a permission one. Workflows that ship a single shared `publish` edge into `published` (the shipped `editorial` shape) are immune — there is only one edge's gate order to reason about.

**First-publish shape note.** A group-routed workflow **must** keep an initial-state → published edge — the shipped `editorial` shape's `publish: from: [draft, review]` — until the option-1 forward-draft follow-up fixes the pointer guard's never-published fallback (see "Deferred: forward drafts on the shipped workflow" above, "First-publish edge rule on review-required workflows"). A workflow whose `publish` is reachable ONLY via an intermediate state (no `draft → published` edge) wedges on first publish regardless of group constraints — that failure mode is orthogonal to WP-3 and pre-dates it. `DepartmentRoutingFlowTest`'s test-local `editorial_dept` workflow deliberately keeps `draft` in `publish`'s `from[]` for exactly this reason.

## Pointer-move guard (WP-2 task 2.5)

The save-path guard only observes `EntityRepository::save()` (via `EntityEvents::PRE_SAVE`). But `rollback()`, `setCurrentRevision()`, and `setPublishedRevision()` move the base-row pointer (or, for `rollback()`, copy a revision forward) WITHOUT a `doSave()` write, so a state change made through any of them bypassed workflow validation entirely. `Waaseyaa\EntityStorage\Event\BeforeRevisionPointerMoveEvent` (L1, dispatched by FQCN before any write on all six pointer-affecting methods, including the translation trio) is the choke point; `Waaseyaa\Workflows\Listener\WorkflowPointerMoveGuard` subscribes to it and validates the implied state change exactly like a transition (edge must exist; permission required only when an acting account context exists; a null context checks edge-legality only) — same reasoning as the save-path guard, applied to a different trigger.

- **Implied state change:** the target revision's `workflow_state` (read from the event's `revisionValues`, no second load) vs. the currently-effective state. For `publish`, that's the **published-pointer** revision's state (`fromRevisionId` is the prior `published_revision_id`); for `rollback`/`revert`, the **current-pointer** revision's state (`fromRevisionId` is the prior `revision_id`). `EntityRepository` already resolves the correct prior pointer per operation, so the guard reads it uniformly. No prior revision (never-published, or unresolvable) falls back to the workflow's initial state.
- **`translation_save` is a deliberate, unconditional pass-through.** Per "State lives on revisions" above, v1 `workflow_state` is tracked per revision, not per revision-translation — translations share their revision's state. A translation write carries translated field values only; it implies no `workflow_state` change, so there is nothing to validate. Kept consistent with the save-path guard, which is likewise translation-unaware today.
- **Bundle resolution:** the event carries only `entityTypeId` + `entityId`, not a bundle. The guard derives it from `revisionValues` using the entity type's own `bundle` key, mirroring `EntityBase::bundle()` (default bundle = entity type id when no bundle key/value exists) rather than loading the entity a second time.

**Adjacent gap closed in the same task (deliberate side-scope, not a refactor):** pointer moves previously invalidated no cache tags, and `rollback()` was invisible to audit (`PublishPointerAuditListener` only covers `setCurrentRevision()`/`setPublishedRevision()` via `RevisionPointerMovedEvent`, which `rollback()` never dispatches — that event is reserved for pointer moves WITHOUT a new revision). `EntityCacheSubscriber` now also invalidates on `RevisionPointerMovedEvent` and the legacy `EntityEvents::REVISION_REVERTED`. `Waaseyaa\Audit\Listener\RollbackAuditListener` gives rollback its own audit kind (`AuditEventKind::RevisionRollback`): it ARMS on `BeforeRevisionPointerMoveEvent` with `operation === 'rollback'` — dispatched pre-write by exactly one code path, `rollback()` itself, so unambiguous by construction — and consumes the armed slot on the following `REVISION_REVERTED` for the same entity. Every pointer operation's pre-event re-sets the slot (armed only for `rollback`, cleared otherwise), so an aborted rollback's stale arm cannot correlate with a later legitimate publish/revert, and an ordinary save followed by `setPublishedRevision()` of that same revision (the forward-draft publish flow) records nothing here. (An earlier `REVISION_CREATED` + `REVISION_REVERTED` identity-pairing design was rejected in review precisely because that flow made it fabricate rollback records.)

## Forward-draft mechanics (WP-2 task 2.6)

`TransitionService::transition()`'s **Apply** step (see "TransitionService — the one door" above) implements the two-pointer status semantics in full:

- **Every transition-service save forces a new revision** (`RevisionableInterface::setNewRevision(true)`/`RevisionableEntityInterface` duck-checked, mirroring the `#1654` pattern in `EntityRepository::doSave()`), regardless of the bundle's `new_revision` default (Task 2.3). A bundle opted out of automatic revisioning would otherwise save in place and clobber whatever revision happened to be loaded — frequently the published one — silently corrupting a forward draft.
- **Target state `default_revision: true`:** save the new revision (status untouched so far), then `EntityRepository::setPublishedRevision()` (may throw `TransitionDeniedException` — see the pointer-move guard below), then flip `status` to the state's `published` flag via a second, non-revision-creating save (`setNewRevision(false)`, so it updates the same tip in place). The order is deliberate: flipping `status` before the pointer move commits would leave the base row claiming a live state the pointer doesn't yet back, and a denied move must never leave `status` flipped with the pointer stuck.
- **Target state `default_revision: false` on an entity with an existing published pointer (forward draft):** the new tip carries the target state; `status` is copied from the *published* revision's own recorded `status` (not derived from the target state) so the otherwise-unavoidable base-row write — `EntityRepository::doSave()` writes whatever `status` sits on the entity into the base row on every save, with no special-casing for that column — is idempotent rather than a silent flip. The published pointer itself is never touched.
- **No published revision yet:** WP-1 behavior stands — `status` follows the target state's `published` flag directly.

**Gotcha found during implementation (verified empirically, not merely reasoned):** `EntityRepository::find()` hydrates the base row's `published_revision_id` into the generic values bag `toArray()` returns, even though that column has no field definition. An entity loaded *before* `setPublishedRevision()` runs therefore carries the *old* pointer value in memory; a subsequent `save()` on that same object — the status-flip follow-up above — would silently write the stale value back and undo the pointer move that just happened in the same `transition()` call. The fix: `TransitionService` explicitly re-asserts `$entity->set('published_revision_id', $newRevisionId)` immediately after a successful `setPublishedRevision()`, before the follow-up save. This is the same "dual-state" gotcha class CLAUDE.md's Architecture Gotchas section warns about (two sources of truth for one fact) — here the two sources are "what the entity object remembers" vs. "what the pointer move just wrote."

**`WorkflowStateGuard::applyState()` — status rides the pointer, uniformly** (amended by the task-2.6 adversarial panel): once an entity has a published pointer, the guard NEVER derives `status` from the state the save is entering — for ANY target, `default_revision: true` included. `status` is derived from the **published-pointer revision's own `workflow_state`** mapped through the workflow's `published` flag (decision 2's literal definition); a pointer revision whose state is unknown to the workflow (pre-backfill) falls back to copying its stored `status`. Deriving from the pointer's *state* rather than copying its stored *status column* is load-bearing: on `TransitionService`'s second (post-pointer-move, status-flip) save the pointer already sits on the just-promoted revision whose stored column is still pre-flip — the state-derived value agrees with the flip on both the publish (→ 1) and archive (→ 0) paths, where a stored-status copy would overwrite it. The earlier rule (guard derives from the target state for `default_revision: true` targets) defeated `TransitionService`'s deliberate ordering: the guard fires on the service's FIRST (revision-creating) save, so it committed `status = 1` in that save's transaction before the pointer move could be denied — a denial then left `status` flipped with the pointer stuck (the exact "status says live, pointer says otherwise" state the ordering exists to prevent). Never-published entities keep WP-1 status-follows-state. The guard still cannot move the pointer itself (PRE_SAVE fires before the new revision id exists); only `TransitionService` (or a direct, sanctioned repository call) does that.

**State-changing saves on pointered entities always create a revision** (panel finding B, made uniform by the verifier's residual finding): in the guard's state-changing-update path, ANY save that changes `workflow_state` on an entity with a published pointer forces `setNewRevision(true)` — regardless of the target state's `default_revision` flag — overriding the bundle opt-out (`NodeType new_revision: false` / entity-type `revisionDefault: false`) and even an explicit earlier `setNewRevision(false)`. Precedence: the bundle opt-out governs ordinary NON-state-changing edits only. Without the force, an opt-out bundle's state-changing raw save updates the CURRENT revision in place, and when that is the published revision, the new content and `workflow_state` are written into the very row the published pointer serves (live content corruption — originally scoping the force to `default_revision: false` targets left exactly this hole for raw saves into `archived`/`published`: one committed row with `workflow_state='archived'` AND the pointer-derived `status=1`).

**Consequence: raw saves never enact pointer moves.** A raw save into a `default_revision: true` state (`published`, `archived`) creates an unpromoted tip carrying that state while the pointer — and the pointer-derived `status` — stay truthful; enacting default-revision states (moving the pointer, flipping status) is exclusively `TransitionService`'s job. This makes raw-save-into-`archived` uniform with raw-save-into-`published`: both are validated (edge + permission) but produce only an unpromoted tip until the one door promotes it. The unconditional set is order-independent with respect to `NodeRevisionDefaultListener` (Task 2.3): that listener respects an already-set non-null value, so guard-first keeps `true`; node-listener-first sets `false`, which the guard then overrides.

**Denied-promotion residue (documented):** a `TransitionService` promotion whose pointer move is guard-denied has already committed its revision-creating save — the result is an orphan tip revision stamped with the target state that was never promoted. It carries the pointer-derived `status`, is invisible to the public read path (the pointer never moved), and a later successful transition supersedes it.

**Pointer-move guard reconciliation (carried from task 2.5's review, amended by task 2.6's own review).** `TransitionService` validates a forward draft's `publish` against the tip revision's real predecessor state (e.g. `review -> published`); `WorkflowPointerMoveGuard` only ever sees a before/after snapshot of the *published pointer itself*. The sanctioned two-step deliberately makes those two views agree at the moment the pointer moves: the service saves the `published`-stamped tip FIRST, then calls `setPublishedRevision()`, so the guard sees a **same-state** move (`published -> published`). The guard's rule is therefore two-branch:

1. **Same-state pointer move** (implied from-state === to-state, e.g. `published -> published` when promoting a forward draft, or rolling back to an earlier `published`-stamped revision): state-legal without an edge — the workflow *state* does not change, only which revision serves. Permission, when an acting account context exists: the account must satisfy **at least one transition targeting that state**, checked over ALL transitions into the state (any-of, not first-declared) — holding any legal way *into* a state is what authorizes controlling which of its revisions serves. As of WP-3, "satisfy" for each candidate transition means **permission AND satisfied group constraint** (a constraint-less candidate counts on permission alone, so pre-WP-3 workflows are unaffected). A null account context is allowed outright (edge-legality only, and there is no state change to check). This allowance applies uniformly to `publish`, `rollback`, and `revert` — Task 2.8's spine relies on rollback-to-a-published-revision succeeding with the publish permission (`published -> published` has no edge, so a strict-only rule would always deny it). A total failure of the any-of loop (every candidate fails, whether by permission, by group constraint, or by a mix) still reports `REASON_PERMISSION` — deliberate: the any-of loop was never granular about *why* it found nothing, only *that* it did, and WP-3 does not change that.
2. **Different-state pointer move**: the strict pre-2.6 rule, no exceptions — the `currentState -> newState` edge must exist in the workflow, and its own permission is required when an account context exists. No any-transition-into-state fallback: an earlier revision of task 2.6 relaxed the edge check for `publish` into `default_revision: true` targets, which **reopened the bypass on the shipped editorial workflow** — an account holding only `use editorial transition publish` could resurrect an old `published`-stamped revision by calling `setPublishedRevision()` directly while the pointer sat on `archived`, despite no `archived -> published` edge existing. Crossing states via a pointer move must be exactly as hard as crossing them via a transition.

The strict rule makes the archived-republish flow depend on a real edge: `restore` produces a forward draft whose published pointer still sits on the `archived` revision, so publishing that draft is an `archived -> published` different-state pointer move. The shipped editorial workflow satisfies it with the `restore_to_published` transition (see "Concepts and config schema" above) — the acting account needs that edge's permission for the final pointer move, in addition to `publish` for the transition itself. Custom workflows using `default_revision: true` states other than the publish target must likewise ship an edge from each such state into every state whose forward drafts should be promotable past it; the guard's denial message names the missing edge.

Same-state degenerate case (documented quirk): for a state with no incoming transitions at all, the same-state any-of permission check is a check over an empty set — an authenticated account is always denied, a null account context always allowed. No shipped workflow has such a state; fail-closed for authenticated actors is the intended default (design invariant 5).

## Default-revision discipline (CW-v1 option-1, #1920 PR-2 — as-built)

The forward-draft mechanics above describe the WP-2 substrate: a published pointer that tracks which revision is *default*, with the base row always holding the tip. PR-2 lands the option-1 rebuild the WP-2 rework deferred: **the base row holds the PUBLISHED revision, not the tip.** Storage mechanics (`RevisionableEntityTrait::setDefaultRevisionDiscipline()`, `EntityRepository::doSave()`/`setPublishedRevision()`/`rollback()` honoring the flag, `loadWorkingCopy()`) landed dormant in PR-1 (`docs/specs/revision-system-unified.md` §7); PR-2 is the workflows-layer wiring that makes them live.

- **Discipline is workflow-layer-decided, storage-mechanically-applied** (design §1). `WorkflowStateGuard::onPreSave()` sets `setDefaultRevisionDiscipline($pointered)` — an UNCONDITIONAL boolean, never set-on-true-only — on every guarded save of a bound entity, where `$pointered` = a live `published_revision_id` on the base row. `WorkflowPointerMoveGuard::onBeforePointerMove()` sets the analogous `BeforeRevisionPointerMoveEvent::applyDefaultRevisionSemantics()` flag: always for `publish`; for `rollback`, only when a published pointer already exists. **Two-axis (revisionable + translatable) entity types cannot be bound at all** — `WorkflowBindingResolver::resolve()` hard-throws (mirroring its existing non-revisionable throw), and the same check runs at `WorkflowAssignmentsValidator` (packages/workflows/src/Validation/WorkflowAssignmentsValidator.php) for the config-import surface once one exists to call it — see the note at the end of this section. Per-translation workflow state remains a documented post-v1 stage.
- **`WorkflowStateGuard::guardUpdate()`'s original-state basis moves to the working copy** (`EntityRepositoryInterface::loadWorkingCopy()`, mechanically safe on any entity — undisciplined ones have latest === base pointer, so it degenerates to `find()`). Without this, every disciplined draft edit would re-validate as `published → draft` against the still-published base row.
- **Same-state republish, the named behavior change (design §3.1, verifier finding 1; rule corrected by the PR-2 fix wave):** **every** disciplined same-state save whose state is `default_revision: true` (published AND archived, uniformly) — revision-creating or in-place — requires, at PRE_SAVE, the same any-of authorization (permission AND group constraint of at least one transition INTO the state; null account context passes) `WorkflowPointerMoveGuard`'s same-state branch already used for pointer moves. **This is the headline invariant-5 change: a plain content edit of already-served (default-revision) content now requires workflow authorization, because under discipline changing what serves IS publishing.** The as-first-landed rule gated only revision-creating saves; the fix wave made it unconditional after adversarial review found the hole on `new_revision: false` bundles: an in-place save of the published tip reaches the SERVED base row directly (storage `writeBase` rule), and in the `NodeRevisionDefaultListener`-first PRE_SAVE order (the production order) the earlier gate short-circuited before the auth check — an account with plain entity update access edited live content unchecked. The unconditional gate correctly also covers `TransitionService`'s own second (status-flip) save and sanctioned in-place published edits — both pass, because the acting account holds the fired transition's permission (a transition INTO the target state) or the context is null. ARMING and promotion apply **only when a new revision was created**: on authorization of a revision-creating save the guard ARMS a per-save marker (`Waaseyaa\Workflows\Republish\RepublishMarker`, a `\WeakMap` keyed on the entity object — arm-at-PRE_SAVE / consume-at-POST_SAVE, never re-derived at POST_SAVE, because the POST_SAVE event's `originalEntity` is the base row and would misclassify `TransitionService`'s promote-branch first save as same-state); `Waaseyaa\Workflows\Listener\WorkflowRepublishListener` (POST_SAVE) consumes the marker and promotes the just-saved tip via `setPublishedRevision()` — the pointer guard re-validates the same rule. **The promotion self-skips when the base row's live `published_revision_id` already equals the saved entity's revision id** (one cheap `find()` read): a spurious arm is possible in the guard-first listener order (the guard's `willCreateRevision()` runs before the bundle opt-out is applied), and promoting the already-served revision would re-fire the pointer-move event/audit/reindex chain for a no-op — the self-skip makes the arm/consume pair harmless in every PRE_SAVE listener order. The guard additionally CLEARS any stale arm for the entity object unconditionally at the start of every guarded save (mirroring the unconditional discipline-flag reset), so a PRE_SAVE-aborted save can never leave an arm a later save of the same object consumes. A same-state save into a `default_revision: false` state (a draft edit) stays revision-only, ungated — that is the forward-draft case itself.
- **Doctrine inversion, named (finding A3):** "raw saves never enact pointer moves" becomes **"raw saves never enact STATE-CHANGING pointer moves; an authorized same-state edit of a default-revision state re-publishes through the `setPublishedRevision()` choke point."** The WP-2 residue text above ("Consequence: raw saves never enact pointer moves") is superseded by this sentence for disciplined entities; it remains literally true for undisciplined ones (Playbook-H-shaped rows) and for state-changing saves on any entity.
- **`TransitionService::transition()`'s working-copy basis and deterministic content rule** (design §3.2, verifier findings 4/A4): the service loads the working copy itself and resolves `fromState` from it — not from the passed object, which may be a stale `find()`-loaded snapshot under discipline. Content rule: the passed entity's content rides the transition only when its revision id equals the working copy's; otherwise the service throws `RevisionConflictException` (the same house payload the optimistic-locking contract uses: `entityTypeId`, `entityId`, `expectedRevisionId` = the passed object's, `currentRevisionId` = the working copy's) rather than silently discarding or promoting stale content. The promote branch's first save and the forward-draft branch's save are revision-only via the guard's discipline flag, exactly as PR-1's storage mechanics describe — `TransitionService` does not re-implement that, it inherits it.
- **`WorkflowPointerMoveGuard`'s revert denial (design §2.3):** `setCurrentRevision()` (the `revert` operation) on a bound entity with a live published pointer is now DENIED outright — before the pre-existing same-state/different-state edge logic runs — with a message directing callers to `rollback` (restore into the working copy) or the transition path. A direct base-row repoint has no coherent meaning once the base row belongs to the published pointer. Unbound or never-published (unpointered) entities are unaffected. (The `fromRevisionId === null` pointer-establishment rule — design §6 — is untouched by PR-2; a later PR owns it.)
- **Rollback becomes draft-restore under discipline (design §2.3):** `rollback()` on a disciplined entity writes the restored content as a NEW TIP REVISION ONLY — the base row (still serving whatever the published pointer points at) is untouched. This is a CONSCIOUS INVERSION of the pre-option-1 assertion ("the base row carries the tip/restored content") the WP-2-era `ForwardDraftFlowTest` pinned — restoring old content into the working copy is a draft operation; it goes live via the normal promotion path, exactly like any other forward draft.
- **Read-side re-sourcing (design §3.3):** `SearchIndexSubscriber` and `EntityEmbeddingListener` re-load the entity via `repository->find()` (the served base row) at POST_SAVE, `RevisionPointerMovedEvent`, and the legacy `EntityEvents::REVISION_REVERTED`, instead of indexing the in-memory saved/reverted entity. This closes the previously-documented de-index bug (editing a published node into a forward draft used to delete its embedding, because `WorkflowVisibility` was evaluated against the tip's `workflow_state='draft'`) WITHOUT the previously-sketched `WorkflowVisibility` precedence flip — see "Visibility (read side)" under Integration, updated below.
- **Exception mapping on newly-reachable surfaces (finding A2):** `TransitionDeniedException` (403 permission / 422 other) and `RevisionConflictException` (409) are now mapped on `FieldAutoSaveController`, GraphQL `resolveCreate()`/`resolveUpdate()` (as a `GraphQL\Error\UserError`, the client-safe exception type — an unmapped `TransitionDeniedException` would otherwise be masked by webonyx/graphql-php as a generic "Internal server error"), and `WorkflowTransitionController`'s POST (`RevisionConflictException` → 409, mirroring JSON:API's `REVISION_CONFLICT` mapping). `GenericAdminSurfaceHost` create/update needed no code change — it delegates entirely to `JsonApiController::store()`/`update()`, which already mapped both exceptions before PR-2 (pinned by a dedicated regression test, not a behavior change).
- **Config-import validation, a documented gap:** `WorkflowAssignmentsValidator` (packages/workflows/src/Validation/WorkflowAssignmentsValidator.php) provides the same two structural checks (non-revisionable, revisionable+translatable) as pure functions over the raw `workflows.assignments` array, ready for a config-import surface to call — but **no such surface exists yet**: `ConfigImporter` has no wired domain-validation hook for this config item (it is plain settings-shaped config, not one of the `entity_type.entity_id` files the DAG-apply pipeline drives through `ConfigImportApplyHookInterface`). The "Binding requires... rejected at config-import validation otherwise" line above and the "Config validation tests" bullet under Testing requirements describe the RESOLVER's runtime enforcement (first `resolve()` call, lazily) as the only enforcement that actually runs in a booted install today; wiring an actual import-time call is tracked as a workflows follow-up.

**Regression discipline:** an unbound-and-unpointered (or bound-but-never-published) entity's save/rollback/setCurrentRevision/setPublishedRevision path is BYTE-IDENTICAL to pre-option-1 behavior — the discipline flag is false, storage's `disciplined` gate is false, every branch above is a no-op. `EntityRepositoryPublishedRevisionTest` (entity-storage) pins the unflagged `setPublishedRevision()` shape and stays untouched by PR-2. The rewritten `ForwardDraftFlowTest` (below) is the option-1 integration spine; `ImportSaveContextGuardTest` gains an update-path adjacency case (an authenticated-context import UPDATE of an already-published bound row without any-of authorization is newly denied; a null-context import UPDATE still passes and now also promotes through the choke point — outcome-equivalent to a pre-option-1 import's direct base-row write).

## Deferred: forward drafts on the shipped workflow (WP-2 rework)

The final whole-branch review (`.superpowers/sdd/final-review-findings.md`) found the forward-draft mechanic, as exposed on the shipped `editorial` workflow, unshippable as-is. The human chose **option 2**: ship the safe substrate now (node revisionable opt-in + migration, the `BeforeRevisionPointerMoveEvent` choke point + `WorkflowPointerMoveGuard`, `workflows:backfill-state`, cache/audit listeners, `restore_to_published`, and the `TransitionService`/`WorkflowStateGuard` engine semantics described above — all of it live, dormant substrate) and defer forward drafts to a later follow-up (**option 1**: true default-revision semantics, where the base row keeps serving the published revision and drafts live only in revision rows). `DefaultWorkflows::EDITORIAL` no longer ships the `revise` (published → draft) edge; the mechanic remains reachable via custom workflows that define their own such edge, and via the archived → restore → publish round trip (unpublished throughout — see `restore_to_published` above).

Findings folded into this rework as contained fixes (not deferred): the published-pointer establishment gap (backfill now establishes `published_revision_id`), the upgrade top-up gap (the boot seed additively tops up a persisted `editorial`), the `TransitionDeniedException` → JSON:API HTTP mapping gap, the prune/delete published-pointer immortality gap, this runbook's ordering hazard (`operations-playbooks.md` Playbook H, failure mode 3), and — from the final-review fix wave — the rollback/`setCurrentRevision()` stale-snapshot writeback (see below, now fixed rather than deferred).

Findings the option-1 follow-up owns, by theme:

- **Read-side pointer awareness — ENGINE HALF CLOSED by #1920 PR-2 (see "Default-revision discipline" above); SURFACE HALF still open (PR-3).** The original finding: no reader (`find()`, JSON:API serialization, SSR, search indexing) is pointer-aware, so a forward draft's tip content is disclosed publicly during the review window. PR-2 makes `find()` itself pointer-aware BY CONSTRUCTION for every disciplined entity (the base row IS the published revision — nothing to patch per reader) and re-sources the two indexer listeners (`SearchIndexSubscriber`, `EntityEmbeddingListener`) so their POST_SAVE/pointer-move re-indexing reads served content, not the in-memory tip. What remains (PR-3, design §4): JSON:API PATCH/GET-with-`?workingCopy=1` targeting the working copy, `GenericAdminSurfaceHost` edit-surface working-copy targeting, SSR preview, `FieldAutoSaveController`/GraphQL `resolveUpdate` working-copy targeting, and the admin SPA wiring — none of these are read-path *disclosure* risks (the engine-level fix already closes that), they are write-target/editor-UX correctness work.
- **Write-side field allowlist / pointer-column write hole — CLOSED (CW-v1 option-1 PR-4, #1920).** ~~The JSON:API write path applies every submitted attribute with only per-field access as the gate — no allowlist restricts writes to declared, non-bookkeeping fields. Neither `published_revision_id` nor `revision_id` is covered by any shipped field-access policy, so an account with plain entity `update` access can move the published pointer (or forge the current-revision id) directly through a PATCH body, bypassing `WorkflowPointerMoveGuard` and every transition permission entirely. Reachable today via the documented evaluation-binding path (`operations-playbooks.md` Playbook H step 5) — production is unaffected because production does not bind.~~ A shared `Waaseyaa\Entity\Write\EntityWritePayloadGuard` now runs at `JsonApiController::store()`/`update()` (and, via delegation, `GenericAdminSurfaceHost`; and, defense-in-depth, GraphQL's `EntityResolver::resolveCreate()`/`resolveUpdate()`), rejecting (422, `code: FIELD_NOT_WRITABLE`) any payload key that is not a declared field or writable entity key, or that is an identity/bookkeeping column (`revision_id`, `published_revision_id`, ...) regardless of declaration — reject, never strip. On `update()` this is echo-tolerant (PR-4 rework, `docs/specs/api-layer.md` "Echo-tolerant rejection on update()"): a submitted identity/bookkeeping key is refused only when its value DIFFERS from the entity's current stored value, so a read-modify-write client's own round trip of a value it legitimately read (FR-008) is not itself refused. `FieldAutoSaveController` was verified already-safe (declared-field-allowlisted). Full contract: `docs/specs/api-layer.md` "Write-side field allowlist (CW-v1 option-1 PR-4)". The Playbook H evaluation-binding caveat this bullet referenced is likewise closed; the "First-publish edge rule" bullet below remains open.
- **First-publish edge rule on review-required workflows.** The pointer guard's never-published fallback (initial state) plus its strict different-state rule means any workflow whose `publish` is reachable only via an intermediate state (e.g. `draft → review → published`, the review-required shape CW-v1's department-routing use case is built for, with no `draft → published` edge) permanently wedges on first publish: the guard denies the pointer move after the revision-creating save already committed `status=1` with no published pointer — a residue the spec's "denied moves never leave `status` lying" invariant does not actually prevent for never-published entities.

**Fixed (final-review fix wave, no longer deferred): rollback / `setCurrentRevision()` stale snapshot writeback.** Revision rows snapshot the whole entity values bag, including `published_revision_id` and `status` folded into the revision's `_data` blob. `rollback()` and `setCurrentRevision()` used to write that whole snapshot back to the base row, silently moving the published pointer (or desyncing `status` from the live state) with no pointer-move validation, no audit entry, and no event distinguishing it from a legitimate transition. Both methods now overwrite `published_revision_id`/`status` in the outgoing row with the LIVE base row's values (read once, before the pre-write event) rather than the target revision's frozen ones — restoring CONTENT only, never the pointer or status, per the invariant that moving the pointer/flipping status is exclusively `TransitionService`'s job (CW-v1 decision 2). A base row/legacy schema lacking either column is tolerated exactly as before (the key is simply unset, not defaulted).

None of this is re-litigated here — see `.superpowers/sdd/wp2-rework-plan.md` and `.superpowers/sdd/final-review-findings.md` for the full analysis and evidence.

## Integration

- **Audit (L3 → L1, downward):** `TransitionService` writes transition entries (who, entity/revision, from → to, timestamp) through the audit package's public API. Deliberately *not* implemented as an audit-side subscriber to a workflows event — that would be an upward type import requiring a `KERNEL_EXEMPT_FILES` entry.
- **Notifications (L3 → L3):** the notification package (or app code) subscribes to `WorkflowTransitionEvent`. The framework ships the event surface; recipient routing is app configuration.
- **Visibility (read side) — CLOSED by #1920 PR-2, WITHOUT the previously-sketched precedence flip.** The WP-2-era finding: `WorkflowVisibility::nodeState()` trusts a raw `workflow_state` value over `status` whenever both are present on the values map it is handed, which was correct pre-WP-2 (tip and published-facing state were always the same row) but wrong for a forward draft's in-memory tip (`workflow_state='draft'` while `status` stays correctly pointer-derived at `1`) — concretely reproduced via `Waaseyaa\AI\Vector\EntityEmbeddingListener::onPostSave()` de-indexing a still-live node. The WP-2-era plan sketched fixing this by flipping `WorkflowVisibility`'s precedence (trust `status` over `workflow_state`), which would have touched a pinned unit test and at least six consumer packages that each construct `WorkflowVisibility` inline. **PR-2 retires that plan.** The actual fix (design §3.3) re-sources both `SearchIndexSubscriber` and `EntityEmbeddingListener` from `repository->find()` (the served base row) at POST_SAVE and on `RevisionPointerMovedEvent`/`REVISION_REVERTED`, instead of indexing the in-memory tip/reverted-revision object directly — a draft save then re-indexes the (unchanged) published content, and `isNodePublicForEntity()` evaluates against served `workflow_state`/`status`, which agree by construction. `WorkflowVisibility`/`WorkflowVisibilityFilter`/`EditorialVisibilityResolver`'s existing precedence and `WorkflowVisibilityTest::nodeVisibilityRespectsWorkflowStateFirst()` are UNTOUCHED — the flip is unnecessary once every consumer is fed served content, and it was independently flagged as leak-prone in the final review's refuted-findings.
- **API (WP-4, landed as-built):** `POST /api/{type}/{id}/workflow/transition` (body `{ transition: "publish" }`) and `GET /api/{type}/{id}/workflow/transitions` (available transitions for `_account` + `meta.workflow_state`), per entity type, `requireAuthentication()`, `Waaseyaa\Api\Controller\WorkflowTransitionController` dispatched by `WorkflowTransitionApiRouter`, registered only when `TransitionService` resolves (no-workflows installs 404 naturally). **Deviation from the original sketch:** view access is enforced **in the controller, not via a route `_gate` option** — the R8 oracle standard requires a view-denied entity to return the same canonical 404 document, byte-identical, as a missing one (one private factory, both branches; fail-closed 404 when no `EntityAccessHandler` is wired), and a route-option gate's 403 would break that. `TransitionDeniedException` keeps the WP-2 HTTP contract (`permission` → 403, every other reason → 422, `code: WORKFLOW_TRANSITION_DENIED`, `meta.reason`). The multi-edge denied-promotion residue caveat applies verbatim through this endpoint: a POST can 422 from the pointer guard after its revision-creating save committed (orphan tip, documented above). Raw `PATCH` of `workflow_state` stays legal-but-guarded (see save-path guard) for parity with generic clients. Full endpoint contract: `docs/specs/api-layer.md` "Workflow Transition Endpoints (CW-v1 WP-4)".

## Design invariants (why it looks like this)

1. **One door.** Every state change flows through `TransitionService` validation — the service directly, or the save-path guard proving equivalence. The predecessor died precisely because enforcement was optional.
2. **Definitions are data.** No preset-in-code as the canonical definition.
3. **Revision-aware from day one.** Retrofitting revisions under a state-on-entity engine is a redesign; shipping revision-aware with staged delivery is not.
4. **Nothing generalizes from `node`.** The engine addresses entity type + bundle via bindings; `node` is just the first bound type (WP-2).
5. **Fail closed, deny loudly.** Typed denial exceptions with machine-readable reasons; no silent no-ops, no fail-open defaults.
