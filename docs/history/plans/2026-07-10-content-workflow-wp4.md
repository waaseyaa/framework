# CW-v1 WP-4 Implementation Plan — workflow transition API + admin SPA transition UI + membership write tooling

**Goal:** Make the CW-v1 engine reachable by users: `GET /api/{type}/{id}/workflow/transitions` + `POST /api/{type}/{id}/workflow/transition` (surface-enforced entity view access, R8 oracle standard), transition buttons + state badge in the admin SPA, and a minimal membership write surface (service methods + CLI) so department routing is operable end-to-end.

**Anchor:** #1920. **Baseline:** `origin/main` @ 2f46b8a51 (WP-3 merged, #1955).

## Scope call (re-anchored 2026-07-10)

Membership write-side tooling is **in WP-4**: the group constraint is fail-closed (no `group_content` row ⇒ every constrained transition denied), so the transition UI is inoperable for the client story without a sanctioned way to create departments, memberships, and content assignments. Minimal shape only: write methods on the existing `GroupMembershipService` + `groups:*` CLI commands. Explicitly NOT in WP-4 (follow-ups): un-parking the `group` JSON:API access PARK (#1871 owns that decision), admin SPA membership-management UI, temporal-window (`start_date`/`end_date`) evaluation, wiring `RelationshipPreSaveListener` into production boot (pre-existing gap, discovered during WP-4 scoping).

## Design decisions (locked)

1. **Routes are registered per entity type** (literal `/api/{$entityTypeId}/...` segments + `->default('_entity_type', $id)`), mirroring `JsonApiRouteProvider::registerFieldAutoSave()`. Both routes `->requireAuthentication()`. Registered ONLY when `TransitionService` resolves (core-only installs without `waaseyaa/workflows` get natural 404s; `ci/core-only-boot` stays green).
2. **View access is enforced in the controller, not via `_gate`** (deviation from the spec's original sketch, recorded in the spec update): the R8 oracle standard requires a view-denied entity to be **byte-identical** to a missing one (same 404 document from one private factory, per `JsonApiController::show()`), which a route-option gate's 403 would violate. Both endpoints: load by id/uuid → not found ⇒ canonical 404; `EntityAccessHandler::check($entity, 'view', $account)` not allowed ⇒ the SAME canonical 404. Deny-by-default (`!isAllowed()`, Neutral = denied).
3. **`TransitionDeniedException` mapping is the WP-2 contract, reused verbatim** on POST: `REASON_PERMISSION` → 403, everything else (`illegal_edge`, `unknown_transition`, `unbound`, `group_constraint`) → 422; JSON:API error `code: WORKFLOW_TRANSITION_DENIED`, `meta: {reason}` (policy of `JsonApiController::workflowTransitionDeniedError()`, which stays private — the new controller carries its own copy of the tiny mapping).
4. **Ambient-vs-explicit account (WP-3 caveat carried):** the controller passes `_account` explicitly to `TransitionService`; the ambient `AccountContextInterface` used by `WorkflowStateGuard`/`WorkflowPointerMoveGuard` during the service's internal saves is already synced by `SessionMiddleware` for every HTTP request (outermost scope, unconditional set). The integration test pins the synced path; the spec documents that non-HTTP callers must sync manually.
5. **Response shapes** (the SPA builds against these):
   - GET 200: `{"data": [{"id","label","to"}...], "meta": {"workflow_state": "<current>"}}` — data only ever lists what `getAvailableTransitions()` returns (the one sanctioned UI read side; group- and permission-filtered). Unbound entity type: 200 with empty `data` (no buttons is the correct UI), `meta.workflow_state` omitted or null.
   - POST 200: `{"data": {"transition","from","to"}}` from `TransitionResult`. Malformed/missing `transition` body member → 400.
6. **Membership writes are idempotent and soft-revoke-aware:** `addMember`/`assignContent` reactivate an existing `status=0` row (or no-op on a live row) instead of inserting duplicates; `removeMember`/`unassignContent` soft-revoke (`status=0`), never delete. Writes validate the target group exists (loud failure beats dangling edges); lookups stay system-context (`accessCheck(false)`), consistent with the read side.
7. **CLI tooling lives in `packages/cli`** (`Handler/` + `Provider/GroupsCliServiceProvider`), following the `WorkflowsBackfillStateHandler` precedent: `groups:create <type> <name>` (ensures the `group_type` config entity exists), `groups:member-add <uid> <group>`, `groups:member-remove <uid> <group>`, `groups:content-assign <entity_type> <id> <group>`, `groups:content-unassign <entity_type> <id> <group>`.
8. **SPA:** new `useWorkflowTransitions` composable over `useApi().apiFetch` (never raw `$fetch`); new `components/workflow/TransitionControls.vue` referenced as `<WorkflowTransitionControls>` (nested-dir prefix — populated-path test required) on `pages/[entityType]/[id].vue`; `workflow_state` badge (status-pill pattern) in `SchemaList.vue`. Errors surface `err.data?.errors?.[0]?.detail`. i18n keys added to BOTH `en.json` and `fr.json`. `bin/build-admin-dist` rebuild committed with `dist/` + `dist.signature` (blocking `check-admin-dist-fresh` gate).
9. **Multi-edge denied-promotion residue (WP-3 caveat carried):** a POSTed transition can be denied by the pointer guard AFTER its revision-creating save committed (422 with the guard's reason; orphan tip revision as documented in the spec). The endpoint does not try to hide or roll this back — it is engine-documented behavior; the spec's API section cross-references it.

## Global constraints

Everything from the WP-2 plan's Global Constraints verbatim (strict_types, `final`, PHPUnit 10.5 attributes / no `-v`, Waaseyaa `LoggerInterface`, getquery-bindings gate, layer rules — `api` L4 → `workflows` L3 is downward and fine; `groups` stays L2 with no `access` dependency). Changelog `[Unreleased]` entry in this PR; commit-trailer `spec-reviewed:` acks; PR title carries `#1920`, body `Part of #1920`. Unit suite needs `-d memory_limit=1G`. `git stash` is forbidden. Retired M4A controllers (`WorkflowDryRunController`, `WorkflowGuardsController`) are WP-5 deletion targets — copy the wiring pattern, never extend them.
