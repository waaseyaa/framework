## Why this mission exists

Today Waaseyaa's OCAP substrate (`packages/access` — `AccessChecker`, `AccessPolicyInterface`, `FieldAccessPolicyInterface`, the route-options pipeline) governs **human** HTTP requests through `AuthorizationMiddleware` and `EntityAccessHandler`. It does **not** govern:

1. **Agent tool execution.** `AgentToolInterface::execute(array $arguments, AccountInterface $account)` (see `packages/ai-tools/src/AgentToolInterface.php`) currently receives the account but the framework provides no first-class `AccessChecker` handle — every tool implementer is on the honour system to do per-record checks. The four shipped bimaaji tools (`IntrospectGraphTool`, `IntrospectSectionTool`, `SearchSpecsTool`, `ProposeMutationTool` under `packages/ai-agent/src/Tool/Bimaaji/`) read application metadata and so today are not data-leaking; but the first governed-data tool (Drive search, Doc draft, etc. — gap-matrix E1, plan item #14) cannot land safely until the boundary is OCAP-by-architecture, not OCAP-by-convention.
2. **MCP serializer responses.** The `mcp` endpoint (`packages/mcp/src/`) returns entity-shaped payloads to external AI clients via JSON-RPC 2.0. The entity-to-MCP-response shaping in `packages/mcp/src/Tools/EntityTools.php` does **not** consult `FieldAccessPolicyInterface`. An MCP caller therefore receives more data than the same caller would receive through JSON:API (`ResourceSerializer` paired with `EntityAccessHandler` field-access checks per the JSON:API serializer). This is the silent governance gap A5 calls out.
3. **Per-file AI access.** `packages/media` and `packages/attachment` entities have no first-class "AI accessible" toggle. The framework cannot today express "this PDF is open to humans with the right role but never to any AI tool, regardless of capability."

Per gap-matrix row A5: *"Capability gating at the tool boundary is wired; **no data-level access check inside any shipped tool today** — the five bimaaji tools read application metadata, not user data. MCP serializer does not call `FieldAccessPolicyInterface`."* Per alpha-to-beta-plan §2 item #1: *"Inject `AccessChecker` and `_account` into every `AgentToolInterface::execute()`. Wire `FieldAccessPolicyInterface` into the MCP serializer. Add a per-file AI-access toggle field to media/attachment. This is the flagship governance integration — small code change, defining product claim."* Per assumptions.md §2: *"When the per-record AI access flagship (gap-matrix A5) is wired, Waaseyaa becomes the only framework exposing its own governance graph to external AI clients via MCP with per-record + per-field controls built in."*

This mission is the smallest integration that makes Waaseyaa's defining product claim true in code, not just in spec.

## Layer architecture interaction

This mission cross-cuts **Layers 1, 5, 6** per the CLAUDE.md layer table. No upward-import violation is introduced; the wiring direction is always downward or same-layer:

- **WP01** edits L5 (`ai-tools`, `ai-agent`) and L1 (`access`). `ai-tools` already declares an L1 dependency (`use Waaseyaa\Access\AccountInterface;`) so adding an `AccessChecker` parameter to `AgentToolInterface::execute()` is a same-direction edge expansion, not a new layer relationship. `bin/check-package-layers` MUST stay green.
- **WP02** edits L6 (`mcp`) which already depends on L1 (`access`) and L1/L2 (`entity`, `field`). Wiring `FieldAccessPolicyInterface` into `EntityTools` is a same-direction edge.
- **WP03** edits L2 (`media`, `attachment`) and L6 (`admin`). The new field type lives in `packages/field/src/FieldType/AiAccessibleField.php` (L1) so `media` and `attachment` consume it via existing same-direction edges. Admin SPA UI lands as a renderer registration.

The CodifiedContext three-tier pattern (read contract in the lower layer, adapter binding in the higher layer, service-provider resolution at boot) is applicable where a tool implementation needs an out-of-package collaborator (e.g. WP02's MCP serializer needs `FieldAccessPolicyInterface` resolution; the policy classes live in consumer applications, not in `packages/mcp`). The serializer accepts the policy collection via constructor injection bound by `McpServiceProvider`, mirroring how `EntityAccessHandler` already receives field-policy implementations.

## Scope

### In scope

**WP01 — AI tool boundary OCAP injection (L5 + L1):**
- Extend `AgentToolInterface::execute()` so every implementation receives a framework-supplied `AccessChecker` capable of `entityAccess()` and `fieldAccess()` checks against any entity touched during execution. The signature change is the implementer's choice (see "Decisions deferred"): either a new third parameter `AccessCheckerInterface $accessChecker`, or a new `AgentToolContext` DTO bundling `AccountInterface`, `AccessCheckerInterface`, and a per-call audit handle.
- A new `#[Capability(governed_data: false)]` PHPDoc / PHP attribute marker (or attribute parameter on the existing `#[AsAgentTool]`) allows application-metadata-only tools to opt out of mandatory `AccessChecker` use. Tools without the marker MUST consult `AccessChecker` per record touched; reviewers gate on this.
- Audit lineage: every `AccessChecker` call inside a tool MUST be recorded against the agent run via existing `AgentAuditLog` plumbing (`packages/ai-agent/src/Entity/AgentAuditLog.php`), preserving DIR-004's "OCAP audit lineage takes priority" rule.
- Tool registry (`packages/ai-tools/src/Catalogue/AttributeToolRegistry.php`) + agent runtime (`packages/ai-agent/src/AgentExecutor.php`) updated to construct and propagate the new context to each `execute()` call.
- All built-in tools updated: `packages/ai-tools/src/Entity/{EntityCreateTool,EntityReadTool,EntityUpdateTool,EntitySearchTool,EntityDeleteTool,EntityListTool}.php`, `packages/ai-tools/src/Relationship/RelationshipTraverseTool.php`, `packages/ai-tools/src/Vector/VectorSearchTool.php`, and the four bimaaji tools at `packages/ai-agent/src/Tool/Bimaaji/{IntrospectGraphTool,IntrospectSectionTool,SearchSpecsTool,ProposeMutationTool}.php`. Each tool either consumes the new checker (data-touching tools) or carries the `governed_data: false` marker (metadata-only tools).
- A **WP01 boundary integration test** seeds two accounts with divergent entity access (one allowed, one denied) and asserts the same `EntityReadTool::execute()` returns the entity for the allowed account and a structured access-denied result for the denied account. This is the dead-code-in-production guard for FR-001 / FR-002.

**WP02 — MCP serializer field-access wiring (L6 + L1):**
- Wire `FieldAccessPolicyInterface` lookups into the MCP entity serializer at `packages/mcp/src/Tools/EntityTools.php` (and any sibling entity-shaping site under `packages/mcp/src/`). The serializer MUST consult a per-entity-type field policy via `EntityAccessHandler` (the same collaborator JSON:API uses), passing the resolved `_account` from the MCP request.
- Open-by-default semantics: `AccessResult::neutral()` → field exposed; `AccessResult::allowed()` → field exposed; `AccessResult::forbidden()` → field redacted. This mirrors `docs/specs/field-access.md` exactly.
- Redaction shape: a forbidden field MUST be replaced by the literal `{accessRestricted: true, reason: "field_forbidden_for_account"}` object in place of the value, NOT a 403 on the whole entity response. This preserves response shape for partial-disclosure scenarios (DIR-004 §3 audit lineage requirement: the caller MUST know that something was redacted, never silently absent).
- `McpServiceProvider` binds the wiring so that MCP requests resolve the same `EntityAccessHandler` + `FieldAccessPolicyInterface` set as JSON:API. No second policy registry.
- A **WP02 parity integration test** asserts that for an account with a `FieldAccessPolicy` returning `forbidden` on field `body` of a `node` entity, the MCP `entity.read` response replaces `attributes.body` with the redaction marker AND the JSON:API `GET /api/node/{id}` response for the same account omits `attributes.body`. The two surfaces MUST agree on which fields are reachable.

**WP03 — Per-file AI-access toggle field (L1 + L2 + L6):**
- New field type `Waaseyaa\Field\FieldType\AiAccessibleField` at `packages/field/src/FieldType/AiAccessibleField.php`. Persisted values: `'yes'`, `'no'`, `'inherit'`. Default = `'inherit'`.
- Field added to media and attachment entity registration: `packages/media/src/Entity/Media.php` (`fieldDefinitions`) + `packages/attachment/src/Entity/Attachment.php`. Field key: `ai_accessible`.
- Storage migration: `packages/media/migrations/<timestamp>_add_ai_accessible_to_media.php` + sibling under `packages/attachment/migrations/`. SQLite + MySQL + PostgreSQL covered by the framework's `SqlSchemaHandler` two-axis driver (no manual DDL).
- `AccessChecker` integration: a new `AiAccessibilityPolicy` at `packages/access/src/Policy/AiAccessibilityPolicy.php` carrying `#[PolicyAttribute(entityType: 'media')]` + `#[PolicyAttribute(entityType: 'attachment')]`. The policy implements both `AccessPolicyInterface` and `FieldAccessPolicyInterface` (intersection-type pattern per CLAUDE.md). When `ai_accessible = 'no'` AND the account is operating inside an agent run (detected via a new `AccountInterface::isAgentInitiated()` helper or via a per-request flag — implementer chooses; see "Decisions deferred"), the policy returns `AccessResult::forbidden()`. `'inherit'` defers to entity-level classification (M-A4 will populate this; until then `'inherit'` resolves to `'yes'` to preserve current behaviour).
- Admin SPA toggle: `packages/admin/app/components/media/AiAccessibleToggle.vue` + i18n keys in `packages/admin/app/i18n/en.json`. Surface on media + attachment edit forms.
- A **WP03 toggle integration test** seeds a media entity with `ai_accessible = 'no'`, exercises `EntityReadTool::execute()` with an agent-initiated account, asserts forbidden; flips the toggle to `'yes'`, re-runs, asserts allowed. Confirms the toggle is enforced end-to-end through the tool boundary wiring from WP01.

## Risks

- **R1 — Dead code in production (primary).** A tool boundary that ships an `AccessChecker` parameter but in practice is never invoked by individual tool implementations silently restores the pre-mission behaviour. **Mitigation:** the three per-WP integration tests (FR-004, FR-007, FR-011) are mandatory and MUST be designed to fail when the wiring is removed. Reviewer focus item (a) below codifies the verification.
- **R2 — Layer violation via attribute scanning.** Foundation (L0) attribute discovery already references attribute class names as strings to avoid upward imports (CLAUDE.md "Layer discipline for imports" gotcha). The new `#[Capability]` marker MUST follow the same pattern: foundation discovers it by string FQCN, not by `::class`. **Mitigation:** the implementer enumerates the attribute's FQCN-as-string handling site and the reviewer grep's for any `\\AI\\Tools\\Attribute\\Capability::class` in `packages/foundation/src`.
- **R3 — JSON:API / MCP field-set drift.** WP02's parity test only proves agreement at one entity type today; future entity-type additions could drift the two surfaces. **Mitigation:** the parity test is parameterised over the registered entity-type set, so any new type that introduces a `FieldAccessPolicy` automatically exercises both surfaces. Documented in `docs/specs/field-access.md` "MCP parity" section.
- **R4 — Agent-initiation detection ambiguity.** The `'no'` AI-access toggle relies on a way to know "this request is happening inside an agent run." Two viable mechanisms: (a) extend `AccountInterface` with `isAgentInitiated(): bool`; (b) carry a request-scope `_agent_run_id` attribute populated by `AgentExecutor`. **Mitigation:** the implementer picks one (see "Decisions deferred"); whichever is chosen, the policy reads from a single canonical source so a future migration is one-place. Avoid leaking agent-state into `AccountInterface` if that breaks the L1 boundary (option b is the safer default).
- **R5 — `getQuery()` baseline regression.** Adding per-record `AccessChecker` calls inside tools may introduce new `getQuery()->...->execute()` chains. **Mitigation:** the new chains MUST go through `setAccount()` (which is precisely the substrate this mission validates). `bin/check-getquery-bindings` is the gate; no baseline-entry additions are expected from a green build.
- **R6 — Bimaaji tool classification error.** Mis-marking `ProposeMutationTool` as `governed_data: false` would silently bypass OCAP for a mutation surface. **Mitigation:** the reviewer MUST audit every `governed_data: false` marker against the test "does this tool's output expose entity-data-shaped content OR does its side effect mutate governed data". `ProposeMutationTool` mutates the bimaaji graph (application metadata), not governed user data, so the marker is correct — but the reviewer confirms this explicitly, not by inheritance from the implementer's reasoning.

## Decisions pre-resolved

- **Three parallel WPs, no inbound dependencies.** Each can land independently. The dead-code-in-production guards per WP collectively prove the integration.
- **Capability opt-out marker is `#[Capability(governed_data: false)]` (or equivalent parameter on `#[AsAgentTool]`).** Implementer chooses the exact attribute shape; the name and the boolean semantics are fixed.
- **Per-file AI-access field is a field on existing entities**, not a separate entity type.
- **MCP redaction shape is `{accessRestricted: true, reason: "field_forbidden_for_account"}`.** Not a 403, not a silent drop.
- **Backwards compatibility on `AgentToolInterface::execute()` is NOT preserved.** Per DIR-003 alpha-stage Greenfield Removal Policy.
- **Decision preference order across the mission:** preserve OCAP audit lineage (DIR-004) > minimise vendor lock-in > don't break codified policy gates (DIR-006). Where these conflict, audit lineage wins.

## Decisions deferred to implementer (with guidance)

- **D-D1 — Signature change shape for `AgentToolInterface::execute()`.** Either (a) add a third parameter `AccessCheckerInterface $accessChecker`; or (b) collapse `(array $arguments, AccountInterface $account)` into a new `AgentToolContext` DTO that also carries `AccessCheckerInterface` and a per-call audit handle. *Guidance:* prefer (b) if multiple new context elements are likely to land in the next few missions (audit run-id, classification context); prefer (a) if the only mid-term addition is `AccessCheckerInterface`. Either is acceptable; both preserve OCAP audit lineage. (a) minimises diff surface; (b) is more future-proof.
- **D-D2 — Agent-initiation detection mechanism for the `'no'` toggle.** Either (a) extend `AccountInterface` with `isAgentInitiated(): bool`; or (b) carry a request-scope `_agent_run_id` attribute populated by `AgentExecutor`. *Guidance:* (b) is preferred because (a) leaks agent-state into the L1 `AccountInterface` and risks coupling L1 to L5 semantics over time. Pick (a) only if (b) requires invasive plumbing through synchronous code paths that don't have access to the request.
- **D-D3 — Exact list of bimaaji tools opting out via `governed_data: false`.** Default working set: `IntrospectGraphTool`, `IntrospectSectionTool`, `SearchSpecsTool`, `ProposeMutationTool`. *Guidance:* implementer enumerates each against the test "does this tool's output expose entity-data-shaped content OR does its side effect mutate governed user data?" `ProposeMutationTool` mutates bimaaji graph (application metadata) — opting out is correct. If the implementer finds any tool whose output includes user-data fields, that tool MUST consume the checker.
- **D-D4 — Static-analysis vs runtime guard for "tool without marker MUST invoke checker."** Either (a) a PHPStan rule under `tools/phpstan/` that scans `execute()` bodies for an `AccessChecker` call; or (b) a runtime audit-log assertion (e.g. emit a `tool_executed_without_access_check` event consumed by the dead-code-in-production guard test). *Guidance:* (a) is stronger (compile-time) but harder to write; (b) is sufficient for this mission given the per-WP guard tests already exist. Pick (b) unless (a) is cheap to author given existing PHPStan custom-rule patterns in the repo.
