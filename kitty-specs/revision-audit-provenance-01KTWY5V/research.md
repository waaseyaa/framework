# Research & Decisions: Revision & Audit Provenance

**Date**: 2026-06-12 | **Plan**: [plan.md](plan.md)

All findings verified against source at current `main` (post-alpha.203, tag `v0.1.0-alpha.203`). ## Verified ground truth

**Revision write path (live dialect)**

- The public revision-write seam is `RevisionableStorageDriver::writeRevision(string $entityId, array $values, ?string $log, ?string $langcode = null): int` (`packages/entity-storage/src/Driver/RevisionableStorageDriver.php:74-81`). The single-axis row is assembled in the private `writeDefaultRevision()` (`:301-330`): columns `entity_id`, `revision_id`, `revision_created` (`date('Y-m-d H:i:s')`), `revision_log`, plus field values folded into real columns / the `_data` blob by `foldData()` (`:577-613`). **No author column anywhere.** The per-language path `writePerLangcodeRevision()` (`:345-387`) writes the same metadata triple plus `langcode`. (The issue cited "writeRevision ~:301-330" — that span is now the private `writeDefaultRevision()`; the signature also grew a `$langcode` param since the evidence was taken.)
- All `writeRevision()` callers live in `EntityRepository` — seven sites: `doSave()` immediate (`packages/entity-storage/src/EntityRepository.php:435`) and deferred-id (`:480`), `rollback()` (`:653`), `saveTranslationRevision(s)` (`:870`, `:898`), `saveTranslation()` (`:1009`), `backfillInitialRevisions()` (`:1299`). Threading an author through `writeRevision()` covers every revision-creation path in the framework.

**Live revision table schema & sync**

- `SqlSchemaHandler::buildRevisionTableSpec()` (`packages/entity-storage/src/SqlSchemaHandler.php:641-717`) emits `<entity>_revision` with `entity_id`, `revision_id`, `revision_created`, `revision_log`, mirrored label/bundle/langcode/uuid key columns, `_data`; PK `(entity_id, revision_id)`. `buildTranslationRevisionTableSpec()` (`:731-751`) emits `<entity>__translation__revision` with the same metadata triple. **Neither has an author column.**
- **`ensureRevisionTable()` (`:248-259`) and `ensureTranslationRevisionTable()` (`:289-302`) early-return when the table exists — there is NO additive column sync for revision tables today.** Additive sync exists only for base tables (sql-column path, `ensureTable()` `:107-116`; `addFieldColumns()` `:371-380`), bundle subtables (`ensureBundleSubtable()` `:155-163` — the `fieldExists`→`addField` pattern to mirror), and translation tables (`TranslationSchemaHandler::sync()` `:108-119`). The spec's assumption "additive sync is supported by the existing schema-sync machinery" is therefore false for revision tables; FR-003 must add the additive arm. Production callers of `ensureRevisionTable()`: the kernel repository factory (`packages/foundation/src/Kernel/AbstractKernel.php:219`) and `EntitySchemaSync` (`packages/entity-storage/src/EntitySchemaSync.php:109`, `:113` for the translation-revision sibling) — both go through `SqlSchemaHandler`, so one fix covers both.

**Save path, SaveContext, publish pointer**

- `EntityRepository::save(EntityInterface $entity, bool $validate = true, ?SaveContext $context = null): int` (`packages/entity-storage/src/EntityRepository.php:267-270`); `doSave()` (`:351-539`) dispatches `EntityEvents::PRE_SAVE` (`:384`), `BeforeSaveEvent` (`:398`), `EntityEvents::POST_SAVE` (`:510`), `EntityEvents::REVISION_CREATED` (`:517`), `AfterSaveEvent` (`:528`). `EntityEvent` carries entity/originalEntity/langcode only — **no account** (`packages/entity/src/Event/EntityEvent.php:25-30`); `BeforeSaveEvent`/`AfterSaveEvent` carry entity + SaveContext + createRevision flag, also no account.
- `SaveContext` (`packages/entity-storage/src/SaveContext.php`) is a final immutable value object with private constructor and `withoutNewRevision` / `langcode` / `isImport` / `translations` — designed to extend additively ("Future flags … extend this object without changing call sites", `:13-15`).
- `setPublishedRevision()` (`:795-848`) moves only the base-table `published_revision_id` pointer and dispatches **`EntityEvents::REVISION_REVERTED`** (`:842-845`) — a misnomer shared with `setCurrentRevision()` (`:752-755`); `rollback()` dispatches `REVISION_CREATED` + `REVISION_REVERTED` (`:671-678`). No event carries the actor or the revision transition; no audit listener subscribes to `REVISION_REVERTED` — publish-pointer moves are audit-invisible, confirming #1645's third surface.

**Revision metadata accessor**

- `RevisionMetadata` (`packages/entity/src/RevisionMetadata.php`) is `(\DateTimeImmutable $revisionCreatedAt, ?int $revisionAuthor = null, ?string $revisionLog = null)`. Its docblock claims storage in `<entity>__revision` as `revision_created_at`/`revision_author`/`revision_log` — **that is the dormant M-004 dialect, not the live one** (doc drift to fix under FR-009).
- `RevisionableEntityTrait::revisionMetadata()` (`packages/entity/src/RevisionableEntityTrait.php:97-100`) returns the private field; **`setRevisionMetadata()` (`:135-138`) has zero production callers** (grep: only tests construct `RevisionMetadata`). `EntityRepository::loadRevision()` (`:592-630`) hydrates `revisionId`/`isCurrentRevision` via `method_exists` (`:620-627`) but never builds `RevisionMetadata` — the accessor is permanently null on every load path. Confirms #1644.

**Audit attribution surfaces (#1645)**

- `EntityLifecycleAuditListener::resolveAccountUid()` (`packages/audit/src/Listener/EntityLifecycleAuditListener.php:128-138`) reads the **entity's own `uid` field** and falls back to `0` — the saved entity's owner field, not the acting account. Subscribes PRE_SAVE/POST_SAVE/POST_DELETE (`:37-44`).
- `AgentToolAuditListener` hardcodes `accountUid: 0` (`packages/audit/src/Listener/AgentToolAuditListener.php:62`) with the comment "account bound by agent run context" — but the subscribed event `AgentRunToolCallObserved` (`packages/ai-observability/src/Event/AgentRunToolCallObserved.php:17-24`) carries only `runId`/`toolName`/`succeeded`. The dispatcher, `AgentExecutor::executeRun()`, **has** `$initiatorAccount` in scope at both dispatch sites (`packages/ai-agent/src/AgentExecutor.php:337`, `:367`) and passes it into every tool execution (`:319`).
- `McpDispatchAuditListener` subscribes the string event name `waaseyaa.mcp.dispatch` (`packages/audit/src/Listener/McpDispatchAuditListener.php:30`) and duck-reads `method`/`params`/`accountUid` (`:50-52`). **Nothing fires it**: `McpEndpoint` (`packages/mcp/src/McpEndpoint.php:29-99`) has no event-dispatcher dependency at all. The endpoint is container-resolved via the controller string `Waaseyaa\Mcp\McpEndpoint::handle` (`packages/mcp/src/McpRouteProvider.php:17`, dispatched by `AppControllerRouter`); the auth-resolved account is available at `:61-76`. Confirms FR-007's premise; the #1635/#1636 transport bugs are independent of adding a dispatch.
- `ApiRequestAuditListener` already resolves the actor correctly from the `_account` request attribute (`packages/audit/src/Listener/ApiRequestAuditListener.php:50-53`) — the model the other listeners should converge on, generalised off the Request object.

**Audit schema & append-only guard (#1648)**

- `audit_event.account_uid` is **`INTEGER NOT NULL DEFAULT 0`** (`packages/audit/src/Schema/AuditEventSchemaHandler.php:45`), created via `CREATE TABLE IF NOT EXISTS` — existing installs never get DDL changes from the CREATE statement. SQLite cannot relax NOT NULL via ALTER; making `account_uid` itself nullable would require a table rebuild, which violates C-004's additive-only constraint. `AuditEventDescriptor::$accountUid` is `int` (non-nullable) (`packages/audit/src/Contract/AuditEventDescriptor.php:21`).
- `AuditEventQuery` selects all columns (`fields('ae')`, `packages/audit/src/Query/AuditEventQuery.php:33`) — additive columns flow through existing query tooling untouched (C-004 satisfied by construction). `AuditEvent::getAccountUid(): int` (`packages/audit/src/Entity/AuditEvent.php:56-58`).
- `AppendOnlyAuditDatabase::query()` (`packages/audit/src/Storage/AppendOnlyAuditDatabase.php:84-87`) **passes raw SQL through unguarded**; only the builder methods `update()`/`delete()` call `assertMutable()` (`:94-105`). Confirms #1648.
- The decorator is held by exactly one object: `AuditEventWriter` (wrapped at `packages/audit/src/AuditServiceProvider.php:60`), which only ever calls `insert()` (`packages/audit/src/Writer/AuditEventWriter.php:39-56`) — it never calls `query()`. The retention prune (`packages/cli/src/Command/Audit/PruneCommand.php`) takes the **raw** `DatabaseInterface` (`:42`) and deletes via the builder (`:123`) — it never touches the decorator. A `query()` guard therefore has zero legitimate traffic to false-positive on (NFR-003 holds by wiring, proven by the existing suite incl. `packages/audit/tests/Integration/AuditImmutabilityTest.php`).

**Actor propagation — what exists**

- **No request-scoped account context/holder service exists anywhere** (`rg "AccountContext|CurrentAccount|currentAccount" packages/` → only unrelated hits in graphql/admin-surface that read `_account` off the Request). The acting account travels exclusively as the `_account` request attribute set by `SessionMiddleware` (`packages/user/src/Middleware/SessionMiddleware.php:61`) — unreachable from entity-storage, which never sees the Request.
- Composer/layer facts: `entity-storage` (L1) **already requires `waaseyaa/access`** (L1); `audit` (L1) requires entity/entity-storage/foundation/database-legacy but **not** access; `user`, `mcp`, `ai-agent` all already require access. `access` requires entity/foundation/plugin — adding `audit → access` creates no cycle and is a same-layer (L1→L1) edge, permitted by the layer rule ("own layer or lower"). An `access ↔ entity` mutual manifest edge already exists in-tree, so same-layer mutual edges are an accepted precedent at the manifest level.
- Kernel precedent for cross-cutting repository collaborators: the alpha.204 validator is constructed once in `AbstractKernel::bootEntityTypeManager()` and captured by the repository factory closure (`packages/foundation/src/Kernel/AbstractKernel.php:203-206`, passed at `:262`). The same pattern fits an account-context holder.

**Dormant dialect (FR-009)**

- `RevisionTableBuilder` (`packages/entity-storage/src/Schema/RevisionTableBuilder.php`) emits the M-004 dialect: `<entity>__revision` (double underscore) with surrogate `vid` PK and metadata `revision_created_at` / **`revision_author INTEGER NULL` (soft FK, `:284-289`)** / `revision_log`; the two-axis variant repeats `revision_author` at `:420-423`. Its only production reference is `TranslationSchemaHandler::syncTwoAxis()` (`packages/entity-storage/src/Schema/TranslationSchemaHandler.php:183-184`) — **which itself has zero production callers** (kernel calls `sync()` only, `AbstractKernel:233`; `EntitySchemaSync` calls `sync()` at `:94`; all other references are tests). The live two-axis table is created by `SqlSchemaHandler::ensureTranslationRevisionTable()` instead. Confirmed dormant: two divergent dialects exist on disk, one live (no author), one dormant (has author), exactly as the spec's edge case warns. `docs/specs/revision-system-unified.md` §6 already schedules the vid stack for retirement but keeps `RevisionTableBuilder`/`TranslationSchemaHandler` "where still used by the translation substrate".

## D1 — Actor propagation seam

**Decision**: Introduce a request-scoped acting-account holder in **`packages/access`** (L1, the package that owns `AccountInterface`): `Waaseyaa\Access\Context\AccountContextInterface` (`current(): ?AccountInterface`, `set(?AccountInterface $account): void`) with mutable implementation `RequestAccountContext`. One instance is constructed in `AbstractKernel::bootEntityTypeManager()` (validator precedent), captured by the repository factory closure, and bound on the kernel services bus so service providers (audit) and controllers (mcp) resolve the same instance. Writers of the context:

1. `SessionMiddleware` sets it in the same statement block that sets `_account` (`SessionMiddleware.php:61`) — every HTTP request, every account state (authenticated N, `AnonymousUser` id 0, dev fallback `PHP_INT_MAX`).
2. `McpEndpoint::dispatch()` sets it to the bearer-auth-resolved account after `authenticate()` succeeds (`McpEndpoint.php:61-76`), restoring the prior value in `finally` (the MCP account deliberately differs from the session account per the endpoint's own docblock).
3. `AgentExecutor::executeRun()` sets it to `$initiatorAccount` for the duration of the run (set/restore in `finally`) so entity saves made *by agent tools* — including queue-driven runs with no HTTP request — carry the initiator.
4. CLI/queue/bootstrap contexts that set nothing read back `null` — the spec's "no actor context" state.

PLUS an explicit per-save override on `SaveContext`: `withActorUid(?int $uid)` setting an `actorOverridden` flag (see data-model.md for precedence). Author resolution happens once per `doSave()`/pointer operation in `EntityRepository`: override if flagged, else `AccountContext::current()?->id()` cast to int, else null.

**Layer answer (the tricky part, explicit)**: the holder must be readable from `entity-storage` (L1) and `audit` (L1) without upward imports. `access` is L1 — same layer — and `entity-storage` already declares the `waaseyaa/access` edge; `audit` gains a new same-layer `waaseyaa/access` require (no cycle: access requires only entity/foundation/plugin; the constraint literal `^0.1.0-alpha.203` per CP-NEW). Setters live in `user` (L1, has access edge), `mcp` (L6→L1, has edge), `ai-agent` (L5→L1, has edge) — all downward or same-layer. The kernel passes the instance under its sanctioned entry-point exemption. No `DomainEvent` upward channel is needed because nothing flows upward.

**Alternatives considered**: (a) Holder in `entity` — rejected: the CLAUDE.md circularity gotcha assigns `AccountInterface` ownership to access; an account holder in entity inverts that. (b) Holder in `foundation` (L0) — rejected: L0 cannot type-hint `AccountInterface` (L1) without a string-typed bag, losing type safety for no benefit since every consumer is L1+. (c) Thread the account as a `save()` parameter only (no ambient context) — rejected: FR-002 explicitly requires no manual threading; every controller/service callsite framework-wide would need changes. (d) Read `_account` via a request stack — no request stack exists in Waaseyaa, and entity-storage must work in non-HTTP contexts.

## D2 — Revision author storage

**Decision**: New nullable column **`revision_author` (int, `not null => false`, no default, soft FK — no ON DELETE)** on both live revision tables. Three changes in `SqlSchemaHandler`: (1) add the column to `buildRevisionTableSpec()` and `buildTranslationRevisionTableSpec()` for new tables; (2) give `ensureRevisionTable()` and `ensureTranslationRevisionTable()` an additive arm — when the table exists, `fieldExists` → `addField` for `revision_author` (the `ensureBundleSubtable()` pattern at `:155-163`); (3) nothing else — no backfill, no rewrite (C-001). `RevisionableStorageDriver::writeRevision()` gains a trailing `?int $author = null` parameter threaded into both row assemblies; `EntityRepository` passes the resolved actor at all seven callsites (`backfillInitialRevisions` passes the same resolution — a CLI backfill with no context records null, correctly).

**Rationale**: The column name converges the dialects — the dormant `RevisionTableBuilder` already calls it `revision_author` with identical nullable-int soft-FK semantics (`RevisionTableBuilder.php:284-289`), and `RevisionMetadata::$revisionAuthor` already expects it. Nullable-no-default makes pre-existing rows and ALTER-added columns read back as SQL NULL → metadata `null` with zero migration (FR-003, SC-004). `ADD COLUMN` of a nullable column is metadata-only DDL on SQLite, MySQL 8, and PostgreSQL — safe on large tables.

**Alternatives considered**: (a) Snapshot the author into `_data` — rejected: invisible to SQL (no future "revisions by author" queries), and `foldData()` would make presence depend on schema state; a real column is the contract. (b) `revision_uid` Drupal-style naming — rejected: diverges from both the dormant dialect and `RevisionMetadata`, creating a third vocabulary. (c) NOT NULL DEFAULT 0 — rejected outright by FR-001's "absence is recorded as null, never coerced to 0".

## D3 — Audit actor (null vs 0, additive path)

**Decision**: `audit_event.account_uid` stays physically NOT NULL (it cannot be relaxed additively — verified above). Add a new **nullable `actor_uid INTEGER NULL` column** as the authoritative actor: included in the `CREATE TABLE` DDL for new installs, added to existing installs by an idempotent guarded `ALTER TABLE audit_event ADD COLUMN actor_uid INTEGER` in `AuditEventSchemaHandler::ensureSchema()`, plus index `audit_event_actor_uid`. `AuditEventDescriptor::$accountUid` widens from `int` to `?int` (null = no acting context); `AuditEventWriter` writes `actor_uid = $descriptor->accountUid` (null preserved) and `account_uid = $descriptor->accountUid ?? 0` (legacy column keeps its historical 0-sentinel semantics, so existing dashboards/filters keep working). `AuditEvent` read model gains `getActorUid(): ?int` (`''`/missing → null, mirroring the `getEntityTypeId2` empty-sentinel precedent); `getAccountUid()` unchanged. Listeners stop deriving actors locally: `EntityLifecycleAuditListener` drops `resolveAccountUid()` (entity-`uid` misattribution) and reads the injected `AccountContextInterface`; `AgentToolAuditListener` reads a new `?int $accountId` property on `AgentRunToolCallObserved` (additive constructor param, populated by `AgentExecutor` from `$initiatorAccount`), falling back to the context, else null; `McpDispatchAuditListener` preserves null instead of casting absent to 0.

**Rationale**: C-004 (additive only, `AuditEventQuery` keeps working) forecloses making `account_uid` itself nullable on existing installs; a parallel nullable column is the only additive encoding of three-state actors (N / 0 / null). `AuditEventQuery` does `fields('ae')` so the new column is automatically readable. Widening the descriptor property `int → ?int` is parameter-compatible for every existing caller and is an alpha-phase API change documented in the CHANGELOG (DIR-003 greenfield policy).

**Alternatives considered**: (a) Make `account_uid` nullable via table rebuild — rejected: violates C-004/C-002 and rewrites an append-only log. (b) Magic sentinel (-1 = no actor) in `account_uid` — rejected: the spec's whole point is that sentinel-coding absence caused this mess; also collides with nothing today but is un-queryable as "absent". (c) Separate `actor_uid` AND keep descriptor's int — rejected: two overlapping descriptor fields invite drift; one nullable canonical field with a derived legacy column is strictly simpler.

**Spec-fidelity note (DIRECTIVE_010)**: the spec's Key Entities line says "actor (`account_uid`, now nullable-distinct)". Source reality (NOT NULL, SQLite, C-004) makes that unimplementable additively; the nullable-distinct actor lands in `actor_uid` instead, with `account_uid` retained as a derived legacy column. This is a documented adaptation, not silent drift; FR-004's normative text ("absence recorded distinctly from account 0") is fully met.

## D4 — Publish audit

**Decision**: New dedicated event class `Waaseyaa\EntityStorage\Event\RevisionPointerMovedEvent` (sibling of `BeforeSaveEvent`) carrying `entityTypeId`, `entityId`, `operation` (`'publish'` | `'revert'`), `fromRevisionId: ?int`, `toRevisionId: int`. Dispatched (FQCN event name, best-effort alongside — not replacing — the existing `REVISION_REVERTED` dispatches) from: `setPublishedRevision()` (operation `publish`; `from` = the prior `published_revision_id`, read from the base row inside the existing transaction) and `setCurrentRevision()` (operation `revert`; `from` = the prior base `revision_id` pointer). `rollback()` is NOT a pointer-only move — it creates a new revision whose authorship D2 already records (spec edge case "revisions created by reverts") and flows through `REVISION_CREATED`; it gets no pointer event. New listener `PublishPointerAuditListener` in `packages/audit` (audit already requires entity-storage, so a typed import is layer-clean) records two new additive `AuditEventKind` cases — `RevisionPublish = 'revision.publish'`, `RevisionRevert = 'revision.revert'` — with actor from `AccountContextInterface` (null-distinct per D3) and attributes `{operation, from_revision_id, to_revision_id, entity_id}`.

**Rationale**: Enriching `EntityEvents::REVISION_REVERTED` was the considered alternative, but `EntityEvent` is a shared class whose constructor shape is consumed framework-wide and it cannot carry a transition without widening every dispatch site; worse, `REVISION_REVERTED` fires for three semantically different operations today, so a listener could not distinguish publish from revert. A purpose-built event names the transition precisely and costs nothing at the two dispatch sites. Two enum cases (vs one with an `operation` attribute) keep `filter[kind]` queries first-class, matching the taxonomy's dotted-verb convention and the additive-only extension policy in `docs/specs/ocap-audit-log.md`.

**Alternatives considered**: (a) Enrich `REVISION_REVERTED` — rejected above. (b) Audit inside `EntityRepository` directly — rejected: entity-storage must not depend on audit (would invert L1 peer coupling and bypass the listener catalogue pattern); events are the established seam. (c) Single kind `entity.publish` — rejected: a revert recorded as "publish" misleads reviewers.

## D5 — MCP dispatch event firing point

**Decision**: Fire in `McpEndpoint::dispatch()` — after `authenticate()` succeeds and the JSON-RPC envelope parses with a known `method` key, immediately before the `match` (`McpEndpoint.php:92`), so every authenticated JSON-RPC method invocation (including `tools/call`, FR-007) produces exactly one event. New class `Waaseyaa\Mcp\Event\McpDispatchEvent` with `public const NAME = 'waaseyaa.mcp.dispatch'` (value pinned to `McpDispatchAuditListener::EVENT_NAME` by a cross-package test; mcp does not require audit, so the literal is duplicated by design) and public readonly `method: string`, `params: array`, `accountUid: ?int` (from `$authenticated->id()`). `McpEndpoint` gains an optional trailing constructor param `?EventDispatcherInterface $dispatcher = null` (Symfony contracts — already the dispatcher interface providers resolve, `AuditServiceProvider.php:82`), container-resolved when `AppControllerRouter` builds the endpoint; dispatch is wrapped best-effort (try/catch) so audit can never break the RPC response. The same `dispatch()` block also sets the `AccountContextInterface` per D1. **Explicitly out of scope**: the 500/tools-list transport bugs #1635/#1636 — the event fires from the seam as-is and must not depend on those fixes (spec assumption confirmed).

**Rationale**: `dispatch()` is the single choke point where the auth-resolved account and the parsed method coexist; firing pre-`match` matches the listener's documented contract ("each JSON-RPC method invocation", `McpDispatchAuditListener.php:17-19`) and keeps the params-hash privacy property (hashing happens in the listener, which never logs raw params).

**Alternatives considered**: (a) Fire only inside `handleToolsCall()` — narrower than the listener's documented contract; FR-007 would pass but `initialize`/`tools/list` invocations would stay invisible for no saved complexity. (b) Fire from `AgentToolRegistryBridge::execute()` — wrong layer (the bridge is also used conceptually per-tool, would double-fire with `agent.tool_execute`) and loses the JSON-RPC method name.

## D6 — Raw-SQL guard in AppendOnlyAuditDatabase::query()

**Decision**: Guard `query()` (`AppendOnlyAuditDatabase.php:84-87`) with a token-level check before delegating: strip single-quoted/double-quoted string literals and SQL comments (`--`, `/* */`) from the SQL, then if the remainder contains a word-boundary match for any of `UPDATE | DELETE | DROP | ALTER | TRUNCATE` **and** a word-boundary match for any append-only table name (`audit_event`), throw the **same `\LogicException`** produced by `assertMutable()` (refactored so both paths share the message factory, with the detected operation interpolated). Everything else — SELECTs over audit_event, mutations of other tables, inserts — passes through untouched.

**Rationale**: Literal-stripping kills the realistic false-positive class (`SELECT … WHERE attributes LIKE '%delete%'` — `attributes` is a JSON TEXT column, so payloads genuinely contain such words). The conjunctive rule (verb AND audit table) keeps mutations of non-audit tables working through the decorator. Fail-closed on the residual pathological case (an identifier literally named `delete` joined against audit_event) is the correct posture for an append-only guarantee and is documented in the contract. Zero-false-positive proof for NFR-003 is structural, verified in ground truth: the only holder of the decorator is the insert-only writer (never calls `query()`); prune resolves the raw `DatabaseInterface` (`PruneCommand.php:42`, `:123`) and `AuditEventQuery` likewise — the existing audit suite (immutability + chaos + prune) passing unchanged is the pinning evidence.

**Alternatives considered**: (a) Full SQL parser — over-engineering for one decorator; no parser dependency exists in-tree. (b) Whitelist (only allow statements starting with SELECT) — rejected: breaks legitimate raw mutations of *other* tables through the decorator and is a behavioral break C-002 doesn't ask for. (c) First-keyword-only check — rejected: misses `WITH x AS (…) DELETE FROM audit_event` and multi-statement strings.

## D7 — FR-009: dormant dialect reconcile-or-retire

**Decision**: **Reconcile the author column; explicitly retire the rest of the dormant emission dialect in docs.** Concretely: (1) the live dialect *adopts* the dormant dialect's author column definition verbatim — name `revision_author`, nullable int, soft FK, survives user deletion — making it the single authoritative author definition (D2); (2) `docs/specs/revision-system-unified.md` gains an explicit note in §6 that `RevisionTableBuilder`'s `<entity>__revision` vid dialect (including its `revision_created_at`/`revision_author` metadata block) is **non-live and superseded** — its author semantics now live in the real `<entity>_revision` tables — and that `syncTwoAxis()` has no production callers (verified above); (3) `RevisionMetadata`'s docblock is corrected from the dormant table/columns (`<entity>__revision`, `revision_created_at`) to the live ones (`<entity>_revision`, `revision_created`, `revision_author`, `revision_log`). Deleting `RevisionTableBuilder`/`syncTwoAxis` is NOT done here — the unified spec's §6 retirement plan owns that and conditions it on translation-substrate work that is out of this mission's scope.

**Rationale**: The spec demands "single authoritative author column definition OR explicit retirement"; this delivers both halves where each is cheapest — the *definition* converges into the live dialect (no second author vocabulary can emerge), and the *dormant emission path* is documented as retired rather than deleted (deletion would touch the two-axis test suite and the unified spec's own staged plan, pure scope creep for a provenance mission). Risk of divergence drops to zero because the only author definition reachable from production code is the live one.

**Alternatives considered**: (a) Delete the dormant stack now — rejected: §6 of the unified spec conditions removal on live two-axis capability tests; doing it here couples an attribution release to a storage-stack removal. (b) Wire `syncTwoAxis()` into production to "reconcile by activation" — rejected: it would create *second* parallel revision tables (`__revision` alongside `_revision`) for two-axis types; actively harmful.

## Performance note (NFR-001)

Actor resolution is one property read on an in-memory holder plus a possible `id()` call — no query, no I/O. The revision write grows by one column in an existing INSERT. The additive schema check adds one `fieldExists` call per `ensureRevisionTable()` invocation (kernel boot / db:init, not per save). The integration perf smoke (200 saves with vs without an account in context) pins the ≤5% envelope; nothing here is expected to register above noise.
