## Verified ground truth

**Discovery index (#1649, surface 1)**

- `ApiDiscoveryController::discover()` (`packages/api/src/ApiDiscoveryController.php:26-44`) iterates `EntityTypeManagerInterface::getDefinitions()` and emits a link per type id, unconditionally (`:30-35`). The controller has no account, no access handler — only the type manager and a base path (`:16-19`).
- The `api.discovery` route is registered with `->allowAll()` (`packages/api/src/JsonApiRouteProvider.php:37-44`), which sets `_public` — pinned by `tests/Integration/Phase7/ApiDiscoveryIntegrationTest.php:66` ("api.discovery must be public").
- **Dispatch path**: the controller is NOT container-resolved. `DiscoveryRouter` (registered from `ApiServiceProvider::httpDomainRouters()`, `packages/api/src/ApiServiceProvider.php:90-93`) matches on the controller string and constructs `new ApiDiscoveryController($this->entityTypeManager)` inline per request (`packages/api/src/Http/Router/DiscoveryRouter.php:40-44`). The same method already builds `$ctx = WaaseyaaContext::fromRequest($request)` (`:37`), and `WaaseyaaContext` carries the request account read from the `_account` attribute (`packages/foundation/src/Http/Router/WaaseyaaContext.php:24,31-39`). The account is one argument away from the controller — confirming the seam is entirely inside `packages/api`.
- **Adjacent surfaces (out of spec scope, recorded)**: `/api/schema/{entity_type}`, `/api/openapi.json`, and `/api/entity-types` are registered with no access options at all (`packages/foundation/src/Kernel/BuiltinRouteRegistrar.php:31-53`); `AccessChecker` returns neutral for option-less routes (`packages/access/src/AccessChecker.php:109-111`), i.e. they are anonymous-reachable and also enumerate type ids. The spec's Key Entity is the `GET /api` discovery index only; these are flagged in plan Risks for a follow-up issue.

**Categorical view access — what exists (#1649, the load-bearing question)**

- `AccessPolicyInterface` (`packages/access/src/AccessPolicyInterface.php`) has exactly three methods: `access(EntityInterface $entity, string $operation, AccountInterface $account)` (`:24` — requires a *concrete entity*, parameter is non-nullable), `createAccess(string $entityTypeId, string $bundle, AccountInterface $account)` (`:33` — type-level but create-only), `appliesTo(string $entityTypeId)` (`:40`).
- `EntityAccessHandler` aggregates: `check()` (`:82-87`, entity-level, `isAllowed()` semantics), `checkCreateAccess()` (`:129`), `checkFieldAccess()`/`filterFields()` (field-level, `!isForbidden()` semantics). It exposes **no type-level view check and no policy list** — `$this->policies` is private with no getter.
- Gates delegate to the same two methods: `EntityAccessGate::allows()` handles `EntityInterface` subjects via `check()` and string subjects only for ability `create` via `checkCreateAccess()`; any other string-subject ability is **denied** with a warning (`packages/access/src/Gate/EntityAccessGate.php:43-83`).
- Policy implementations confirm row-dependence: `GenealogyContentAccessPolicy::access()` routes `view` through `viewAccess($entity, …)` reading entity fields, with a tombstone field check first (`packages/genealogy/src/Access/GenealogyContentAccessPolicy.php:37-51`); `GenealogyRelationshipAccessPolicy::viewEdge()` loads both relationship *endpoints* from the edge's field values (`packages/genealogy/src/Access/GenealogyRelationshipAccessPolicy.php:55-58`). A "null-entity" or prototype-entity invocation is not supported by the API surface and would feed these policies empty field values.
- **Conclusion: the spec assumption "access policies expose a categorical check or equivalent" is FALSE.** The spec's own fallback clause governs: "the discoverable flag plus an authenticated-only default" (decided as D1).

**Denied vs missing single read (#1649, surface 2)**

- `JsonApiController::show()` (`packages/api/src/JsonApiController.php:131-170`): missing entity → `errorDocument(JsonApiError::notFound("Entity of type '{$entityTypeId}' with ID '{$id}' not found."))` (`:141-145`); real-but-denied (`check($entity,'view',$account)` not allowed) → `errorDocument(JsonApiError::forbidden("Access denied for viewing entity '{$id}'."))` (`:147-155`). (The issue cited "~:148-155" — current span matches.)
- `JsonApiError::notFound()` emits `{status:'404', title:'Not Found', detail:…}` with **no `code` member**; `forbidden()` adds `code:'FORBIDDEN'` (`packages/api/src/JsonApiError.php:60-80`, serialization `:35-55`). So today the two cases differ in status, title, code, and detail — a fully diffable oracle.
- Both documents leave through one emitter: `JsonApiRouter::handle()` builds the controller with `($entityTypeManager, $serializer, $accessHandler, $ctx->account)` and returns `jsonApiResponse($document->statusCode, $document->toArray())` (`packages/foundation/src/Http/Router/JsonApiRouter.php:47-69`) — headers are identical by construction once the documents match. Byte-identity (NFR-002) is therefore decidable entirely at the document level.
- The access check runs only when `accessHandler !== null && account !== null` (`:148`); in production HTTP both are always present (`SessionMiddleware` sets `_account` for every request, including `AnonymousUser`).
- Mutation denial sites that must stay 403 (FR-004): create `:259-267`, create-field-edit `:271-279`, update `:360-366`, update-field-edit `:374-382`, delete `:432-438`. The POST/PATCH/DELETE routes all carry `requireAuthentication()` (`JsonApiRouteProvider.php:82-114`), so the residual existence signal on mutations is reachable by authenticated callers only.
- Tests encoding the old behavior: `packages/api/tests/Unit/JsonApiControllerAccessControlTest.php` asserts `'403'` for denied show (`:59` among others) — to be deliberately updated; `tests/Integration/Phase7/ApiDiscoveryIntegrationTest.php:97-114` asserts every registered type appears in discovery — to be made account-aware.

**EntityType definition (#1649, the flag)**

- `EntityType` is `final readonly`, constructed with named params (`packages/entity/src/EntityType.php:68-84`); existing additive precedents: `tenancy` (mission #1257), `primaryStorageBackend`. A trailing `discoverable: bool = true` + `isDiscoverable(): bool` accessor is the established shape. `fromClass()` (`:196-253`) takes presentation-grade overrides and caches per class — a `discoverable` passthrough param follows the same first-call-wins rule as the other non-tenancy overrides.
- `EntityTypeInterface` (`packages/entity/src/EntityTypeInterface.php`) has **seven anonymous-class implementors in tests outside this mission's surface** (cli ×4, listing ×1, relationship ×1, plus fixtures): widening the interface would break them all. The only production implementor is `EntityType` itself.

**Bearer token auth (#1652)**

- `BearerTokenAuth::authenticate()` (`packages/mcp/src/Auth/BearerTokenAuth.php:16-29`): prefix check, then `return $this->tokens[$token] ?? null;` (`:28`) — a hash lookup whose timing varies with key existence/length, and no account-state check of any kind. (Issue evidence ":16-29" — current.) `getTokens()` (`:41-44`) feeds admin fingerprinting (`ServerConfigReadModel`) — must keep returning the raw map.
- Token map shape: `array<string, AccountInterface>` (`:11`). PHP array-key coercion: a purely numeric token string becomes an `int` key — the constant-time scan must `(string)`-cast candidates before `hash_equals()`.
- Default binding is `new BearerTokenAuth(tokens: [])`; production deployments override by re-binding `McpAuthInterface` (`packages/mcp/src/McpServiceProvider.php:44-47`, README "Authentication").
- **Blocked/inactive state**: `AccountInterface` (`packages/access/src/AccountInterface.php`) exposes only `id()`, `hasPermission()`, `getRoles()`, `isAuthenticated()` — **no status member**. The framework's account entity `User implements AccountInterface` (`packages/user/src/User.php:29`) and exposes `isActive(): bool` reading the `status` field (`:340-343`; field default `:46`; the auth login query already excludes `status != 1` accounts at session time — `packages/user/src/Http/AuthController.php:61-78` — which is exactly what the bearer path lacks). `UserAccessPolicy` consumes `isActive()` (`packages/user/src/UserAccessPolicy.php:61`) — precedent for treating it as the canonical liveness accessor.
- Freshness: every runtime builds a fresh kernel per request (`public/index.php:36-41` — "A fresh kernel is built per request so no container/entity state bleeds across requests", including FrankenPHP worker mode), so a token map built in a provider holds account objects loaded *this request* — an in-memory `isActive()` read at `authenticate()` time is a request-time check with zero added queries (NFR-003).
- `packages/mcp/composer.json` requires access/entity/api/etc. but **not** `waaseyaa/user` (`:78-87`) — an `instanceof User` check would add a manifest edge; duck-typing avoids it.
- Existing test surface: `packages/mcp/tests/Unit/Auth/BearerTokenAuthTest.php` (7 tests: valid/invalid/missing/empty/malformed/case-insensitive-prefix/empty-map) — all must stay green unchanged.

**WAASEYAA_DB resolution (#1650)**

- The canonical read is `DatabaseBootstrapper::resolvePath()` (`packages/foundation/src/Kernel/Bootstrap/DatabaseBootstrapper.php:25-43`): `$config['database']` → `getenv('WAASEYAA_DB')` → `$projectRoot . '/storage/waaseyaa.sqlite'` (`:27-30`). A relative env or config value is passed **verbatim** to `@mkdir(dirname(...))` (`:37-40`) and `DBALDatabase::createSqlite($path)` (`:22`) — SQLite resolves it against process CWD. The unset default is already project-root-absolute. (Issue evidence matched at `:29`.)
- Single production callsite: `AbstractKernel:197` (`$this->database = new DatabaseBootstrapper()->boot($this->projectRoot, $this->config);`). All four runtimes funnel through it:
  - **HTTP / dev server**: `public/index.php` computes `$projectRoot = dirname(__DIR__)` (`:23`) and builds `HttpKernel($projectRoot)` per request (`:38`) — projectRoot is correct regardless of CWD; only the *relative path joined later by SQLite* breaks. With `php -S` started from the docroot, CWD = `public/` → the stray `public/storage/waaseyaa.sqlite`.
  - **CLI / queue**: `packages/cli/bin/waaseyaa` sets `projectRoot = getcwd()` and refuses to run unless it contains `composer.json` (`:14-20`); `CliApplication` boots `ConsoleKernel($projectRoot, …)` (`packages/cli/src/CliApplication.php:86`), which extends `AbstractKernel`. Queue workers are CLI commands — same path.
- **Divergent parallel resolution in the CLI**: `DbInitHandler::resolveDatabasePath()` (`packages/cli/src/Handler/DbInitHandler.php:160-173`) returns `config['database']` **verbatim** (relative config values stay CWD-relative even here) but absolutizes env values via its own `absolutize()` (`:175-181`) — which treats only `:memory:` and `/`-prefixed strings as absolute (a Windows drive-letter path would be wrongly prefixed). So today even two CLI codepaths can disagree, in addition to the HTTP/CLI split.
- Display-only surfaces showing the raw env value instead of the resolved path: `HealthReportHandler:115`, `AboutHandler:44`.
- Warning seam: `AbstractKernel` has `$this->logger` (`:87`, ctor `:120-123`, config-upgraded `:144-151`) in scope at the `:197` callsite; `DatabaseBootstrapper` currently takes no logger. Framework convention: `?LoggerInterface $logger = null` defaulting to `NullLogger` (CLAUDE.md "No psr/log").
- Docroot: the framework docroot is `{projectRoot}/public` (`public/index.php` is the front controller; no other docroot notion exists in the kernel).
- Existing test surface: `packages/foundation/tests/Unit/Kernel/Bootstrap/DatabaseBootstrapperTest.php` (uses `putenv('WAASEYAA_DB=…')`); `packages/cli/tests/Unit/Handler/DbInitHandlerTest.php`, `HealthReportHandlerTest.php`, `AboutHandlerTest.php` exist.

## D1 — Discovery filtering mechanism (FR-001)

**Decision**: Adopt the spec's pre-approved fallback — **discoverable flag + authenticated-only default**, implemented entirely in `packages/api`. `DiscoveryRouter::handle()` passes `$ctx->account` (already in scope at `:37`) into the inline `ApiDiscoveryController` construction; the controller gains an optional `?AccountInterface $account = null` ctor param. `discover()` emits per-type links only when `$this->account?->isAuthenticated() === true`; an unauthenticated (or absent) account receives the envelope — `meta {api, version}` + `links.self` — with **zero** entity-type links. Types whose definition opts out via `isDiscoverable() === false` (D2) are skipped for every caller, authenticated or not. The `api.discovery` route stays `allowAll()`: the index endpoint answers everyone; only its contents are account-dependent.

**Rationale**: The primary assumption (a categorical per-account/per-type view check) is falsified — verified above: `access()` demands a concrete entity, `createAccess()` is create-only, the handler exposes neither a type-view aggregate nor its policy list, and real policies (genealogy/OCAP) decide `view` from row field values. The spec's Assumptions block names this exact fallback for this exact case. Authenticated-only is the correct conservative direction for an information-leak fix: anonymous discovery reveals nothing (SC-001 — the FNPI bland-type-names mitigation becomes unnecessary), while the admin/authorized edge case ("must still see gated types") holds because every authenticated account sees all discoverable types. NFR-001 holds trivially: one `isAuthenticated()` call per request + one accessor per type, no queries, no row checks.

**Alternatives considered**: (a) *Prototype-entity check* — `check(new $entityClass([]), 'view', $account)` with `!isForbidden()` semantics: rejected; the policy API does not support entity-less invocation, and real policies read field values / load related entities from the probe (GenealogyRelationshipAccessPolicy::viewEdge loads both endpoints), yielding throws or wrong answers on an empty prototype. (b) *New categorical policy interface* (e.g. `TypeViewAccessPolicyInterface` discovered via `instanceof`, the `FieldAccessPolicyInterface` pattern): the right long-term seam, but it expands the mission into `packages/access` and into every policy author's contract — out of this mission's surface; noted as the natural follow-up if per-account granularity in discovery is ever needed. (c) *Route-level `requireAuthentication()` on `api.discovery`* — rejected: a 401 envelope breaks scenario 1's shape ("Given an anonymous caller *listing the index*"), and the `_public` route assertion in the Phase7 integration test is part of the documented contract; body-level filtering preserves the endpoint while removing the leak.

## D2 — Discoverable flag placement (FR-002)

**Decision**: Additive `discoverable: bool = true` constructor parameter on `EntityType` (trailing, named-param construction is the framework norm) + `isDiscoverable(): bool` accessor + a `bool $discoverable = true` passthrough on `fromClass()`. **`EntityTypeInterface` is not widened.** The discovery controller reads the flag duck-typed: `!method_exists($definition, 'isDiscoverable') || $definition->isDiscoverable()` — definitions not exposing the method are discoverable (open default preserved).

**Rationale**: The interface has seven anonymous-class test implementors across cli/listing/relationship packages — outside this mission's owned surface; widening it would force edits there for zero production benefit (the only production implementor is `EntityType`). The `method_exists` seam is the framework's established pattern (`EntityRepository::loadRevision()` hydration; alpha.205 WP01 forward seam). Default `true` preserves current behavior for every existing registration (C-004: the flag is the only new vocabulary). The flag gates the *index listing only* — CRUD routes for non-discoverable types keep registering and keep enforcing access normally; discoverability is visibility, not authorization.

**Alternatives considered**: (a) Widen `EntityTypeInterface` and fix the seven fixtures — clean but crosses WP ownership into four unrelated packages for an interface only one production class implements; deferred to whenever the interface next changes for its own reasons. (b) A `hidden`/`internal` group convention on `getGroup()` — rejected: overloads a presentation field with security semantics. (c) Config-file driven opt-out list — rejected by C-004 explicitly.

## D3 — 404 shape reuse + debug-mode question (FR-003, NFR-002)

**Decision**: Inside `JsonApiController::show()`, both the missing branch and the view-denied branch return the result of one new **private** `notFoundDocument(string $entityTypeId, int|string $id): JsonApiDocument` factory — the existing `JsonApiError::notFound("Entity of type '{$entityTypeId}' with ID '{$id}' not found.")` construction moved verbatim. The denied branch keeps running the access check (the entity must not be serialized!) but discards the result's reason and returns the factory output. Status code, title, detail, and the *absence* of the `code` member are thereby identical bytes; headers are identical because both documents exit through the single `jsonApiResponse()` emitter in `JsonApiRouter`. The NFR-002 pin test constructs both cases against the same controller and asserts `json_encode($denied->toArray()) === json_encode($missing->toArray())` and equal `statusCode`. **No debug/development-mode distinction is implemented** — the 404 is uniform in all environments.

**Rationale**: A single construction site is the only durable way to keep "byte-identical" true through future edits — two call sites with the same literal *will* drift. On debug mode: scenario 2's "may surface the distinction" is permissive, not required; `APP_DEBUG` is not plumbed into `JsonApiController` today, adding it would create a new constructor/config surface (against the mission's minimality and adjacent to C-004), and a conditional response shape is precisely the kind of branch that re-opens the oracle under misconfiguration. Operators diagnosing access issues have the audit log (`entity` access decisions) and the admin surface. Documented as a deliberate non-implementation.

**Scope boundary (FR-004)**: `store`/`update`/`destroy`/field-edit denials keep `JsonApiError::forbidden()` — FR-003 is explicitly single-read. Residual: PATCH/DELETE on a view-denied entity still 403s, leaking existence to authenticated callers only (those routes are `requireAuthentication()`). Accepted; recorded in the contract and plan Risks.

## D4 — Bearer constant-time comparison + blocked-state seam (FR-005, FR-006)

**Decision**: `BearerTokenAuth::authenticate()` is rebuilt in two moves. **(1) Constant-time scan**: replace the array lookup with a full iteration over the token map — `hash_equals((string) $candidate, $token)` per entry, accumulating the match without early exit, single return after the loop. The `(string)` cast is load-bearing (PHP coerces numeric-string keys to `int`; `hash_equals` requires strings). **(2) Blocked check, fail closed**: when a match is found, reject it (`return null`) if the account duck-types as inactive — `method_exists($account, 'isActive') && !$account->isActive()`. A rejection is indistinguishable from an unknown token (no distinct error). Accounts not exposing `isActive()` authenticate as before. `getTokens()` is untouched.

**Rationale**: `hash_equals` is PHP's purpose-built constant-time comparator; scanning *all* candidates without break makes the comparison constant-time over the candidate set, not just per-string (FR-005's wording). For FR-006, the spec assumes "blocked/inactive state is readable from the already-resolved account object" — true only by duck-typing: `AccountInterface` has no status member, and widening it is a framework-wide breaking change far beyond this mission. `User::isActive()` is the framework's canonical liveness accessor (used by `UserAccessPolicy`, mirrored by the session login query's `status = 1` condition — the bearer path is the one surface missing the equivalent check). Freshness needs no extra machinery: kernels (and thus token maps and their account objects) are per-request in every runtime, so the in-memory read reflects current DB state as of this request's boot — zero added queries (NFR-003).

**Alternatives considered**: (a) `instanceof \Waaseyaa\User\User` — rejected: adds an `mcp → user` manifest edge for a type check duck-typing does for free, and excludes app-custom account entities that also expose `isActive()`. (b) Adding `isActive()`/`isBlocked()` to `AccountInterface` — rejected: breaks every implementor (AnonymousUser, DevAdminAccount, OIDC/test stubs, app accounts) for one consumer; the right move only if a second consumer materializes. (c) Per-request DB re-load of the account by id — rejected by NFR-003 (adds a query) and unnecessary given per-request kernel construction. (d) Hashing tokens at construction and comparing digests — equivalent security to `hash_equals` here with extra moving parts; rejected for simplicity.

## D5 — Path resolution seam (FR-007)

**Decision**: `DatabaseBootstrapper::resolvePath()` becomes the canonical resolver: after the existing `config['database']` → `WAASEYAA_DB` → default precedence, any **relative** result is absolutized as `$projectRoot . '/' . $relative` (after stripping a leading `./`). "Absolute" (passes through untouched) = `:memory:`, leading `/`, Windows drive-letter (`/^[A-Za-z]:[\\\/]/`), or UNC (`\\\\` prefix). A `../`-climbing relative concatenates onto the project root and resolves naturally (spec edge case). The unset default already produces `$projectRoot . '/storage/waaseyaa.sqlite'` — byte-identical (scenario 5). Because `AbstractKernel:197` is the sole production callsite and every runtime (HttpKernel via `public/index.php`, ConsoleKernel via `bin/waaseyaa`, queue workers via CLI) boots through it, one fix covers HTTP, dev server, CLI, and queue. The CLI's parallel `DbInitHandler` resolution adopts identical rules — including absolutizing `config['database']` (verbatim passthrough today) and Windows-aware absolute detection — so `db:init` and the kernel can never disagree again. `HealthReportHandler` and `AboutHandler` display the resolved path instead of the raw env value.

**Rationale**: Fixing resolution where the path is *consumed* (the bootstrapper) rather than where env is read keeps the precedence rules in one place and automatically covers config-file values, which have the same CWD bug. `$projectRoot` is already a constructor-validated invariant of every kernel (HTTP: `dirname(__DIR__)` of the front controller; CLI: `getcwd()` gated on `composer.json` presence per ADR-005) — exactly the "documented project root" FR-007 names.

**Alternatives considered**: (a) `chdir($projectRoot)` at kernel boot — rejected: mutates global process state for every other path consumer and is hostile to embedding/testing. (b) Fix only the env read site and leave config values verbatim — rejected: leaves the same bug one config key away, and `DbInitHandler` proves config-sourced relatives already diverge today. (c) `realpath()`-based normalization — rejected: `realpath()` fails on not-yet-created files (the db is created on first boot); lexical join is sufficient and testable.

## D6 — Docroot warning (FR-008)

**Decision**: `DatabaseBootstrapper::boot()` gains a trailing `?LoggerInterface $logger = null` (Waaseyaa logger, NullLogger fallback — the framework's standard optional-logger ctor pattern); `AbstractKernel:197` passes `$this->logger`, which is always initialized before the database boots (`:120-151`). After resolution, the bootstrapper performs a lexical containment check — normalize separators, resolve `.`/`..` segments — of the resolved path against `{projectRoot}/public`; when contained, it logs `warning` with both the resolved path and the docroot, advising `WAASEYAA_DB` correction. Boot proceeds (a warning, not a guard — existing deployments that genuinely serve from elsewhere must not be broken). `:memory:` never warns.

**Rationale**: The warning's purpose is the #1650 failure narrative — a *stray second database silently created in the docroot*; after D5 the stray can only occur when someone explicitly points `WAASEYAA_DB` (or config) into `public/`, which is both a data-exposure risk (the SQLite file becomes a downloadable URL under `php -S` passthrough and naive static configs) and almost certainly a mistake. `{projectRoot}/public` is the framework's only docroot notion (front controller location). Logging at the bootstrapper (not the kernel) keeps the path knowledge and the check in one class, unit-testable with a spy logger.

**Alternatives considered**: (a) Refusing to boot — rejected: FR-008 says "warning", and a hard failure on upgrade would violate the alpha-but-gentle posture of scenario 5. (b) Warning from `AbstractKernel` after boot returns — rejected: the kernel would need to re-derive the resolved path (not returned today); the bootstrapper already owns it. (c) `realpath()`-based containment — rejected: the db file may not exist yet at first boot; lexical normalization is deterministic and covers the climbing-`..` forms the tests pin.

## Performance note (NFR-001, NFR-003)

Discovery filtering: one `isAuthenticated()` call per request, one duck-typed accessor read per registered type — bounded by type count, no I/O. Denied-as-404: strictly *removes* work (no reason serialization differences). Bearer: the scan is O(#tokens) `hash_equals` calls on in-memory strings (token maps are operator-curated and small — single digits in every known deployment); the blocked read is an in-memory field access. Path resolution: string operations at boot, once per process. Nothing here is measurable above noise; no perf smoke is warranted beyond the unit pins.
