## Verified ground truth

**SaveContext (the Mission 1/2 seam, C-004)**

- `SaveContext` is a final immutable value object with a private constructor and `with*()` builders (`packages/entity-storage/src/SaveContext.php:23-60`). The newest builder precedent is `withActorUid(?int)` from mission revision-audit-provenance-01KTWY5V (`:83-93`): trailing private ctor params + accessor methods, every existing builder re-threads the new fields. `withExpectedRevisionId()` follows this exact shape.
- The actor pair uses a two-member pin (`$actorUid` + `$actorOverridden`) because `withActorUid(null)` is meaningful (force NULL author). For revision expectations a `null` expectation is NOT meaningful — there is no "I expect no revision" head state on a persisted revisionable row (revision 1 exists from the first save) — so a single `?int` member suffices: `null` ⇔ no expectation stated (D1 design detail).
- `SaveContext` reaches storage only through `EntityRepository::save(EntityInterface, bool $validate = true, ?SaveContext $context = null)` (`packages/entity-storage/src/EntityRepository.php:354-357`). `saveMany()` takes no context (`:364-384`) and its `doSave()` calls pass `saveContext: null` implicitly (`:379`) — an expectation cannot be stated through `saveMany()` today; nothing to reject there (D6).

**`doSave()` flow (the write path the check must live in)**

- Order today (`EntityRepository.php:438-630`): resolve context + actor (`:444-450`) → **validation** (Mission 1, `:452-463`) → **original-entity load** `$originalEntity = $this->find($id)` for non-new entities (`:465-469`) → `preSave()` + `PRE_SAVE` event (`:471-479`) → `shouldCreateRevision()` (`:481`) → `BeforeSaveEvent` (`:489-493`) → translatable id allocation (`:504-512`) → **transaction** `$transaction = ($unitOfWork === null) ? $this->database?->transaction() : null` (`:516`) → revision write `writeRevision(...)` sets `$values['revision_id']` (`:524-531`) / or in-place `updateRevision()` when not revision-creating (`:532-537`) → bundle partition (`:539-557`) → base write `$this->driver->write($entityTypeId, $id, $baseValues)` (`:559`) → deferred-revision pointer update (`:566-581`) → commit/rollback (`:583-587`) → post events.
- **Single saves ARE transaction-wrapped** when a `DatabaseInterface` is wired (`:516`); inside `saveMany()` the UnitOfWork transaction wraps instead (and `$transaction` stays null — the guard UPDATE participates in the outer transaction because it runs on the same connection). `$this->database` is nullable: driver-only constructions (no DatabaseInterface) get NO transaction — relevant to D6.
- The loaded head's revision id is readable two ways: `$originalEntity->getRevisionId()` (`RevisionableEntityTrait::getRevisionId()` reads `values['revision_id']`, `packages/entity/src/RevisionableEntityTrait.php:149-158`), and the raw base row's `revision_id` pointer column via `$this->driver->read()` (the pattern `loadRevision()` already uses, `EntityRepository.php:700-701`).
- **The repository already issues targeted base-row UPDATEs through `DatabaseInterface` directly**: the deferred-revision pointer update (`:574-577`) and `setPublishedRevision()`'s single-column update (`:952-956`) both do `$this->database->update($table)->fields([...])->condition($idKey, $id)->execute()`. This is the established seam for a guarded pointer UPDATE (D1).
- `UpdateInterface::execute(): int` returns the affected-row count (`packages/database-legacy/src/UpdateInterface.php:13`; `DBALUpdate::execute(): int`, `packages/database-legacy/src/Query/DBALUpdate.php:41`) — the guard's success/failure signal.
- `SqlStorageDriver::write()` (`packages/entity-storage/src/Driver/SqlStorageDriver.php:181-239`) is unconditional: existence check by id → INSERT or UPDATE keyed only on `$this->idKey` (plus community scope). It owns the `_data` split (`splitForWrite`, `:667-707`) — duplicating that in the repository for a guarded full-row write would fork the column-routing convention; the guard must therefore be a *separate, minimal* pointer-claim UPDATE, not a replacement of `driver->write()` (D1).
- `EntityStorageDriverInterface::write()` cannot be widened with a guard parameter — PHP requires implementors to redeclare optional interface params, so it would break `InMemoryStorageDriver` plus every test driver (the same fixture-blast-radius reasoning as Mission 3's D2 against widening `EntityTypeInterface`).
- `shouldCreateRevision()` (`:1489-1516`): non-revisionable type → false (and invariant #9 throws if the entity demands a revision); new → true; entity `isNewRevision()` override; else `getRevisionDefault()`. So a save on a revisionable type can legitimately be **non-revision-creating** (auto-save / `withoutNewRevision` / `revisionDefault: false`) — that path UPDATEs the current revision in place (`:532-537`) and the head pointer does not move. Relevant to D1's soundness boundary and D6.

**Non-revisionable change marker (scenario 6 — the load-bearing question)**

- Base tables materialise **system keys + `_data` only** — id/uuid/bundle/label/langcode + the revision pointer when revisionable (`SqlStorageDriver::splitForWrite()` docblock `:654-666`; `SqlSchemaHandler::buildTableSpec` referenced there). There is **no universal `changed`/`updated` timestamp column**: `grep -rn "changed"` over `packages/entity/src/EntityBase.php`, `ContentEntityBase.php`, and `packages/entity-storage/src/Schema/*.php` finds only `translation_changed` on the sql-COLUMN translation sibling (`TranslationSchemaHandler.php:351`). Individual entity types may carry an ad-hoc `changed` field in `_data`, but `_data` keys are not schema-guaranteed, not monotonic, and not comparable atomically in a guard UPDATE (the value lives inside a JSON blob).
- **Conclusion: no reliable per-save change marker exists for non-revisionable types.** Scenario 6's fallback governs: expectation on a non-revisionable type is **cleanly rejected as unsupported** (D2).

## D1 — Race-safe conflict-check mechanism (FR-001, FR-004, NFR-001)

**Decision**: Two-stage check inside `EntityRepository::doSave()`, active **only when `SaveContext::expectedRevisionId()` is non-null**.

1. **Fail-fast pre-check (before any write, before any lifecycle event)**: immediately after the existing original-entity load (`:465-469`), compare the expectation against the loaded head — `$originalEntity?->getRevisionId()`. Mismatch (or `$originalEntity === null` — row vanished) → throw `RevisionConflictException` carrying expected + current. Zero added queries: the head is already loaded for every non-new save. This satisfies FR-001's "refused **before any write**" for every non-racing conflict, and it runs **after validation** (Mission 1 order: validation first, then the conflict check) and *before* `preSave()`/`PRE_SAVE`/`BeforeSaveEvent` — a refused save dispatches no lifecycle events and calls no entity hooks.
2. **Authoritative guarded pointer-claim (the race closure, FR-004)**: inside the existing write transaction, after `writeRevision()` returns the fresh `$newRevisionId` and **before** `driver->write()`, the repository issues one targeted UPDATE through the established `DatabaseInterface` seam (the deferred-revision/`setPublishedRevision` pattern):

   ```
   UPDATE <base> SET <revisionKey> = :newRevisionId
   WHERE <idKey> = :id AND <revisionKey> = :expected
   ```

   `UpdateInterface::execute(): int` returns affected rows. `1` → the claim holds; proceed with the normal full `driver->write()` (which re-writes `revision_id` to the same value — harmless, same transaction). `0` → a competing writer moved the head between the pre-check and the claim → roll back (the freshly inserted revision row rolls back with the transaction), re-read the base row for the now-current revision id, throw `RevisionConflictException`. The affected-rows signal is **unambiguous on every backend** because the SET always changes the value (`$newRevisionId` is freshly allocated, never equal to `:expected`) — MySQL's no-change-rows-not-counted behavior cannot produce a false 0.

   Atomicity: two concurrent saves stating the same expectation both insert revision rows, but only one claim UPDATE matches `revision_id = :expected`; the loser's transaction (revision row included) rolls back. Under SQLite the writers serialize on the database write lock; under InnoDB/Postgres the second claim blocks on the row lock until the first commits, then matches 0 rows. Exactly one winner (NFR-002).

**Soundness boundary**: the claim mechanism requires the head pointer to MOVE, so an expectation is honored only on **revision-creating** saves (`shouldCreateRevision() === true`) of **single-axis revisionable** types (revisionable, not translatable) through `save()`, with a `DatabaseInterface` wired. Everything outside that boundary rejects explicitly — see D2/D6. (Two-axis types share the base `id` across langcode peer rows, so an id-keyed claim could match/move the wrong peer; the in-place `updateRevision()` path doesn't move the pointer at all, so a claim on it would be the MySQL-ambiguous no-change UPDATE.)

**Rationale**: It is the cheapest sound option grounded in what exists: the pre-check rides a load that already happens (NFR-001's zero-added-queries holds trivially for the no-expectation path — every new branch is gated on `expectedRevisionId() !== null`); the claim is one indexed single-row UPDATE on the expectation path only, issued through a repository→DatabaseInterface seam with two in-file precedents; no interface is widened, no driver duplication of `splitForWrite`, no new isolation-level assumptions (a plain in-transaction re-read would NOT be race-safe under MVCC consistent reads).

**Alternatives considered**: (a) *Guarded full-row write in `SqlStorageDriver::write()`* — widening `EntityStorageDriverInterface::write()` breaks every implementor (PHP optional-param redeclaration rule); a new concrete-only `writeGuarded()` duplicates the write path for one consumer. Rejected; the pointer claim composes with the existing unconditional write instead. (b) *`SELECT … FOR UPDATE` on the base row* — not expressible through the query-builder surface (`SelectInterface` has no locking clause), driver-specific syntax, and unnecessary given (2). (c) *Re-read inside the transaction and compare* — not race-safe on MySQL/Postgres read-committed MVCC (both writers see the old head); only accidentally safe on SQLite. (d) *Version column with per-save increment (classic optimistic locking)* — a schema change; C-001 forbids schema beyond what revision tracking provides, and `revision_id` IS the monotonic version.

## D2 — Non-revisionable types: explicit rejection (FR-007, scenario 6)

**Decision**: An expectation stated on a save of a **non-revisionable** entity type throws `\LogicException` with a message naming the type and the reason ("entity type '<id>' is not revisionable; revision expectations require revision tracking") — before validation, before any load (the check needs only the definition). Documented in the contract and the CHANGELOG: non-revisionable types have **no framework change marker** (verified: base tables carry no `changed` column; `_data` keys are not schema-guaranteed or atomically comparable), so scenario 6 resolves to the spec's "cleanly rejected as unsupported" arm.

**Rationale**: A wrong conflict check is worse than none. Any marker we could improvise (a `changed` field in `_data`) is non-monotonic, app-defined, and unreadable inside a guarded UPDATE (JSON blob), so it cannot satisfy FR-004's race-safety; pretending otherwise would ship a TOCTOU check. `\LogicException` (not `RevisionConflictException`) is correct: this is a caller programming error, not a data race — mirroring the repository's existing invariant style (`shouldCreateRevision()` invariant #9, the `assertTwoAxis()` guards). Apps that need stale-edit protection on a type can flip it `revisionable: true` (+ `revisions:enable` backfill) — that is the framework answer, documented in the quickstart.

**Alternatives considered**: (a) *Add a universal `changed` column* — a schema migration for every base table; explicitly outside C-001. (b) *Hash-the-row as marker* — non-monotonic, ABA-prone, and the compare still isn't expressible as a sound guard. (c) *Silently ignore the expectation on non-revisionable types* — violates FR-007's letter and the edge case "never silently ignore a stated expectation".

## D3 — Tool argument + structured conflict error (FR-005, NFR-003)

**Decision**: `EntityUpdateTool` gains an optional top-level `expected_revision_id` argument (JSON Schema `['type' => 'integer', 'minimum' => 1]`; named with the `expected_` prefix to keep it visibly distinct from the `revision_id` *column*, which `EntityKeyGuard` already refuses inside `values`). Execute path: when present and valid, the save call becomes `$repository->save($entity, context: SaveContext::default()->withExpectedRevisionId($expected))` — guarded by `$repository instanceof EntityRepository` (the `EntityDestination` precedent; a non-concrete repository with a stated expectation returns a structured `revision_expectation_unsupported` error rather than silently ignoring it, FR-007). `RevisionConflictException` is caught **before** the generic `\Throwable` arm (the `EntityValidationException` precedent) and mapped to the Mission 1 error shape:

```php
new AgentToolResult(isError: true, content: [
    ['type' => 'text', 'text' => $message],
    ['type' => 'json', 'data' => [
        'error' => 'revision_conflict',
        'entity_type' => $e->entityTypeId, 'id' => $e->entityId,
        'expected' => $e->expectedRevisionId, 'current' => $e->currentRevisionId,
    ]],
], summary: $message);
```

`\LogicException` from the unsupported-path rejections surfaces as a structured `revision_expectation_unsupported` error (same two-block shape). The success payload additionally carries the post-save `revision_id` (read back from the entity — `writeRevision` sets it) so an agent can chain edits without a re-read. **Dry-run** (edge case): when `expected_revision_id` is present, dry-run loads the entity (it currently loads nothing) and compares the head — a mismatch returns the byte-identical `revision_conflict` payload a real call would produce; a match keeps today's `would_update` success. Deterministic and assertable: payload content is exactly the two revision ids plus static identity (NFR-003).

**Rationale**: Mission 1 established the two-block error contract (`EntityKeyGuard::refusalError()`) and the catch-specific-then-generic execute shape; C-004 forbids parallel vocabulary, so the expectation rides `SaveContext` (not a new entity-level mutator à la `setRevisionLog`, which was considered and rejected as a second way to say the same thing). The concrete-class guard is honest about the `EntityRepositoryInterface::save()` signature gap without widening an interface that six packages' test fixtures implement.

**Alternatives considered**: (a) *`revision_id` inside `values`* — already refused by `EntityKeyGuard` (kind `revision`), and overloading a write-payload key as a precondition conflates data with expectation. (b) *Widening `EntityRepositoryInterface::save()` with the context param* — breaks every fixture implementor (PHP optional-param redeclaration); deferred to whenever the interface next changes for its own reasons. (c) *Entity-carried `setExpectedRevisionId()`* — parallel vocabulary (C-004); SaveContext is the canonical per-save flag carrier.

## D4 — API seam + status (FR-006)

**Decision**: The PATCH body carries the expectation as **resource-object meta**: `data.meta.expected_revision_id` (integer). Grounded: the controller receives only the parsed body (`JsonApiRouter:61`; `WaaseyaaContext` exposes no headers), so a true `If-Match`/ETag implementation is not reachable without widening foundation's router context — out of this mission's surface and documented as the rejected alternative (an additive follow-up can map `If-Match: "rev-N"` onto the same SaveContext seam later). Behavior in `update()`:

- Non-integer/invalid `data.meta.expected_revision_id` → 400 `badRequest`.
- Expectation on a type that is not single-axis revisionable → 422 `unprocessable` (mirror of the storage rejection, screened up front via the definition so the error is friendly; the storage `\LogicException` remains the invariant backstop).
- Expectation stated → the save flows through `getRepository($entityTypeId)->save($entity, context: SaveContext::default()->withExpectedRevisionId($n))` — the revision-aware repository pipeline — instead of the `getStorage()` legacy path (which has no revision support and no context parameter; verified). `EntityValidationException` from the repository path maps to 422. **No expectation → the existing `getStorage()->save()` line is untouched, byte-identical (FR-003/SC-003).**
- `RevisionConflictException` → **409** via `JsonApiError::conflict()` widened additively (`code` + `meta` optional params; `JsonApiError` gains a `meta` member emitted by `toArray()` when non-empty — JSON:API error objects define `meta`; existing construction sites are ≤3 positional args, safe): `code: 'REVISION_CONFLICT'`, `detail` naming the entity, `meta: {expected_revision_id: N, current_revision_id: M}`.

**Rationale**: `data.meta` is JSON:API-conformant ("the revision of the resource I am sending"), needs zero new plumbing, and lands in the member the controller already validates structurally. 409 is both the JSON:API guidance for unresolvable resource-state conflicts and this controller's existing precedent (the `data.id`-vs-uuid mismatch at `:349-355`); the `code` member disambiguates the two 409 shapes machine-readably. Routing expectation-stated saves through the repository is the honest consequence of grounding: the storage path cannot carry a context and does not move revisions, so a "conditional update" through it would be a lie; opting in to an expectation opts in to the standard persistence pipeline (FR-001's words). This asymmetry is documented in the contract and CHANGELOG (an expectation-stated PATCH on a revisionable type cuts a revision — exactly what a conflict-checkable write means).

**Alternatives considered**: (a) *`If-Match` weak ETag* — the orthodox HTTP seam, unreachable from the controller today (no headers in `WaaseyaaContext`); widening foundation's context for one consumer fails the minimality bar; noted as the natural additive follow-up. (b) *Top-level `meta.expected_revision_id`* — document-level meta is "about the request", resource-level meta is "about this resource"; `data.meta` is the tighter fit and survives alongside the existing `data.*` validation. (c) *Always saving through the repository* — changes no-expectation PATCH behavior (events, validation, revision cuts) and violates FR-003/SC-003.

## D5 — FR-008 exposure (current revision readable everywhere an expectation forms)

**Decision**: Minimal, mostly-pin work.

- **API reads**: already expose `revision_id` as an attribute on revisionable types (serializer excludes only id/uuid; the pointer column rides `toArray()` — verified). WP02 pins it with a test on `show()` and the contract documents it as load-bearing (removing it would break expectation-forming clients).
- **`entity.read` tool**: gains a top-level `revision_id` member (from `getRevisionId()`, duck-typed) next to `entity_type`/`id` — deterministic regardless of whether a curated `getValues()` includes the column. Non-revisionable types omit the member.
- **`entity.list` tool**: items gain the same optional `revision_id` member (entities are already fully loaded; zero added queries).
- **`entity.list_revisions`**: already exposes per-revision `revision_id` — unchanged.
- **Conflict payloads themselves** carry `current` (tool) / `meta.current_revision_id` (API), so the recover-and-retry loop needs no extra read.

**Rationale**: FR-008 asks for readability "wherever a caller needs to form an expectation" — the read/list surfaces feeding the two update surfaces. Top-level placement in tool payloads keeps the id out of the writable-values vocabulary (consistent with `EntityKeyGuard` refusing it as a value) and makes it assertable (NFR-003).

## D6 — Rejection semantics for unsupported paths (FR-007, edge cases)

**Decision**: One uniform rule — **a stated expectation that cannot be honored throws `\LogicException` at the storage layer; it is never silently dropped.** The rejection matrix (each with a distinct, greppable message):

| Path | Behavior |
|---|---|
| New (unsaved) entity + expectation | `\LogicException` — caller error: "cannot expect a revision on an unsaved entity" (checked on `isNew()`, before any write). |
| Non-revisionable type + expectation | `\LogicException` (D2). |
| Two-axis type (revisionable + translatable) + expectation | `\LogicException` — per-language tips are a different concurrency domain (`saveTranslation*` paths); the id-keyed pointer claim is unsound across langcode peer rows. Liftable later with a langcode-scoped guard. |
| Non-revision-creating save (`withoutNewRevision()`, `setNewRevision(false)`, `revisionDefault: false`) + expectation | `\LogicException` — the head pointer does not move, so no unambiguous claim exists (MySQL no-change UPDATE counts 0); callers force a revision (`setNewRevision(true)`) to get a checkable save. |
| No `DatabaseInterface` wired + expectation | `\LogicException` — no transaction, no guard (mirrors the existing `saveMany()` requires-database precedent). |
| `rollback()`, `setCurrentRevision()`, `setPublishedRevision()`, `saveTranslation()`/`saveTranslationRevision(s)()`, `saveMany()` | **No SaveContext parameter exists on these signatures** — an expectation cannot be stated, so nothing can be silently ignored (the edge case's failure mode is unreachable). Documented in the contract; threading SaveContext through them is future additive work. |

Surfaces translate the `\LogicException` family into their own vocabulary (tool: structured `revision_expectation_unsupported`; API: 422) but the storage layer is the invariant.

**Rationale**: FR-007's verb is "reject explicitly"; `\LogicException` is the repository's established invariant-violation idiom (revision driver not configured, `assertTwoAxis`, saveMany-requires-database). Each carve-out is a soundness boundary from D1's mechanism, not a convenience — and each message says what to do instead.

## Performance note (NFR-001)

No-expectation saves execute byte-identical code: every new branch is behind `expectedRevisionId() !== null` (one null check per save). Expectation-stated saves add exactly one single-row indexed UPDATE (the claim) on success and one single-row read (current-head re-read) on the racing-conflict path. The pre-check reuses the original-entity load that `doSave()` already performs for every update. Pinned by a query-count test (WP01) using a counting `DatabaseInterface` decorator.
