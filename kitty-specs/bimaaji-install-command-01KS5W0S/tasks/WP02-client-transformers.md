## Objective

Ship the `ClientTransformerInterface` + 7 concrete transformers + 7 unit-test files. Each transformer converts the parsed skill set into the client's expected file format(s).

## Subtasks

### T003 — Per-client convention verification

Before writing any transformer, verify each client's current config-file convention against the client's official documentation (cite the URL + date in the transformer's class-level docblock). Update the AD-02 table in `plan.md` if any client has moved.

Document in `docs/specs/bimaaji-install.md` §"Supported clients" (skeleton from WP01).

### T004 — `ClientTransformerInterface`

```php
namespace Waaseyaa\Bimaaji\Install;

/**
 * @api
 */
interface ClientTransformerInterface
{
    public function clientId(): string;

    /**
     * @param list<ParsedSkill> $skills
     * @return list<TargetFile>
     */
    public function targetFiles(array $skills): array;
}
```

`ParsedSkill` is a simple DTO (`name`, `description`, `frontmatter`, `body`). `TargetFile` is `{path: string (relative to project root), content: string, source_skill: ?string}`. Both DTOs live alongside the interface.

Mark `@api`. The dead-code gate will otherwise flag the DTOs.

### T005 — Multi-file transformer (Claude)

`ClaudeClientTransformer::targetFiles()`:

- One `TargetFile` per skill: `.claude/skills/waaseyaa-<skill-id>.md` (where `<skill-id>` is derived from the directory name, e.g. `entity-system`).
- Plus one shared guidelines file at `.claude/CLAUDE-WAASEYAA.md` (or appended-to `CLAUDE.md` per the WP01 convention decision).

### T006 — Single-file transformers (6 clients)

For Cursor / Codex / Copilot / Gemini / Windsurf / Junie: each transformer returns one `TargetFile` whose content is a concatenation of:

1. A standardized prelude ("Waaseyaa framework conventions — auto-generated by `bin/waaseyaa bimaaji:install`, do not edit between the markers below")
2. Each skill's body, separated by `\n\n---\n\n` and prepended with the skill name as an H2
3. A closing marker

The marker convention (begin/end tokens) supports merge logic if WP03 ever adds a `--merge` mode.

### T007 — Unit tests per transformer

For each transformer in `packages/bimaaji/tests/Unit/Install/<Client>ClientTransformerTest.php`:

- `returnsCorrectClientId`
- `producesExpectedTargetFileCount` (1 for single-file clients; `count($skills) + 1` for Claude)
- `producesNonEmptyContentForEachTarget`
- `firstFileSampleHasPreludeAndAtLeastOneSkillBody` — confirms structure with a known fixture skill set
- `respectsFrontmatterStripping` (FR-005 — body is preserved, frontmatter is dropped from emitted content)

Use a small fixture skill set in `packages/bimaaji/tests/Fixture/Skills/` (3 small skills) so tests don't depend on the live `skills/waaseyaa/*` content.

## Risks and notes

- **Convention drift:** Per R1, client config conventions change. The class docblock URL + date is the audit trail — when WP05 runs the manual smoke, any conventions that have moved show up immediately.
- **Single-file token budget:** If Cursor's `.cursorrules` has a documented limit that's smaller than the full skill set, the transformer needs a truncation strategy. Document in the transformer's docblock and surface in WP05 verification.md.
- **Shared base class:** All 6 single-file transformers share substantial logic. Either extract a `SingleFileClientTransformer` abstract base or accept the duplication for clarity. Both are acceptable — `@api`-mark whichever you extract.
