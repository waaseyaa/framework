- **Fixed — `oidc_client.client_id` is now a database-enforced unique registry identity, and every pre-auth control fails closed on a collision instead of picking an arbitrary row (#2766):** `OidcClient` documented `client_id` as its stable public identifier, but the framework never declared or materialized a uniqueness constraint for it; the supported `sql-blob` repository accepted multiple rows sharing a `client_id`, and `OidcClientLookup::findByClientId()` silently selected `$ids[0]` from any multi-match result — an incidental query-order decision, not registry authority, on the exact pre-auth path the authorize, token (`authorization_code` and `refresh_token` grants), and revoke controls all share. A new migration (`2026_09_06_000009_oidc_client_id_unique_key`) materializes a partial unique index (`WHERE client_id <> ''`, so pre-migration blank rows never block or collide) on fresh installs and existing databases alike; if historical duplicate `client_id` values already exist it throws `DuplicateClientIdException` and creates no index — no row is ever deleted or merged automatically, and an operator must resolve the reported duplicates before re-running. `OidcClientLookup::findByClientId()` now throws `AmbiguousClientIdException` (rather than selecting a row) if more than one match is ever returned — a defense-in-depth backstop for a database that has not yet run the new migration. `OidcClientSeeder` now shares that same lookup (removing a second, independent query-then-create duplication) and recovers from a genuine concurrent-boot race by catching the real `UniqueConstraintViolationException` the physical unique key raises and updating the concurrent winner's row in place, rather than crashing the boot or leaving two rows. `sql-column` remains explicitly unsupported for this entity shape (its three list-valued fields have no column-encoding contract and raise `UnstorableFieldException`, pinned by a new regression test); `sql-blob` is the one and only supported layout, now documented on the entity itself.
