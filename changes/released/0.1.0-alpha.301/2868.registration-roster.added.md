- **Added — ADR-025 persists a registration roster, so retirement can withdraw what it promises (#2868, ADR-025 D-2.1, D-2.1a):** D-2.3 step 6 and D-6.6 both obliged a declared retirement to withdraw *"exactly that unit's registrations"* from `composer.json`, while D-2.1 persisted no member from which that set could be computed — the unit record was the closed object `{id, disposition, generator, input_digest}`, and every other `registrations` in the decision belonged to the transient plan. Main therefore mandated a withdrawal it had no basis to perform, and a second gap followed from the same absence: exclusivity was stated for paths only (`GEN010`, "one path claimed by two units") while D-6.6 merged idempotently, so two units could declare the same provider FQCN and retiring either would silently break the survivor. D-2.1 now carries a top-level `registrations` list of `{fqcn, group?, unit?}` rows, sorted by `fqcn` then `group`, **omitted entirely when empty** so a registration-free document stays byte-identical to one produced before the member existed. Ownership is attributed exactly as `artifacts` already attributes paths: an absent `unit` key means the **root** unit owns the row — a per-unit member could not have expressed root ownership, because `units` holds one record per *non-root* unit, which would have left #2857's recipe-declared providers unrepresentable. New D-2.1a fixes the semantics: verbatim recording from the plan, global FQCN exclusivity, deterministic ordering, a disposition-split evolution matrix naming every transition (creation, addition, removal, `group` change, drift, and each refusal), root rows reconciled only by a root publish and never re-parented, and preview/apply parity whose only exceptions are `GEN008` at lock acquisition and `GEN005` staleness thereafter. A `seeded` unit's registration set is **frozen at creation** — apply-once makes a later declaration unenactable, so it is refused rather than ignored, because silence would be success-shaped. `group` is fixed as roster and plan metadata with **no `composer.json` representation**: the live surface is `extra.waaseyaa.providers`, a flat `list<string>` of FQCNs (`packages/foundation/src/Discovery/PackageManifestCompiler.php` lines 121-122 and 151), so a `managed` group change is a roster update with no Composer edit and `site:doctor` can only detect FQCN *absence*, never a group alteration. Emission conditions are independent: `units` and the per-artifact `unit` key appear only with non-root ownership, while `registrations` appears whenever its roster is non-empty — **including a root-only roster with no non-root unit in the document**, which is exactly the #2857 case. Four codes are reserved for four distinct questions: `GEN012_REGISTRATION_OWNERSHIP_CONFLICT` (this registration belongs to someone else — including a plan claiming an FQCN already present with no roster row, which is the silent-capture refusal), `GEN013_SEEDED_REGISTRATION_REDECLARED` (this declaration cannot be enacted), `GEN014_INVALID_COMPOSER_PROVIDER_STATE` (the Composer provider state on disk is not well-formed — not a list, a malformed or empty member, or a duplicate), and `GEN015_INVALID_REGISTRATION_ROSTER` (the persisted roster itself is not well-formed — a non-object row, an unknown member, a missing or wrongly typed `fqcn`/`group`/`unit`, or non-canonical ordering). The last two validate different documents, so a single code could not tell an operator which file to look at. D-5's self-counting prose — "these ten ids", "an eleventh id" — is replaced by a rule that cannot go stale, having already been falsified by `GEN011` in the amendment that added it.
