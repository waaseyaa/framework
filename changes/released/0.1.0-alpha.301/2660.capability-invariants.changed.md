- **Changed — every `bimaaji:install` client capability field is now executable, and the skill inventory is genuinely canonical (#2660 Part A repair round):** `ClaudeClientTransformer` now **derives** a per-skill file's leading YAML frontmatter block from `ClientCapabilities::$requiresFrontmatterAtByteZero` instead of emitting it unconditionally — the flag was previously never read by production code, so the registry drove only path and prefix and the split authority the registry exists to remove survived inside the transformer. The transformer takes an optional `ClientCapabilities` through its constructor (production still resolves the registered entry; an override declaring a different client id raises a `\LogicException`) so the derivation is provable in both directions: with the flag cleared a per-skill file is exactly `ManagedRegion::wrap($skill->body)`, and the shipped registry entry both declares the flag and produces bytes that open with frontmatter at byte 0. `Waaseyaa\Bimaaji\Install\ClientCapabilities` now closes its shape at construction and raises the new `Waaseyaa\Bimaaji\Install\ClientCapabilityException`: blank client ids, guidance paths, skill directories and skill-id prefixes are rejected, a `SingleConsolidatedFile` client may not carry a skill directory, a skill-id prefix or a frontmatter requirement (it emits no per-skill file for any of them to govern), and a `PerSkillFile` client must name its skill directory. `Waaseyaa\Bimaaji\Install\SkillInventory::fromSkills()` now sorts by skill id whatever order the caller passed and rejects duplicate ids with an `\InvalidArgumentException` naming the id, so `ids()` can no longer repeat an id and `find()` can no longer resolve a collision by position; it previously promised a canonical sorted inventory while only restating the caller's order. No file `bimaaji:install` writes to a consuming project changed — `TransformerOutputRegressionTest` still diffs all seven clients against the pre-refactor golden snapshot, byte for byte, unchanged.
