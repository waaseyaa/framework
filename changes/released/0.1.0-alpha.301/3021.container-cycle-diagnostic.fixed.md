- **Fixed — bound circular service resolution with an ordered diagnostic (#3021):** `ServiceProvider::resolve()` and `KernelHandlerContainer::get()` had no in-flight guard, so a binding factory or auto-wired constructor that resolved its own abstract (directly or through a cycle of others) recursed until the process exhausted memory or the stack. Both now track the in-flight resolution chain without PHP numeric-string key coercion (so `"0"` remains a string), funneled through the single `mergeChildProvider()` merge root so a cycle crossing a merged provider is still caught. They throw the new public `CircularServiceResolutionException`, a `\RuntimeException` subtype naming the ordered cycle (e.g. `A -> B -> A`) using only abstract identifiers, never factory arguments or resolved values; identifiers remain caller-controlled strings and require sink-appropriate encoding or redaction before logging. In-flight state is cleared via try/finally on every exit so a later, valid resolution is unaffected. `resolveOptional()`'s unbound-abstract behavior, the exact "No binding registered for {abstract}." message, and `KernelHandlerContainer`'s existing fall-through/re-throw rules are unchanged.
