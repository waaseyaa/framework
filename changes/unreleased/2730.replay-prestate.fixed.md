- **Fixed — a no-op migration replay can no longer re-baseline schema or ledger drift (#2730):** `SchemaMutationCoordinator::execute()` acquired schema authority, installed the ledger, ran the transition and then unconditionally recorded whatever schema and ledger were live as the new authority manifest, never reading the previous one. An unauthorised `ALTER TABLE`, or a hand-edited ledger row, that `migrate --verify` correctly reported as `schema_drift` / `ledger_drift` was therefore adopted as trusted state by the next unchanged `migrate` (count=0, success), and verify went green while the drift remained. The coordinator now validates prior state under the writer lock it has just taken and before the ledger install/upgrade: an install without a fingerprinted manifest is a fresh install or the #2452 adoption path and proceeds; a recorded manifest that no longer describes the live logical schema or canonical ledger refuses with `[S1-DB109]` inside the transaction, so schema, data, ledger, catalogue, manifest and authority generation stay exactly as found and verify keeps reporting the drift. Because the ledger upgrade runs after the check, a manifest recorded before `apply_mode` existed (the pre-#2701 window) still applies cleanly. `Migrator::run()` now rechecks every already-applied node — legacy and V2 — against its ledger row instead of `hasRun()` alone: package identity and the stored compiled-plan hash are refused with `[S1-DB112]`, a changed legacy source under the same id gets the same `CHECKSUM_MISMATCH` refusal V2 already had (production throws, development warns and skips), and the loaded catalogue fingerprint is recorded only after those checks pass, so a refused replay cannot rewrite the catalogue authority. `db:init` no longer installs or upgrades the ledger outside the coordinator, and the privileged-read ledger (`StrictLedgerSchema`) now creates its table through the coordinator on first use so a kernel boot cannot leave the manifest stale. Writer-first acquisition (#2446), whole-plan rollback, retry and the zero-DDL read paths are unchanged. Operators who have verified drift as benign re-adopt explicitly by clearing the recorded fingerprints (see `docs/specs/s1-schema-authority.md`, "Governed re-adoption"); the framework never re-baselines on its own.
