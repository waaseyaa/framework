- **Fixed — `cache:clear` discovers and clears the application's actually-configured cache bins, and reports truthfully what happened (#3025):** the handler previously could not even be constructed by the real CLI (`CacheFactoryInterface` had no binding anywhere in `ConsoleKernel`'s boot path, so every invocation of `cache:clear` failed with "No binding for ... in KernelHandlerContainer"); a hardcoded `['default', 'render', 'discovery', 'config']` list also stood in for the application's real bins (`render`, `discovery`, `mcp_read`), so `mcp_read` was never reachable and `default`/`config` printed "cleared" while only wiping a fresh, empty, throwaway backend. `CacheConfiguration::getConfiguredBins()` is now the canonical, deterministically-ordered accessor for "the bins this configuration registers" (covering both class-mapped and factory-registered bins); `AbstractKernel::buildCacheFactory()` is the single place `HttpKernel::finalizeBoot()` and the CLI's new `CacheFactoryInterface`/`CacheConfiguration` handler-container bindings compose the framework's production bins from, so the two boot paths cannot register a different set of bins from one another. The handler now enumerates that canonical list instead of the fixed one, catches per-bin failures so one refusing backend does not abort the rest, and reports success, partial failure, or total failure with a matching non-zero exit status rather than an unconditional "All cache bins cleared." An explicit `--bin` naming an unconfigured bin is reported as nothing-to-clear (exit 1), never a false "cleared." `--bin`/`--tags` option shapes, the tag-aware "skipping" message, and the "no bins support tag invalidation" message are unchanged. Does not assert this ever caused a production stale read: `mcp_read` is namespaced by a runtime epoch fingerprint that already makes prior-epoch entries unreadable independent of `cache:clear`, and the inventory gap that made the CLI command non-functional is the defect being fixed here, not an incident.
