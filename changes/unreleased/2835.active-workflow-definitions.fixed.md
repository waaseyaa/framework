A new `Waaseyaa\Workflows\Read\ActiveWorkflows` reader loads the distinct workflows named anywhere in `workflows.assignments` config via `EntityRepositoryInterface::findMany()` (never `getQuery()`, so the unbound-getQuery gate stays clean), bound as a singleton in `WorkflowServiceProvider::register()` and resolved by `HttpKernel` through the same `getHttpServiceResolver()` idiom used for the other optional cross-package HTTP services. No workflow bound, or a `core`-only install with no `waaseyaa/workflows` package at all, both now serve a well-formed `{ data: [] }` — the controller's no-provider default changed from the fictional preset to an empty result. `EditorialWorkflowPreset` itself is unchanged and still backs `EditorialTransitionAccessResolver`/`DefaultWorkflows`; only this one production wiring gap and this one fallback default moved. `WorkflowDefinitionsApiRouterTest` (new) proves the router-level contract end to end; `WorkflowDefinitionsControllerTest`'s prior pin on the retired preset default is deliberately replaced, not deleted.
