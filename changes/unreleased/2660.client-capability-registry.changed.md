- **Changed — `bimaaji:install` client transformers now read a typed capability registry and skill inventory instead of hardcoding per-client behaviour (#2660 Part A):** the seven `ClientTransformerInterface` implementations under `packages/bimaaji/src/Install/Client/` no longer hardcode a `targetPath()` override, or (for Claude) a `DIRECTORY_PREFIX` constant; they now read the same fact — single consolidated file vs per-skill files, whether a per-skill file needs YAML frontmatter at byte 0, and the client's guidance/skill path(s) — from the new `Waaseyaa\Bimaaji\Install\ClientCapabilityRegistry`, keyed by the new `ClientCapabilities` value object and `SkillDeliveryMode` enum. `BimaajiInstallCommand` now enumerates the canonical skill set through the new `Waaseyaa\Bimaaji\Install\SkillInventory` (wrapping `SkillSetParser::parse()`, called once, as before) rather than handling a raw `list<ParsedSkill>` inline. This is a behaviour-preserving refactor: `TransformerOutputRegressionTest` diffs every client's `targetFiles()` output against a golden snapshot captured from the pre-refactor implementation, byte for byte, for both a populated and an empty skill set, and the existing 107 install/transformer/command tests are unchanged and green. No file `bimaaji:install` writes to a consuming project changed. The registry mirrors the currently shipped convention for all seven launch clients (see `docs/specs/bimaaji-install.md` "Supported clients") — it does not encode the `.agents/skills/`-style Codex layout, unsupported-capability diagnostic severity, or root-guidance/skill-body division of labour that `docs/adr/025-client-guidance-and-skill-conventions.md` leaves as open maintainer decisions for the rest of #2660.
