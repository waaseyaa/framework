- **The Dependabot admin-dist rebuild now validates under a pinned interpreter,
  so admin dependency bumps stop dying on a stale `dist` (#2704).**
  `.github/workflows/dependabot-admin-dist.yml` deliberately splits an
  unprivileged `build` job (`contents: read`, where untrusted dependency code
  executes, pinning `shivammathur/setup-php` at 8.5) from a privileged
  `publish` job (`contents: write` + `actions: write`, which commits the
  rebuilt bundle and dispatches CI). `publish` sets up no PHP — that is the
  point of the split — yet it ran `php bin/admin-dist-acceptance verify`, so it
  executed the runner's *default* interpreter. Line 73 of that script uses
  `new AdminDistWorkspaceGuard()->assertAcceptable(...)`, the PHP 8.4+ "new
  without parentheses" form, which is a parse error on anything older
  (`syntax error, unexpected token "->"`, exit 255). The job died at validation
  and never reached "Commit rebuilt dist to the Dependabot branch", so the
  stale `packages/admin-surface/dist` survived every admin bump and each such
  PR failed the same fixed set of checks downstream of it —
  `ci/verify-gates` (`composer check-admin-dist-fresh`), the
  `AdminDistContentTest::shipped_bundle_build_identity_is_internally_consistent`
  shard, and the unit/coverage/random-order jobs carrying that test. `main`
  stayed green throughout, because nothing on the main CI path runs that script
  on a bare runner, so the breakage could sit indefinitely. It was observed
  simultaneously on four unrelated bumps: #2688, #2689, #2690 and #2691.
  The fix is **not** to add `setup-php` to `publish`: that would run a
  third-party action inside a boundary holding `contents: write` and
  `actions: write`, and the build/publish separation is the security property
  the workflow exists to keep. Validation moved into the unprivileged `build`
  job instead, where PHP 8.5 is already pinned — after `bin/build-admin-dist`
  generates the bundle and immediately before the artifact upload, which is the
  next step that touches those files. The #2524 guarantee that "the acceptance
  manifest must describe the bytes that just landed, not the bytes some other
  tree produced" is preserved rather than relaxed: the verifier reads
  `packages/admin-surface/dist`, `dist.signature` and `dist.manifest.json` at
  their repository paths, and those are exactly the three paths the upload
  publishes, so the validated tree and the uploaded tree are the same bytes.
  The artifact is immutable between the two jobs and `publish` installs it
  verbatim, so the manifest that lands is still the one verified against the
  dist beside it — and the committed result is independently re-derived on a
  clean runner with a pinned interpreter by `ci/verify-gates`
  (`composer check-admin-dist-manifest`), dispatched against the pushed head.
  `publish` keeps every shell-level check it had — the
  `dist dist.manifest.json dist.signature` entry-name allowlist, the
  non-regular-file rejection, and the `^[0-9a-f]{64}$` signature check — plus
  its commit and CI dispatch; it simply no longer invokes PHP.
  `tests/Architecture/AdminDistWorkflowInterpreterBoundaryTest.php` parses the
  workflow and holds both properties structurally, so an edit that moves a PHP
  or Composer invocation back into the write-capable job, drops the 8.5 pin
  from the validating job, reorders validation after the upload, changes the
  uploaded path set out from under the verifier, or introduces a new
  third-party action into `publish` fails the Architecture suite. It also
  records the companion audit: `.github/workflows/admin-dist.yml`, the
  main-branch rebuild, is **unaffected** — it has a single `build-and-publish`
  job that pins `shivammathur/setup-php` at 8.5 itself, so its PHP invocations
  always run under a pinned interpreter and it never had the split; a test
  holds that pin in place. The four blocked PRs are intentionally left alone:
  hand-rebuilding each one clears the symptom and leaves the automation broken
  for the next bump, so they get re-triggered once this lands.
