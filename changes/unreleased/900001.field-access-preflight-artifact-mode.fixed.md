- **Fixed — field-access preflight artifact was written at a private mode, outside Studio's portable-artifact contract (#900001 — PLACEHOLDER, no GitHub issue filed yet; assign a real issue before opening a governed PR):** `field-access:preflight --write-artifact` wrote `.waaseyaa/field-access-preflight.json` via `tempnam()`, which always creates its temp file at mode 0600 regardless of umask, then `rename()`d it into place without ever chmod-ing it — leaving the published artifact at 0600 instead of the {0644, 0755} portable-artifact contract every other generated project file carries (`GeneratedArtifact` already enforces this at construction time). The artifact is required at a later, separate application boot (`FieldAccessActivationPreflight`), typically a different process/user than the CLI invocation that generated it, so a 0600 mode left it unreadable there. `FieldAccessPreflightHandler` now `chmod($temporary, 0o644)` before the publishing `rename()`, mirroring the existing correct pattern in `ConfigManifestEnvelopeFile::write()`.

  A framework-wide discovery pass classified every other atomic-write artifact producer by its artifact contract (portable vs. intentionally private vs. not a persistent artifact); see `docs/change-records/FW-ARTIFACT-MODE-SCOPED-REPAIR-01.md` for the full inventory. Only this one confirmed mismatch — the one PROTOCOL302_BUNDLE_ENTRY actually hit on the community-events starter journey — is repaired here. A new behavioural guard, `tests/Architecture/PortableArtifactModeContractTest.php`, materializes real artifacts through their real production code paths (not a `tempnam(` call-site scan) and asserts on-disk inode modes, covering both this confirmed portable artifact and the site-init transaction journal's intentionally-private 0600 mode, so neither a future regression nor a future false positive on private state goes unnoticed.

  Bounded to `packages/cli/src/Handler/FieldAccessPreflightHandler.php` and its tests. `AuthUiScaffoldManager`, `LocalFileRepository`, and `MediaAssetStore` remain unrepaired this round: none is invoked by the community-events starter's `site:init`/`site:apply`/`site:doctor`/`field-access:preflight` lifecycle (no auth capability, no media fields, no AI capability declared), so no mismatch on this journey was confirmed for them.
